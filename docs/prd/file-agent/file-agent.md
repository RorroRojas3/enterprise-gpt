# PRD: File Agent

## 1. Overview

**Problem.** Enterprise GPT can **read** a document and cannot **produce** one. The ingestion pipeline in `Enterprise.Gpt.Service/DocumentService.cs` extracts, chunks, embeds and vector-searches an uploaded file, and `Service/Tool/DocumentTool.cs` hands the result to the model — but there is no path in the other direction. A user who asks for "that as a spreadsheet" gets a Markdown table pasted into a chat bubble, and every downstream step of their real task happens outside this platform. The rails for the fix are already in the tree, unused: `Program.cs` calls `options.UseAgentToolClassification()` for all four providers, `Andes.Extensions.AI.Agent` 0.5.0 is referenced by `Enterprise.Gpt.Api`, `ConversationToolKinds.Agent = 3` exists, and two code comments are addressed to a feature that does not exist yet — `UsageReportTranslator.cs` leaves `ModelId` null on every tool-call row because "only an agent this application configured could answer, and none exists yet", and `ConversationUsageToolCallConfiguration` omits its `ModelId` index with "add it with the first agent that reports a model".

**Solution.** A specialised **File Agent**, exposed to the main assistant as a single tracked tool, that creates, updates and compares documents by writing and running Python in Microsoft Foundry's sandboxed Code Interpreter, embedding images generated by the shared image tool specified in `docs/prd/image-tool/image-tool.md`. It runs synchronously inside the streaming turn and reports its work through the activity frames the stream already carries. Every token it spends is attributed back to the causing turn. Finished files land in the `generated` blob container as `ConversationDocument` rows with the `Generated` type that PRD establishes, never enter the retrieval index, and reach the user through the document chip and download route it ships, which mint a fresh short-lived signed link on click.

**Success criteria.**

- **Artifact validity**: ≥ 90% of completed File Agent runs return an artifact that passes the deterministic verification pass on the first attempt, measured by `file_agent.verification{outcome="passed"}` over a rolling 7-day window, with 0 runs that report success while producing no file.
- **Token attribution completeness**: 100% of turns that invoke the File Agent write a `Core.ConversationUsageToolCall` row with `Kind = 3` (`Agent`), `Depth = 0`, a **non-null** `ModelId` and at least one child row — measured by a query over that table, and 0 agent rows with a null `ModelId` (the defect the current code comment describes).
- **Retrieval isolation**: 0 rows exist in `Core.ConversationDocumentChunk` for any `ConversationDocument` whose type is `Generated`, and 0 citations in any answer name one — measured by a scheduled query and pinned by an integration test.
- **Turn latency**: p95 elapsed time from the File Agent activity's `ActivityStarted` to its `ActivityCompleted` is ≤ 90 s for a single-artifact create, measured by the `file_agent.run.duration` histogram.
- **Delivery**: ≥ 99% of generated-file chip clicks resolve to a `200` from `GET /api/documents/conversations/{conversationId}/{documentId}` within the link's 5-minute lifetime, measured by that route's success rate filtered to `Generated` documents — a criterion this PRD measures but does not build, because the download route's generated-file coverage and the `Generated` document type both ship in `docs/prd/image-tool/image-tool.md` and are consumed here unchanged.

A user asks for a quarterly summary as a Word document. The assistant calls one tool; a card appears in the timeline labelled with the agent's name and an **Agent** kind badge, and beneath it nested child cards show a chart being drawn, Python being run, and the finished file being re-opened and checked. When the card completes, a document chip sits under the answer — the chip, the download route behind it and the message-level file reference that survives a reload are all delivered by `docs/prd/image-tool/image-tool.md`, which ships before this PRD starts. The user clicks it, the client asks that download route for a link at that moment, and the browser saves `q3-summary.docx`. Nothing about the file re-enters the model's context; nothing about it is retrievable or citable; and the whole turn — the assistant's tokens, the agent's tokens, the image model's tokens and the sandbox session's seconds — is one row and its children in the usage audit.

## 2. Goals & non-goals

**Goals.**

- Let a user get a real `docx`, `xlsx`, `pptx`, `csv`, `md`, `txt` or `pdf` out of a conversation, created, updated or compared by the assistant, without leaving the platform.
- Make the artifact trustworthy by construction: every file is re-opened in the sandbox and asserted against the requested shape (parses, expected sheet/slide/page count, non-zero bytes) before it is returned.
- Attribute every token to the turn that caused it, nested, filling the `ModelId`/`DeploymentName` null the usage translator currently writes and adding the index its configuration currently defers.
- Consume the generated-file contract `docs/prd/image-tool/image-tool.md` establishes — the `Generated` document type, its container, the no-chunks invariant, the message-level file reference and the chip that mints a link on click — without changing it, so a file this platform produces is stored, delivered and kept out of retrieval by exactly one implementation no matter which feature produced it.
- Reuse the streaming contract as it stands: the File Agent is a `depth: 1` activity and its internal steps are `depth: 2` children, folded by the reducer the client already vendors.

**Non-goals.**

- **Image generation, generated-file storage, and the generated-file frontend surface.** All three are specified in `docs/prd/image-tool/image-tool.md` and are a **hard predecessor** of this PRD rather than part of it: that PRD ships the image tool, the `Generated` document type and its container, the message-level file reference, the download route's generated-format coverage and the chip. The image tool has to exist before the File Agent can illustrate anything, because the sandbox has no outbound network access and therefore cannot fetch an image for itself. This PRD consumes all of it unchanged and adds nothing to it.
- **A planner/executor/reviewer topology, or a reviewer LLM.** Settled by the product owner on 2026-08-14. Code Interpreter is already an iterative write→run→see-traceback→retry loop, so a separate executor duplicates it, and a reviewer model cannot open a binary `.docx` to inspect it. The reliable check is deterministic and free, and it is what US-204 ships. A reviewer agent remains a documented seam, not a v1 feature.
- **Background or asynchronous execution.** The agent runs inside the streaming turn. The document ingestion pipeline's queue-and-poll design is deliberately not reused; a user waiting for a file they asked for is a foreground activity with a progress feed, not a job.
- **`xlsm`.** Code Interpreter's supported-upload table lists `.xlsx` and not `.xlsm`, so it is not a viable input; it is deferred and carried as an open question rather than silently dropped.
- **Toolbox-hosted Code Interpreter.** Microsoft states plainly that "when Code Interpreter is used through a toolbox in a hosted agent, user isolation isn't supported. All users in the same project share the same container context." That is disqualifying for a multi-tenant enterprise application, and §6 makes the per-request automatic container a security requirement rather than a preference.
- **Adding `Andes.Extensions.AI.Agent` or `Microsoft.Agents.AI` to `Enterprise.Gpt.Service`.** That project's csproj carries an explicit comment recording the exclusion. The agent is composed in `Enterprise.Gpt.Api` and reaches `ConversationService` through an abstraction, mirroring how `IMcpToolProvider` hands back an `IMcpToolLeaseSet`.
- **New SSE frame kinds, or any change to the `Andes.Extensions.AI.UI` event contract.** `AssistantUiEvent` already carries `ActivityStarted`/`ActivityProgress`/`ActivityCompleted`/`ActivityFailed` with `scopeId`, `parentScopeId`, `displayName`, `toolKind` and `depth`, and nesting is already modelled and already folded. Adding a kind would be a breaking change to a third-party package shape and a drift failure in `npm run check:contract`.
- **New RFC 9457 problem type URIs.** The failure modes this feature introduces happen mid-stream and surface as failed activity cards; the pre-stream ones reuse `/problems/provider-not-configured` and `/problems/storage-not-configured`. Problem types are opaque identifiers clients match verbatim, and this PRD adds none.
- **Generated documents on projects.** The type discriminator `docs/prd/image-tool/image-tool.md` adds goes on `ConversationDocument`, not on `BaseDocument`, so `ProjectDocument` is untouched and nothing in this PRD writes a project-scoped generated file. The symmetry is deliberately deferred.
- **Templates, brand styling, or corporate document themes.** The sandbox cannot reach a font CDN or a template store, and nothing in this PRD uploads one.
- **Opening or editing a generated document in the browser.** The deliverable is a downloaded file.
- **Documentation stories.** Docs under `docs/` and the `CHANGELOG.md` entry are the SE Technical Writer flow's job, after implementation.

## 3. Users & access

**Personas.**

- **Chat user**: a signed-in employee holding a conversation. Asks for a file in natural language; never selects the File Agent, because it is an implicit tool the assistant chooses like document retrieval.
- **Administrator**: holds `PermissionIds.Administrator` (`a0b1c2d3-e4f5-4a6b-8c7d-9e0f1a2b3c4d`). Grants the file-generation permission and reads what the feature costs.
- **Operator**: runs the deployment. Consumes the telemetry this PRD adds, holds the feature flags, and owns the decision to switch the feature off without a redeploy.
- **Backend engineer**: owns EP-0 through EP-3, working in `enterprise-gpt-api/` under `.claude/rules/csharp.md` and `aspnet-rest-apis.md`.
- **Frontend engineer**: owns EP-4, working in `enterprise-gpt-ui/` under the `ngrx-signal-store` and `angular-developer` skills.

**Role-based access.**

- **Anonymous**: no access. Every route this feature touches is inside a group already carrying `.RequireAuthorization()`.
- **Chat user without the file-generation grant**: conversations behave exactly as they do today. The File Agent tool is **not attached** to their turns and the assistant is told nothing about it, so it cannot advertise a capability the user does not have. This mirrors how `Upload File` gates the upload affordance rather than producing a 403 on a resource the caller never named.
- **Chat user with the file-generation grant**: the tool is attached to turns on a tool-enabled model. They can download any generated file in a conversation they own, through the same route and the same ownership rule that already serves uploaded documents — ownership is read off the **parent conversation**, and a miss is a 404, never a 403 (`docs/documents/download-workflow.md` §3.1, §3.3).
- **Administrator**: grants and revokes the permission through the existing `api/permissions` surface. Administrators are **not** implicitly granted it, matching the codebase's standing rule that an administrator holds only what they were given.

The grant is resolved through the singleton `IUserPermissionCache`, the same path `PermissionEndpointFilter` uses, and is invalidated per user by `PermissionService` exactly as every other grant already is. Whether it is the existing `Upload File` permission or a new `Generate File` one is **open question 2**, now owned by `docs/prd/image-tool/image-tool.md`; US-211 gates the File Agent on whichever the product owner picks there and states both consequences.

## 5. User experience

**Entry points & first-time flow.** There is no new screen, no new menu item and no picker. A user with the grant simply asks — "make me a spreadsheet of these numbers", "turn this into a deck", "what changed between these two documents" — and the assistant decides to call the tool, exactly as it already decides to call document retrieval. A user without the grant sees no difference from today, because the tool is not attached; nothing renders an unavailable panel, since there is no surface to render it in.

**Core experience.**

1. The user sends a prompt in the existing composer. Nothing about the composer changes.
2. The assistant calls the File Agent. An activity card appears in the timeline at `depth: 1`, labelled with the agent's `displayName` and carrying an **Agent** kind badge — rendered separately, per the streaming contract's rule that a pre-composed label like "Calling File Agent" is a defect.
3. Child cards appear nested inside it at `depth: 2` as the agent works: the image tool when a chart or picture is needed, the code interpreter as Python is written and run, and the verification pass as the finished artifact is re-opened and checked. Sub-status lines beneath each come from `ChatProgress.Report(...)`, which is the only channel that reaches the feed.
4. The agent card completes with a duration. The answer text continues streaming around it.
5. The finished file reaches the user through the generated-file surface `docs/prd/image-tool/image-tool.md` delivers, unchanged: a document chip under the assistant's message, distinguishable from an upload chip, whose click mints a fresh five-minute link at that moment and whose reference is persisted on the message so it survives a reload. Two things are specific to a File Agent artifact. The chip appears only after the verification pass has passed, so a failed run leaves the answer text and no chip at all. And when the conversation is reopened, the activity tree above the chip is **not** replayed — only the answer text and the file references are, matching the existing rule that reopening a conversation replays the answer and never the work that produced it.

**Edge cases & UI states.**

- **Working**: the agent card shows a running ring and its nested children as they arrive. Between the tool call and the first child there may be several seconds of silence; the card's own running state fills that, not a fabricated sub-status.
- **Verification failed**: the agent retried and could not produce an artifact matching the requested shape. The card renders failed with the reason, the assistant explains it in prose, and **no chip renders**. A failed run must never leave a chip pointing at a file that does not parse.
- **No file produced**: the run returned text only. Rendered as a failed activity with "no file was produced", not as a completed turn — Microsoft documents this case explicitly and it is the single most misleading failure available.
- **Cancelled**: the user pressed Stop mid-run. The agent card renders failed/cancelled, the partial answer becomes the existing detached "Stopped — not saved" card, and no document row survives.
- **Busy**: a second turn while one is streaming still returns 409 `conversation-busy`, surfaced as a retryable warning and never auto-retried. A long File Agent run makes this window wider, which is a reason the warning copy must name the running turn rather than read as a generic error.
- **Feature off**: with the flag disabled, turns behave exactly as they do today. There is no "file generation is unavailable" panel, because there is no surface that promised it.

**UI/UX highlights.**

- A File Agent artifact reuses the generated-file chip variant `docs/prd/image-tool/image-tool.md` establishes on `shared/chip/attachment-chip`; this PRD introduces no chip of its own and changes nothing about that one.
- The nested activity rendering is the one `features/chat/transcript/activity-card.ts` already performs for MCP children. This feature adds no new card shape — it is the first producer of a `depth: 2` subtree under an `Agent`-kind parent, which is why US-401 is scheduled after the agent actually emits frames rather than against a fixture alone.
- Keyboard: the chip is a real `<button>`, reachable in tab order, activated by Enter and Space, with focus returning to it after the download starts. Activity cards keep the existing expand/collapse semantics.
- Announcements: the chip's appearance is announced once through the transcript's existing `aria-live` region; the streaming sub-status lines are **not** announced individually, because a polite region that fires on every progress line is unusable.
- Motion honours `prefers-reduced-motion`, using the four keyframes already defined in the token layer. No new keyframe is introduced.

**One registration that does not exist yet.** Every chat provider today registers through `AddKeyedChatClient` over an `OpenAIClient` pointed at `{resource}/openai/v1/`. Code Interpreter needs something different: an `AIProjectClient` against a **project** endpoint of the form `https://{resource}.services.ai.azure.com/api/projects/{project}`, plus `Azure.AI.Projects` and the preview OpenAI extension package. This is a genuinely new registration with its own options class, its own `Enabled` flag and its own `ValidateOnStart` validators — not a variation on an existing one. It is also the **only** registration this PRD adds to `Program.cs`: the image-generation client is `docs/prd/image-tool/image-tool.md`'s and is already in place before this PRD starts, so the two never edit that file at the same time.

**Where the agent is composed.** `Enterprise.Gpt.Service.csproj` references `Andes.Extensions.AI`, `.Mcp` and `.UI` and pointedly **not** `.Agent`, with a comment recording the exclusion. That stands. The File Agent is built in `Enterprise.Gpt.Api` and reaches `ConversationService` through an abstraction that hands back an `AITool` plus a disposable lifetime, mirroring the `IMcpToolProvider` → `IMcpToolLeaseSet` shape the service already consumes. The abstraction lives in `Enterprise.Gpt.Service` (where the consumer is); only its implementation lives in `Api`.

**Data storage & privacy.**

- **The generated-file contract belongs to `docs/prd/image-tool/image-tool.md` and is consumed unchanged.** Four decisions are settled there and are not re-opened here: the document-type discriminator on `ConversationDocument` (and deliberately not on `BaseDocument`), the separate `generated` blob container with its own retention profile, the invariant that a generated document has **no chunks** and is therefore structurally absent from `DocumentRetrievalSql`'s `UNION ALL` of the two chunk tables, and the message-level file reference that carries an identity — id, name, extension, MIME type, size, type — and never a URL. This PRD writes its artifacts through that path and reads them through that contract; it adds no second shape and changes none of the four.
- **Prompt content never leaves the turn's normal path.** Sandbox code and tool arguments are not written to progress events; `ToolTrackingOptions.IncludeToolArguments` stays off, and the middleware's default posture of keeping arguments and results out of activity frames is unchanged.

**Security.**

- **Per-request container isolation is a requirement, not a tuning choice.** The tool is configured with `CodeInterpreterToolContainerConfiguration.CreateAutomaticContainerConfiguration(fileIds: […])` so each request gets its own container. A toolbox-hosted Code Interpreter shares one container context across every user in the project, which would let one user's uploaded input be visible to another's run. No story in this PRD may introduce a toolbox path.
- **The sandbox has no outbound network access.** Foundry dynamic sessions cannot make outbound requests, so the sandbox cannot read Blob Storage, call an image API, or fetch a font or CDN asset. Every input is uploaded into the container by the API and every output is pulled back out by the API. This is also the reason `docs/prd/image-tool/image-tool.md` is a hard predecessor of this PRD rather than a convenience.
- **PDF fidelity is bounded by that fact.** With no reachable web fonts, a PDF the sandbox produces will look plainer than a Word-exported one. US-205 states this as a criterion rather than implying a fidelity the platform cannot deliver.
- **Generated content is model output and is treated as untrusted.** It is served with the existing `attachment` `Content-Disposition` and a signed `Content-Type` derived from the extension, never from a declared MIME type — the same posture the upload path already takes, for the same reason: an `inline` disposition would let generated HTML or SVG execute on the storage origin.
- **SAS signing still requires a shared-key connection string.** `BlobBaseClient.CanGenerateSasUri` is true only for a `StorageSharedKeyCredential`; moving to `DefaultAzureCredential` would require a user delegation SAS. The second container `docs/prd/image-tool/image-tool.md` adds changes nothing about that constraint and does not resolve it.
- **File size is capped.** A generated file is subject to the same ceiling as an upload (`Documents:MaxFileSizeBytes`, 50 MB), enforced when the artifact is pulled out of the container, so a runaway script cannot write an unbounded blob.

**Scalability & performance.**

- A Code Interpreter session stays active for up to an hour with a 30-minute idle timeout, and **each concurrent conversation gets its own session**. Sessions are billed on top of token fees, so token counting alone does not capture this feature's cost — which is why FR-20 exists as a distinct requirement rather than a footnote on FR-19.
- The run is synchronous inside a turn that already holds a conversation lock, so a slow run widens the window in which a second turn gets 409 `conversation-busy`. US-210 bounds it; US-105 bounds the sandbox itself.
- `FunctionInvokingChatClient.MaximumIterationsPerRequest = 5` bounds the **outer** assistant's tool loop. The File Agent's own pipeline needs its own bound, configured on its own registration; inheriting the outer number by accident is a defect, not a default.
- The upload/download round trip into and out of the container is the dominant latency for large inputs. Inputs are uploaded once per run, not once per iteration.

**AI system requirements.**

- **Tools the system needs**: Code Interpreter (per-request automatic container) and `gpt-5.6-sol` as the File Agent's model, both gated by EP-0 before any code depends on them, plus the image-generation deployment `docs/prd/image-tool/image-tool.md` provisions and gates on its own.
- **The primary evaluation is deterministic and free**: after generating, the agent runs a second sandbox snippet that re-opens the artifact and asserts it parses and matches the requested shape — sheet count for `xlsx`, slide count for `pptx`, page count for `pdf`, non-zero bytes for all. That check is an acceptance criterion (US-204), not a metric, and its outcome is what the artifact-validity success criterion counts.
- **Offline benchmark and pass threshold**: a fixed benchmark of 30 prompts spanning all seven create formats and both the update and compare verbs. Pass threshold before EP-2 is accepted: **≥ 90% produce an artifact that passes verification within the agent's iteration budget**, and **100% of the remainder surface as a failed activity card** — a silent text-only answer counts as a failure of the benchmark regardless of the text's quality.
- **Activity labels are never pre-composed.** `displayName` and `kind` are rendered separately by the client; the agent supplies a name, not a sentence.

- **Story**: As an operator, I want File Agent activity in the traces I already collect, so that a slow or failing run is diagnosable without reading application logs.
- **Priority**: P1 · **Estimate**: M · **Depends on**: US-201
- **Status**: Not started
- **Acceptance criteria**:
  - Given a new `ActivitySource`/`Meter` pair, when it is registered, then it is added by name in `TelemetryRegistration.AddEnterpriseTelemetry`'s `WithTracing`/`WithMetrics` calls, following the one-line-per-source pattern `ChatTelemetrySourceName` already establishes.
  - Given the instruments, when they are constructed, then they live in `Enterprise.Gpt.Service` and never in `Api`, because `Service` does not depend on `Api`.
  - Given a run, when it completes, then `file_agent.run.duration` records elapsed time and `file_agent.verification` increments with a pass/fail outcome — the direct sources for two of the section 1 success criteria.
  - Given an image call made **inside** an agent run, when its span is emitted, then it is a child of the agent's span; image activity outside an agent run belongs to `docs/prd/image-tool/image-tool.md` and this story adds nothing to it.
  - Given any instrument, when its tags are inspected, then none carries prompt content, a tool argument, generated source code, a file name that is user content, or a signed URL.

#### US-306: See what file generation costs

- **Story**: As an administrator, I want to see what the platform is spending on file generation and who is spending it, so that I can decide whether the ceiling is right.
- **Priority**: P2 · **Estimate**: M · **Depends on**: US-303, US-304
- **Status**: Not started
- **Acceptance criteria**:
  - Given the audit rows and the session metric, when a report is produced, then it breaks down agent tokens, image tokens and sandbox seconds by user and by model over a period — the image tool itself is `docs/prd/image-tool/image-tool.md`'s, and its calls appear here as children of an agent row.
  - Given there is **no HTTP surface over `ConversationUsage` today**, when this story is scheduled, then it either extends the usage endpoint that `docs/prd/enterprise-ui-rebuild.md`'s US-1301 introduces, or reports through the telemetry backend alone — this story does not invent a second usage API beside that one.
  - Given a period with no File Agent activity, when the report is read, then it reads as zero rather than as missing data.
  - Given the report, when it renders per-model figures, then it uses the `(ModelId, DateCreated)` index from US-302 rather than a table scan.

#### US-307: Bound what one user can spend

- **Story**: As an operator, I want a ceiling on file generation per user or per conversation, so that one person's afternoon cannot become the month's cost anomaly.
- **Priority**: P1 · **Estimate**: M · **Depends on**: US-304
- **Status**: Not started
- **Acceptance criteria**:
  - Given the ceiling the product owner chooses (open question 1) — per user per day, per conversation, or telemetry-only at launch — when it is configured, then a request that would exceed it does not run and the assistant tells the user the limit was reached.
  - Given the ceiling is unset, when the feature runs, then it behaves exactly as it does without this story, so the ceiling is opt-in rather than a surprise default.
  - Given a user at the ceiling, when they hit it, then the refusal is a stood-down tool and a plain explanation, not a 403 or a failed turn.
  - Given the ceiling, when it is measured against, then it counts both tokens and sandbox seconds, because a token-only ceiling misses the part of the bill US-304 exists to expose.

### EP-4: Frontend surface

#### US-401: Watch the File Agent work

- **Story**: As a chat user, I want to see what the assistant is doing while it builds my file, so that a long wait reads as progress rather than as a hang.
- **Priority**: P1 · **Estimate**: M · **Depends on**: US-202
- **Status**: Not started
- **Acceptance criteria**:
  - Given a turn that calls the File Agent, when the stream is folded, then a `depth: 1` activity card renders with the agent's `displayName` and an **Agent** kind badge shown as separate elements — a pre-composed label like "Calling File Agent" fails this criterion.
  - Given the agent's internal steps, when they arrive as `depth: 2` events with a `parentScopeId` naming the agent's scope, then they render nested inside the agent card, using the nesting `activity-card.ts` already performs.
  - Given the stream, when it is inspected, then **no new `AssistantUiEvent` kind** was added and `npm run check:contract` still passes against the vendored `Andes.Extensions.AI.UI` 0.5.0 contract.
  - Given an activity that completes, when it renders, then its `durationSeconds` is shown; given one that fails, then the failed state renders with its reason.
  - Given the window between the tool call and the first child event, when it is rendered, then the agent card's own running state fills it — no sub-status line is fabricated to cover the gap.

#### US-402: Generated-file failure states

- **Story**: As a chat user, I want a failed file request to look like a failure, so that I do not wait for a chip that is never coming.
- **Priority**: P1 · **Estimate**: M · **Depends on**: US-401, US-209
- **Status**: Not started
- **Acceptance criteria**:
  - Given an `ActivityFailed` on the agent's scope, when it renders, then the card shows failed with its reason and **no chip renders** for that turn.
  - Given the three distinct backend outcomes — verification failed, no file produced, and the run threw — when each renders, then the copy differs; a single generic "something went wrong" fails this criterion.
  - Given a turn cancelled by Stop, when it renders, then the existing detached "Stopped — not saved" card appears and no chip does.
  - Given a stream that ends with no `Finished` event during a File Agent run, when it renders, then the existing truncated-turn treatment applies unchanged — this story adds no fourth truncation signal.

#### US-403: Use the generated-file surface without a mouse

- **Story**: As a chat user relying on a keyboard or a screen reader, I want to reach and download a generated file, so that the feature is usable rather than decorative.
- **Priority**: P0 · **Estimate**: M · **Depends on**: US-401, plus the generated-file chip story in `docs/prd/image-tool/image-tool.md`
- **Status**: Not started
- **Acceptance criteria**:
  - Given the chip, when the transcript is navigated by keyboard, then it is a real `<button>` in tab order, activated by Enter and Space, with a visible focus ring meeting the app's focus-indicator contrast, and focus returns to it after the download begins.
  - Given a screen reader, when a chip is focused, then its accessible name states that the file was generated and names it — the icon is not the only carrier of that distinction.
  - Given a chip appearing at the end of a turn, when it renders, then it is announced once through the transcript's existing `aria-live` region; the streaming `depth: 2` sub-status lines are **not** announced individually.
  - Given the axe-core run on the chat route in both themes, when this story lands, then it reports 0 serious or critical violations attributable to the new chip or the agent activity subtree.
  - Given `prefers-reduced-motion: reduce`, when the agent card's running indicator renders, then its animation is suppressed using the existing motion rules; no new keyframe is added.
