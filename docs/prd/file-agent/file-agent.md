# PRD: File Agent

## 1. Overview

**Problem.** Enterprise GPT can **read** a document and cannot **produce** one. The ingestion pipeline in `Enterprise.Gpt.Service/DocumentService.cs` extracts, chunks, embeds and vector-searches an uploaded file, and `Service/Tool/DocumentTool.cs` hands the result to the model — but there is no path in the other direction. A user who asks for "that as a spreadsheet" gets a Markdown table pasted into a chat bubble, and every downstream step of their real task happens outside this platform. The rails for the fix are already in the tree, unused: `Program.cs` calls `options.UseAgentToolClassification()` for all four providers, `Andes.Extensions.AI.Agent` 0.5.0 is referenced by `Enterprise.Gpt.Api`, `ConversationToolKinds.Agent = 3` exists, and two code comments are addressed to a feature that does not exist yet — `UsageReportTranslator.cs` leaves `ModelId` null on every tool-call row because "only an agent this application configured could answer, and none exists yet", and `ConversationUsageToolCallConfiguration` omits its `ModelId` index with "add it with the first agent that reports a model".

**Solution.** A specialised **File Agent**, exposed to the main assistant as a single tracked tool, that creates, updates and compares documents by writing and running Python in Microsoft Foundry's sandboxed Code Interpreter, embedding images generated by a shared image tool. It runs synchronously inside the streaming turn and reports its work through the activity frames the stream already carries. Every token it spends is attributed back to the causing turn. Finished files land in a `generated` blob container as `ConversationDocument` rows with a new `Generated` type, never enter the retrieval index, and reach the user as a document chip that mints a fresh short-lived signed link on click.

**Success criteria.**

- **Artifact validity**: ≥ 90% of completed File Agent runs return an artifact that passes the deterministic verification pass on the first attempt, measured by `file_agent.verification{outcome="passed"}` over a rolling 7-day window, with 0 runs that report success while producing no file.
- **Token attribution completeness**: 100% of turns that invoke the File Agent write a `Core.ConversationUsageToolCall` row with `Kind = 3` (`Agent`), `Depth = 0`, a **non-null** `ModelId` and at least one child row — measured by a query over that table, and 0 agent rows with a null `ModelId` (the defect the current code comment describes).
- **Retrieval isolation**: 0 rows exist in `Core.ConversationDocumentChunk` for any `ConversationDocument` whose type is `Generated`, and 0 citations in any answer name one — measured by a scheduled query and pinned by an integration test.
- **Turn latency**: p95 elapsed time from the File Agent activity's `ActivityStarted` to its `ActivityCompleted` is ≤ 90 s for a single-artifact create, measured by the `file_agent.run.duration` histogram.
- **Delivery**: ≥ 99% of generated-file chip clicks resolve to a `200` from `GET /api/documents/conversations/{conversationId}/{documentId}` within the link's 5-minute lifetime, measured by that route's success rate filtered to `Generated` documents.

A user asks for a quarterly summary as a Word document. The assistant calls one tool; a card appears in the timeline labelled with the agent's name and an **Agent** kind badge, and beneath it nested child cards show a chart being drawn, Python being run, and the finished file being re-opened and checked. When the card completes, a document chip sits under the answer. The user clicks it, the client asks the existing download route for a link at that moment, and the browser saves `q3-summary.docx`. Nothing about the file re-enters the model's context; nothing about it is retrievable or citable; and the whole turn — the assistant's tokens, the agent's tokens, the image model's tokens and the sandbox session's seconds — is one row and its children in the usage audit.

## 2. Goals & non-goals

**Goals.**

- Let a user get a real `docx`, `xlsx`, `pptx`, `csv`, `md`, `txt` or `pdf` out of a conversation, created, updated or compared by the assistant, without leaving the platform.
- Ship image generation first, as its own capability, callable both directly by the main assistant and from inside the File Agent — because the sandbox has no outbound network access and therefore cannot fetch an image for itself.
- Make the artifact trustworthy by construction: every file is re-opened in the sandbox and asserted against the requested shape (parses, expected sheet/slide/page count, non-zero bytes) before it is returned.
- Attribute every token to the turn that caused it, nested, filling the `ModelId`/`DeploymentName` null the usage translator currently writes and adding the index its configuration currently defers.
- Keep a generated document structurally unreachable from retrieval — it has an owner and an identity, and it has **no chunks**, so it cannot be ranked or cited.
- Deliver the file as an identity plus a link minted on click, so no bearer credential is ever written into the Cosmos transcript or an SSE frame.
- Reuse the streaming contract as it stands: the File Agent is a `depth: 1` activity and its internal steps are `depth: 2` children, folded by the reducer the client already vendors.

**Non-goals.**

- **A planner/executor/reviewer topology, or a reviewer LLM.** Settled by the product owner on 2026-08-14. Code Interpreter is already an iterative write→run→see-traceback→retry loop, so a separate executor duplicates it, and a reviewer model cannot open a binary `.docx` to inspect it. The reliable check is deterministic and free, and it is what US-404 ships. A reviewer agent remains a documented seam, not a v1 feature.
- **Background or asynchronous execution.** The agent runs inside the streaming turn. The document ingestion pipeline's queue-and-poll design is deliberately not reused; a user waiting for a file they asked for is a foreground activity with a progress feed, not a job.
- **`xlsm`.** Code Interpreter's supported-upload table lists `.xlsx` and not `.xlsm`, so it is not a viable input; it is deferred and carried as an open question rather than silently dropped.
- **Toolbox-hosted Code Interpreter.** Microsoft states plainly that "when Code Interpreter is used through a toolbox in a hosted agent, user isolation isn't supported. All users in the same project share the same container context." That is disqualifying for a multi-tenant enterprise application, and §6 makes the per-request automatic container a security requirement rather than a preference.
- **Adding `Andes.Extensions.AI.Agent` or `Microsoft.Agents.AI` to `Enterprise.Gpt.Service`.** That project's csproj carries an explicit comment recording the exclusion. The agent is composed in `Enterprise.Gpt.Api` and reaches `ConversationService` through an abstraction, mirroring how `IMcpToolProvider` hands back an `IMcpToolLeaseSet`.
- **New SSE frame kinds, or any change to the `Andes.Extensions.AI.UI` event contract.** `AssistantUiEvent` already carries `ActivityStarted`/`ActivityProgress`/`ActivityCompleted`/`ActivityFailed` with `scopeId`, `parentScopeId`, `displayName`, `toolKind` and `depth`, and nesting is already modelled and already folded. Adding a kind would be a breaking change to a third-party package shape and a drift failure in `npm run check:contract`.
- **New RFC 9457 problem type URIs.** The failure modes this feature introduces happen mid-stream and surface as failed activity cards; the pre-stream ones reuse `/problems/provider-not-configured` and `/problems/storage-not-configured`. Problem types are opaque identifiers clients match verbatim, and this PRD adds none.
- **Generated documents on projects.** The type discriminator goes on `ConversationDocument`, not on `BaseDocument`, so `ProjectDocument` is untouched. The symmetry is deliberately deferred.
- **Templates, brand styling, or corporate document themes.** The sandbox cannot reach a font CDN or a template store, and nothing in this PRD uploads one.
- **Opening or editing a generated document in the browser.** The deliverable is a downloaded file.
- **Documentation stories.** Docs under `docs/` and the `CHANGELOG.md` entry are the SE Technical Writer flow's job, after implementation.

## 3. Users & access

**Personas.**

- **Chat user**: a signed-in employee holding a conversation. Asks for a file in natural language; never selects the File Agent, because it is an implicit tool the assistant chooses like document retrieval.
- **Administrator**: holds `PermissionIds.Administrator` (`a0b1c2d3-e4f5-4a6b-8c7d-9e0f1a2b3c4d`). Grants the file-generation permission and reads what the feature costs.
- **Operator**: runs the deployment. Consumes the telemetry this PRD adds, holds the feature flags, and owns the decision to switch the feature off without a redeploy.
- **Backend engineer**: owns EP-0 through EP-5, working in `enterprise-gpt-api/` under `.claude/rules/csharp.md` and `aspnet-rest-apis.md`.
- **Frontend engineer**: owns EP-6, working in `enterprise-gpt-ui/` under the `ngrx-signal-store` and `angular-developer` skills.

**Role-based access.**

- **Anonymous**: no access. Every route this feature touches is inside a group already carrying `.RequireAuthorization()`.
- **Chat user without the file-generation grant**: conversations behave exactly as they do today. The File Agent tool is **not attached** to their turns and the assistant is told nothing about it, so it cannot advertise a capability the user does not have. This mirrors how `Upload File` gates the upload affordance rather than producing a 403 on a resource the caller never named.
- **Chat user with the file-generation grant**: the tool is attached to turns on a tool-enabled model. They can download any generated file in a conversation they own, through the same route and the same ownership rule that already serves uploaded documents — ownership is read off the **parent conversation**, and a miss is a 404, never a 403 (`docs/documents/download-workflow.md` §3.1, §3.3).
- **Administrator**: grants and revokes the permission through the existing `api/permissions` surface. Administrators are **not** implicitly granted it, matching the codebase's standing rule that an administrator holds only what they were given.

The grant is resolved through the singleton `IUserPermissionCache`, the same path `PermissionEndpointFilter` uses, and is invalidated per user by `PermissionService` exactly as every other grant already is. Whether it is the existing `Upload File` permission or a new `Generate File` one is **open question 2**; US-411 ships whichever the product owner picks and states both consequences.

## 5. User experience

**Entry points & first-time flow.** There is no new screen, no new menu item and no picker. A user with the grant simply asks — "make me a spreadsheet of these numbers", "turn this into a deck", "what changed between these two documents" — and the assistant decides to call the tool, exactly as it already decides to call document retrieval. A user without the grant sees no difference from today, because the tool is not attached; nothing renders an unavailable panel, since there is no surface to render it in.

**Core experience.**

1. The user sends a prompt in the existing composer. Nothing about the composer changes.
2. The assistant calls the File Agent. An activity card appears in the timeline at `depth: 1`, labelled with the agent's `displayName` and carrying an **Agent** kind badge — rendered separately, per the streaming contract's rule that a pre-composed label like "Calling File Agent" is a defect.
3. Child cards appear nested inside it at `depth: 2` as the agent works: the image tool when a chart or picture is needed, the code interpreter as Python is written and run, and the verification pass as the finished artifact is re-opened and checked. Sub-status lines beneath each come from `ChatProgress.Report(...)`, which is the only channel that reaches the feed.
4. The agent card completes with a duration. The answer text continues streaming around it.
5. A **document chip** renders under the assistant's message: file name, extension glyph, size. It is a variant of the existing `shared/chip/attachment-chip` component, distinguished from an upload chip so a reader can tell a file the assistant made from a file they gave it.
6. Clicking the chip calls `GET /api/documents/conversations/{conversationId}/{documentId}` at that moment, and `DocumentDownloadStore` hands the returned URL to a detached anchor. The link is never prefetched, never stored, never placed in a router URL. This is the shipped US-804 path, unchanged.
7. Reopening the conversation later replays the transcript, the chip renders again from the reference persisted on the message, and the click mints a **fresh** five-minute link. The activity tree is not replayed — only the answer text and the file references are transcribed, matching the existing rule that reopening a conversation replays the answer and never the work that produced it.

**Edge cases & UI states.**

- **Working**: the agent card shows a running ring and its nested children as they arrive. Between the tool call and the first child there may be several seconds of silence; the card's own running state fills that, not a fabricated sub-status.
- **Verification failed**: the agent retried and could not produce an artifact matching the requested shape. The card renders failed with the reason, the assistant explains it in prose, and **no chip renders**. A failed run must never leave a chip pointing at a file that does not parse.
- **No file produced**: the run returned text only. Rendered as a failed activity with "no file was produced", not as a completed turn — Microsoft documents this case explicitly and it is the single most misleading failure available.
- **Cancelled**: the user pressed Stop mid-run. The agent card renders failed/cancelled, the partial answer becomes the existing detached "Stopped — not saved" card, and no document row survives.
- **Download expired or gone**: a `404` from the download route reads as "no longer available", not "deleted", because the same status covers a document that was never the caller's. A `503` `/problems/storage-not-configured` reads as a deployment fact about the platform, not a fault of that file. Both behaviours already exist in `DocumentDownloadStore` and are inherited.
- **Busy**: a second turn while one is streaming still returns 409 `conversation-busy`, surfaced as a retryable warning and never auto-retried. A long File Agent run makes this window wider, which is a reason the warning copy must name the running turn rather than read as a generic error.
- **Feature off**: with the flag disabled, turns behave exactly as they do today. There is no "file generation is unavailable" panel, because there is no surface that promised it.

**UI/UX highlights.**

- The chip reuses `shared/chip/attachment-chip` and its existing variant set rather than introducing a second chip component; the generated variant differs by its leading glyph and its accessible name ("Generated file, {name}"), so a screen-reader user is told which kind of file it is without relying on the icon.
- The nested activity rendering is the one `features/chat/transcript/activity-card.ts` already performs for MCP children. This feature adds no new card shape — it is the first producer of a `depth: 2` subtree under an `Agent`-kind parent, which is why US-604 is scheduled after the agent actually emits frames rather than against a fixture alone.
- Keyboard: the chip is a real `<button>`, reachable in tab order, activated by Enter and Space, with focus returning to it after the download starts. Activity cards keep the existing expand/collapse semantics.
- Announcements: the chip's appearance is announced once through the transcript's existing `aria-live` region; the streaming sub-status lines are **not** announced individually, because a polite region that fires on every progress line is unusable.
- Motion honours `prefers-reduced-motion`, using the four keyframes already defined in the token layer. No new keyframe is introduced.

**Two registrations that do not exist yet.** Every chat provider today registers through `AddKeyedChatClient` over an `OpenAIClient` pointed at `{resource}/openai/v1/`. Code Interpreter needs something different: an `AIProjectClient` against a **project** endpoint of the form `https://{resource}.services.ai.azure.com/api/projects/{project}`, plus `Azure.AI.Projects` and the preview OpenAI extension package. This is a genuinely new registration with its own options class, its own `Enabled` flag and its own `ValidateOnStart` validators — not a variation on an existing one. The image tool is a second new registration on the image-generation surface. **Both land in `Program.cs`, which is the one real merge collision in this plan**; §8 sequences around it.

**Where the agent is composed.** `Enterprise.Gpt.Service.csproj` references `Andes.Extensions.AI`, `.Mcp` and `.UI` and pointedly **not** `.Agent`, with a comment recording the exclusion. That stands. The File Agent is built in `Enterprise.Gpt.Api` and reaches `ConversationService` through an abstraction that hands back an `AITool` plus a disposable lifetime, mirroring the `IMcpToolProvider` → `IMcpToolLeaseSet` shape the service already consumes. The abstraction lives in `Enterprise.Gpt.Service` (where the consumer is); only its implementation lives in `Api`.

**Data storage & privacy.**

- **The type discriminator goes on `ConversationDocument`, not `BaseDocument`.** Putting it on the base would change `ProjectDocument` too, which nothing in this PRD produces. The enum belongs in `Enterprise.Gpt.Dto/Enums/` beside `JobStatus` and `FileExtensions`, and follows the same append-only rule: values are frozen once deployed and new ones are appended, never renumbered. The column name equals the property name — **no `HasColumnName` exists anywhere in this repository**, and the hand-written retrieval SQL depends on that holding.
- **Generated files live in their own container**, `AzureStorage:GeneratedContainer`, separate from `AzureStorage:DocumentsContainer`. Separate because the two have different retention profiles (open question 3) and because a container-level lifecycle policy is the only cheap way to express that difference.
- **A generated document has no chunks. This is the invariant that must never regress.** `DocumentRetrievalSql` builds its candidate set by `UNION ALL`-ing the two *chunk* tables; a document with zero chunk rows contributes nothing to either side and cannot be retrieved, ranked or cited. No type predicate is needed and **no SQL change is required** — which is precisely why the invariant has to be stated and tested rather than assumed, since nothing in the query would break if chunks appeared.
- **The transcript carries an identity, never a credential.** `DocumentDownloadDto.downloadUrl` is a bearer credential that cannot be revoked (`docs/documents/download-workflow.md` §5.4) and dies in five minutes. A URL written into an assistant message would be both a persisted secret and dead by the time anyone re-read the conversation. **Resolved design decision:** `CosmosConversationMessage` gains an `attachments[]` array shaped like `CosmosConversationDocument` plus the type discriminator — `{ id, name, extension, mimeType, size, type }`, no URL. The conversation-level `CosmosConversation.Documents[]` is **not** reused: it answers "what files does this conversation hold", is written by the upload path, and carries no message linkage, so a chip could not be placed back on the message that produced it, and a generated file would masquerade as conversation-scope input to anything reading that array. The addition is small against the Cosmos 2 MB item cap.
- **Prompt content never leaves the turn's normal path.** Sandbox code and tool arguments are not written to progress events; `ToolTrackingOptions.IncludeToolArguments` stays off, and the middleware's default posture of keeping arguments and results out of activity frames is unchanged.

**Security.**

- **Per-request container isolation is a requirement, not a tuning choice.** The tool is configured with `CodeInterpreterToolContainerConfiguration.CreateAutomaticContainerConfiguration(fileIds: […])` so each request gets its own container. A toolbox-hosted Code Interpreter shares one container context across every user in the project, which would let one user's uploaded input be visible to another's run. No story in this PRD may introduce a toolbox path.
- **The sandbox has no outbound network access.** Foundry dynamic sessions cannot make outbound requests, so the sandbox cannot read Blob Storage, call an image API, or fetch a font or CDN asset. Every input is uploaded into the container by the API and every output is pulled back out by the API. This is also the reason the image tool is a hard predecessor rather than a convenience.
- **PDF fidelity is bounded by that fact.** With no reachable web fonts, a PDF the sandbox produces will look plainer than a Word-exported one. US-405 states this as a criterion rather than implying a fidelity the platform cannot deliver.
- **Generated content is model output and is treated as untrusted.** It is served with the existing `attachment` `Content-Disposition` and a signed `Content-Type` derived from the extension, never from a declared MIME type — the same posture the upload path already takes, for the same reason: an `inline` disposition would let generated HTML or SVG execute on the storage origin.
- **SAS signing still requires a shared-key connection string.** `BlobBaseClient.CanGenerateSasUri` is true only for a `StorageSharedKeyCredential`; moving to `DefaultAzureCredential` would require a user delegation SAS. Adding a second container changes nothing about that constraint and does not resolve it.
- **File size is capped.** A generated file is subject to the same ceiling as an upload (`Documents:MaxFileSizeBytes`, 50 MB), enforced when the artifact is pulled out of the container, so a runaway script cannot write an unbounded blob.

**Scalability & performance.**

- A Code Interpreter session stays active for up to an hour with a 30-minute idle timeout, and **each concurrent conversation gets its own session**. Sessions are billed on top of token fees, so token counting alone does not capture this feature's cost — which is why FR-28 exists as a distinct requirement rather than a footnote on FR-27.
- The run is synchronous inside a turn that already holds a conversation lock, so a slow run widens the window in which a second turn gets 409 `conversation-busy`. US-410 bounds it; US-305 bounds the sandbox itself.
- `FunctionInvokingChatClient.MaximumIterationsPerRequest = 5` bounds the **outer** assistant's tool loop. The File Agent's own pipeline needs its own bound, configured on its own registration; inheriting the outer number by accident is a defect, not a default.
- The upload/download round trip into and out of the container is the dominant latency for large inputs. Inputs are uploaded once per run, not once per iteration.

**AI system requirements.**

- **Tools the system needs**: Code Interpreter (per-request automatic container), an image-generation deployment, and `gpt-5.6-sol` as the File Agent's model. All three are gated by EP-0 before any code depends on them.
- **The primary evaluation is deterministic and free**: after generating, the agent runs a second sandbox snippet that re-opens the artifact and asserts it parses and matches the requested shape — sheet count for `xlsx`, slide count for `pptx`, page count for `pdf`, non-zero bytes for all. That check is an acceptance criterion (US-404), not a metric, and its outcome is what the artifact-validity success criterion counts.
- **Offline benchmark and pass threshold**: a fixed benchmark of 30 prompts spanning all seven create formats and both the update and compare verbs. Pass threshold before EP-4 is accepted: **≥ 90% produce an artifact that passes verification within the agent's iteration budget**, and **100% of the remainder surface as a failed activity card** — a silent text-only answer counts as a failure of the benchmark regardless of the text's quality.
- **Activity labels are never pre-composed.** `displayName` and `kind` are rendered separately by the client; the agent supplies a name, not a sentence.

#### US-403: Create a document from a prompt

  - Given the run, when the timeline is read, then the agent card carries child activities for the code run, and the resulting document's identity reaches the persisted assistant message through US-205's `attachments[]`.
  - Given a script that raises, when the sandbox returns the traceback, then the agent retries within its iteration budget; when the budget is exhausted, the activity renders failed and no document row is created.

#### US-404: Verify the artifact before returning it

- **Story**: As a chat user, I want the assistant to check that the file it made actually opens and matches what I asked for, so that I do not discover a corrupt document after downloading it.
- **Priority**: P0 · **Estimate**: M · **Depends on**: US-403
- **Status**: Not started
- **Acceptance criteria**:

  - Given verification fails, when the agent reacts, then it retries the generation within its iteration budget; when the budget is exhausted, the activity renders failed, the assistant explains what did not match, and **no document row and no chip are created**.
  - Given verification passes, when the timeline is read, then the verification step appears as its own `depth: 2` child activity, so a reader can see the file was checked.
  - Given the benchmark from §6, when it is run, then ≥ 90% of its 30 prompts pass verification within the iteration budget and 100% of the remainder surface as a failed activity.

#### US-409: Stand down or fail cleanly

Touches `Entity/`, `Repository/`, `DocumentService` and the Cosmos shape, needs no Azure capability, and can therefore start during Wave 0. **Lane B (Image)**: EP-1's US-101, US-102. **Lane C (Code Interpreter)**: EP-3 in full (US-301 … US-305) | ~2 weeks |
| **Wave 2 — the join, plus parallel work** | EP-4's US-401 … US-403 (the critical path — needs all three lanes); EP-1's US-103 … US-105; EP-5's enablers US-501 and US-502; EP-6's US-601 … US-603, which need only Lane A's contract and are testable against a hand-inserted `Generated` row | ~2 weeks |
| **Wave 3 — needs a working agent** | EP-4's remaining verbs (US-404 … US-408) plus US-409 and US-410; EP-5's US-503 … US-505; EP-6's US-604 … US-606. Progress rendering is deliberately last, because activity frames only become real once the agent emits them | ~2.5 weeks |
| **Wave 4 — hardening before switch-on** | US-411 (permission gate), US-412 (flags and rollback), US-207 (retention), US-507 (ceiling), US-506 (admin visibility) | ~1 week |

**The one real collision.** Lanes B and C both add registrations to `Program.cs`, and Lane B's attachment story adds a tool to `CreateChatOptionsAsync` — the single funnel where `chatOptions.Tools` is assigned exactly once at the end. Two lanes editing the same two files is a merge conflict waiting to happen, and worse, two people each adding a tool to that funnel can each believe they own the assignment. The plan takes the cheap resolution: **US-103 (the image tool's attachment) is sequenced after US-301 (the `AIProjectClient` registration)**, so one lane touches `Program.cs`'s registration block first and the funnel gains its first new tool only once. The alternative — refactoring the funnel to compose from a registered tool set up front — is a legitimate choice but is a bottleneck story every lane would wait on, and it is not taken here.

**Critical path.** `US-001 → US-301 → US-302 → US-303 → US-403 → US-404 → US-604`, with `US-401 → US-402` joining ahead of US-403. EP-3 is the longest and riskiest lane, because it is the one sitting on a preview SDK; everything else has slack. Schedule pressure is spent on Lane C, and Lane A is the natural place to put anyone idle in Wave 0 since it needs no Azure capability at all.

**Risks & mitigations.**

| Risk | Mitigation |
| --- | --- |
| The .NET Foundry Agents SDK is in preview: the API can move between the spike and the implementation | EP-0 pins the exact package versions that worked and records them; the whole path is behind `CodeInterpreter:Enabled`, defaulting off (US-412), so a breaking bump is a switch rather than an incident |
| Code Interpreter, `gpt-5.6-sol` or the image model is not provisioned in the target region | This is what Wave 0 exists to find out, before any of Waves 1–4 is estimated in detail. US-002 requires the alternative be reported rather than the work started on an assumption |
| A future change routes Code Interpreter through a toolbox, silently sharing one container across every user in the project | US-302's acceptance criterion is a code search for toolbox creation, and the concurrent-run container-id assertion fails if isolation is ever lost. Stated as a security requirement in §6, not a preference |
| `AIAgent.AsAIFunction()` is used instead of `WithTracking(...)`, or `trackUsage` is set wrongly | Two independent guards: US-402 asserts zero bare `AsAIFunction()` call sites, and US-503's totals test fails on a doubled count. A wrong `trackUsage` is invisible in the UI and visible only in the arithmetic |
| A generated document is chunked by a future refactor and becomes retrievable and citable | US-206's integration test is the guard, and it is written precisely because `DocumentRetrievalSql` needs **no** change for the invariant to hold — nothing in the query would break if chunks appeared, which is what makes the regression silent |
| Sandbox session cost is invisible because token counting looks complete | US-504 measures session time as a first-class metric and FR-28 is a separate requirement from FR-27, so "we track tokens" cannot be mistaken for "we track cost" |
| A synchronous run inside the turn widens the 409 `conversation-busy` window and looks like a hang | US-305 bounds the run, US-410 makes Stop actually stop it, and US-604 renders progress so the wait reads as work. The three together are the mitigation; any one alone is not |
| The PDF path is judged against Word-export typography and declared broken | US-405 makes the fidelity limit an acceptance criterion and puts it in the answer text, so the expectation is set at the point of delivery rather than in a document nobody reads |
| Two lanes edit `Program.cs` and the tool funnel concurrently | Sequenced explicitly above; called out in the build-order file's wave notes as well |
| Generated blobs accumulate faster than uploads and nothing reclaims them | US-207, plus US-505's telemetry making the growth rate visible even before a policy is configured |

**Rollout & rollback.** Three independent flags, all defaulting **off**: the image tool, Code Interpreter, and the File Agent. With all three off, a conversation behaves exactly as it does today, and US-412 asserts that with a regression test. Enablement is staged in that order — image first (it ships standalone and its failure mode is one missing picture), then Code Interpreter, then the agent — so each is observed on its own before the next is added on top. Rollback is a configuration change with no redeploy; the path is exercised at least once before production enablement rather than documented and left untested. The two schema changes ride the ordinary migration path `Database.Migrate()` already runs at startup, and both are additive: the type column defaults every existing row to `Uploaded`, and the `attachments[]` array deserializes as empty on transcripts written before it existed, so rolling the **code** back leaves both stores readable. The permission gate is the last gate before general availability: until US-411 lands, the feature is reachable by anyone in an environment where the flags are on, which is why the flags default off.

## 9. Assumptions & open questions

**Assumptions.** Each is a guess a reviewer can veto.

- The document-type discriminator is `Uploaded = 1` / `Generated = 2`, numbered from 1 rather than 0 so an unset column is distinguishable from a legitimate value — matching `JobStatus`, which starts at 1 for the same reason.
- `CosmosConversationMessage` gains an `attachments[]` array rather than reusing `CosmosConversation.Documents[]`. The rationale is in §6; the veto-able part is that this adds a second place a file identity can live in the transcript. Reusing the conversation-level array would avoid that at the cost of losing message linkage and ordering, and would make generated output look like conversation-scope input.
- The File Agent is an **implicit** tool — attached by the application, not selected by the user — so it stands down with a warning on a non-tool model rather than failing the turn with a 400, matching document retrieval rather than an MCP selection. If the product owner wants an explicit per-turn toggle, US-402 and US-409 both change shape.
- The agent's tool name is supplied explicitly through `WithTracking`'s `functionOptions` rather than derived from the agent's name. Deriving it would work and would be one fewer parameter, but the derived name's leading `{token}_` prefix is exactly what `ResolveMcpServerId` matches on, and a name like `Document_…` collides with the case `CreateChatOptionsAsync`'s existing comment already flags.
- File generation defaults **off** in every environment, including development. A feature billed per sandbox session should be switched on deliberately.
- Generated files are capped by the existing `Documents:MaxFileSizeBytes` (50 MB) rather than a separate ceiling. A generated file is not obviously subject to the same limit as an upload, but two limits for "how big may a file in this system be" is a worse answer than one.
- An update produces a **new** document rather than a new version of the existing row. Versioning would be a better model and is a larger change — it would need a version chain on `ConversationDocument` and a UI for it — and this PRD does not take it.
- The exact package set for the Foundry project client is settled by US-001 rather than asserted here. `Azure.AI.Projects` is stable at 2.x, and the OpenAI extension surface currently appears under more than one package name and prerelease state; naming one now would be a guess dressed as a fact.
- Numeric targets not supplied in the request, proposed here for veto: the ≥ 90% first-attempt verification pass rate, the 30-prompt benchmark size, the p95 ≤ 90 s create latency, the ≥ 99% chip-click download success rate, and the ≥ 90% benchmark threshold in §6. The sandbox run's time, iteration and output-byte bounds in US-305 are `TBD` and must be set from the first real runs rather than guessed now.
- Phase durations in §8 are relative sizing derived from the story estimates, not a commitment, and assume no team size — none was specified and none is invented here.
- US-506 assumes it can extend whatever usage HTTP surface exists when it is scheduled. **There is none today** — `ConversationUsage` has no endpoint, and `docs/prd/enterprise-ui-rebuild.md`'s US-1301 is the unstarted enabler that would create one. If that story never lands, US-506 reports through the telemetry backend alone and this PRD does not create a second usage API beside it.
- The generated-file chip is a variant of the existing attachment chip. `docs/design/` carries no board for it, so its visual treatment is derived from the existing component rather than from a design frame; if a board is added later, it wins on everything except accessibility.
- The deterministic verification pass runs in the same container as the generation, not a fresh one. A fresh container would prove the artifact is readable by something that did not create it, at the cost of a second session; the same-container check is assumed sufficient because the artifact is re-opened from bytes on disk.
- No new RFC 9457 problem type is introduced. Every failure this feature adds is either mid-stream (a failed activity card) or reuses `/problems/provider-not-configured` or `/problems/storage-not-configured`.

**Open questions.**

- **Does v1 need a per-user or per-conversation cost ceiling, or is telemetry-only acceptable at launch?** Code Interpreter bills beyond tokens — each concurrent conversation opens its own session, active up to an hour with a 30-minute idle timeout — so token counting alone understates the cost. US-507 implements whichever answer comes back and is P1 rather than P0 precisely because the answer is not yet given — *product owner, before Wave 4*.
- **Reuse the existing `Upload File` permission, or add a `Generate File` one?** The cost profiles differ sharply: an upload costs storage and one ingestion, a generation costs a model, an agent, an image model and a billed sandbox session. That argues for a separate grant, but a second permission is a second thing to administer and a seeded row that can never be renumbered. US-411 is written to take either — *product owner, before US-411 starts*.
- **Does the `generated` container get a lifecycle policy that `documents` lacks, and what is the window?** Blobs are never reclaimed on soft delete today — the code defers it to a retention job that does not exist — and generated files will accumulate faster than uploads. US-207 needs a number — *product owner and operator, before US-207 starts*.
- **May the File Agent pull any blob in the conversation, or only ones named explicitly in the turn?** "Any" is more useful and makes the agent's reach implicit; "explicit only" is narrower and auditable. The answer goes into the agent's instructions and into US-406's criteria, so it must be settled before that story rather than left to the model — *product owner, before US-406 starts*.
- **Does `gpt-5.6-sol` need reasoning, and if so does the File Agent run through a different registration?** `AzureAIFoundryChatDefaults.Create()` sets `options.Reasoning = null` unconditionally, because reasoning is a Responses-API feature that a Chat Completions deployment rejects outright — so the Foundry path strips it entirely. If the agent needs reasoning it cannot use that registration as it stands. US-002 gathers the evidence; the decision is not this PRD's to make — *backend engineer with the product owner, at the end of US-002*.
- **Which of Code Interpreter, `gpt-5.6-sol` and the image models are actually provisioned in the target region and project?** Everything downstream is estimated on the assumption that all three are. This is the whole purpose of Wave 0 — *operator, in EP-0*.
- **Is deferring `xlsm` acceptable?** Code Interpreter's supported-upload table lists `.xlsx` and not `.xlsm`, so a macro-enabled workbook cannot be uploaded into the sandbox at all — this is a service limitation, not a scoping preference, and there is no cheap workaround. `FileExtensions.Xlsm` exists in the upload enum today, so a user *can* upload one and then be told the agent cannot read it — *product owner, before EP-4 ships*.
- **Should a failed verification retain the failing artifact for diagnosis?** This draft discards it: no row, no blob, no chip. Keeping it would help debug a systematic failure and would also persist a file the platform knows is broken — *backend engineer with the operator, during US-404*.
