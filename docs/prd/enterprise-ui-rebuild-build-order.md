# Build order: Enterprise GPT frontend rebuild

A dependency-resolved execution sequence for the 94 stories in [`enterprise-ui-rebuild.md`](enterprise-ui-rebuild.md), for tracking progress against.

**The PRD is authoritative.** This file adds no requirements and changes no scope. It derives one linear order from §8's phase table plus each story's `Depends on` field, because §7 is grouped by surface and its numbering is not a valid build order — four stories depend on a later-numbered one (US-105→US-109, US-106→US-109, US-307→US-901, US-401→US-405). Where this file and the PRD disagree, the PRD wins and this file is wrong.

Status here mirrors the `Status` field on each PRD story. Update both, or update the PRD and re-derive this.

**Progress: 71 / 94 done.** Current position: **P6 is complete and P7 is under way — US-1402 and US-1401 both landed on 2026-08-17**, giving the streaming answer a polite live region that is `aria-busy` for the length of the turn, and then closing the two keyboard gaps behind it: a scrolling code block that could not be reached without a pointer, and five focus indicators under WCAG's 3:1, one of which was every button in the app. Both claims are now build gates rather than comments. The administration area behind them has a layout route, a rail that marks the open tab from the router, a working user directory (server-paged search, a create modal, a permission-editing offcanvas and a deactivate confirmation), a model catalog (the whole set in one request, filtered in memory, an eleven-field create-and-edit dialog, Set as default, and a retire confirmation whose event also refreshes the chat picker's catalogue), an MCP server registry (the same regime again, a five-field dialog whose Scope is conditional in both directions, and a deactivate confirmation that names the permission cascade) and a **reports tab that is a URL and frame `5i`'s unavailable panel**, because the API behind it does not exist — US-1302 fills it in, in P8, and inherits the route rather than creating one. **P7 continues with US-1403 and US-1404, and US-1405 is now unblocked** — it was the only story waiting on US-1401. Nine things are outstanding against shipped stories: US-706, the sort enabler that retires US-705's stated order (row 89), a backend enabler for the Last active column US-1201 could not build, a backend enabler for restoring a retired model, the same for reactivating a deactivated MCP server, US-1402's two — a screen-reader pass against real assistive technology, and the post-`Finished` delta the fold does not refuse — and US-1401's three: the `outline` scan reading `src/` rather than the built stylesheet, Bootstrap's transient active-state wash, and two tab stops per code block.

Within a phase, stories on the same table row have no ordering constraint between them and can be taken in any order or in parallel. `→` in the notes column means "must follow".

**EP-7 completed 2026-08-14, in the numbered order.** The four stories all edit the same three files, so they are sequential whatever order they take, and each one's shape depends on the one before it: US-704's selection has to survive a Load more, and US-705's "no client-side reordering" is only assertable once a partially loaded list exists. **EP-8 completed 2026-08-14, in the numbered order.** The five stories are one feature — every one of them is a state the same chip can be in — so they were taken as a unit rather than sequenced. Documented in [docs/ui/file-attachments.md](../ui/file-attachments.md). Two decisions in it were not derivable from the criteria and are recorded there in full: **uploads start as early as a conversation id exists** and `TurnStore` gates the stream on `UploadStore.settled$()`, because retrieval attaches `document_search` from what the conversation _already_ holds and a file posted as the stream opens is invisible to the very turn that asked about it; and **the upload POST is raw `XMLHttpRequest`**, because `HttpEventType.UploadProgress` is emitted by `HttpXhrBackend` only and the app runs `provideHttpClient(withFetch())` — so frame `4l`'s transfer percentage is unobtainable through `HttpClient` here. That transport restates the auth interceptor's single forced-refresh replay via `authErrorDecision` and deliberately does **not** restate `retryInterceptor`, which would queue the file twice. Concurrency is capped at three transfers, because the origin's six connections are shared with the SSE stream and the status polls.

⚠ **Two deliberate departures from frame `4l`**, both because the board is wrong about the API rather than because the app disagrees with the design. The board's example copy names XLSX and CSV, which the API does not accept, and omits PPTX, which it does — so the supported set is built from `GET api/documents/file-extensions` and no string is quoted from the board. And the board draws Retry on its **unsupported** chip, which this app does not: re-posting a `.mov` produces the same refusal, the same reasoning `canRetry` in `core/errors` already records. Retry stays on the `failed` arm, where a second attempt can succeed. Neither story's criteria are weakened — US-802 ties Retry to `Failed`, and US-805 asks only that the unsupported chip name the extension and the supported set.

**EP-12's first four completed 2026-08-16, in the numbered order, which was not optional.** US-1202, US-1203 and US-1204 all hang off US-1201 and all three write the same three files — `AdminUsersStore`, `UserActionsStore` and `admin-users.html` — so two worktrees would have collided on every one of them, exactly as EP-7 and EP-9 did. Within that, the create modal came before the edit panel because the shared `PermissionChecklist` is simpler in frame `5b` (an inline caption, no lock) than in frame `5c` (a lock glyph, a block caption and a per-row refusal slot), and settling the smaller variant first is the same reasoning EP-6 used for the code-block chrome.

**The shared kit had been waiting for this epic.** `Paginator` ("the numbered pager of frame `5a`"), `Offcanvas` ("the admin detail drawer of frame `5c`", already defaulting to 420px with a sticky footer and focus return) and `PermissionBadge` ("in the admin user list and detail drawer") were all built by US-106 *against these frames* and had no consumer but `/ui-kit` until now. Between them they needed one page-size select, one `liveSummary` opt-out and nothing else. Two things did have to be built: `AvatarInitials`, whose four-tone ramp lives in the component rather than in `_tokens.scss` because it is the only consumer and that file is global; and the `AdminLayout` rail, which lists only the tabs that exist.

**US-1209 was smaller than it looked, and it closed the phase.** The layout route, the rail marking the active tab from the router, and the `/admin` → `/admin/users` redirect all landed with US-1201, because frame `5a` draws the rail as part of the users screen. US-1207 then added the models route and its rail entry in the same commit, and US-1208 the MCP route and `bi-plug` in the same commit again, on the rule that a tab is added by the story that builds it. What was left was the **fourth** tab — and that is where a deadlock had to be broken: this file and the docs page had both booked it to US-1302, which `Depends on: US-1209`. The rule is unchanged and still binds; US-1209 simply is the story that built the route, and frame `5i` ("Reports — unavailable panel (**current state**)", captioned "Required frame") is the design authority for shipping it that way. `/admin/reports` therefore renders an `<h1>` and the shared `UnavailablePanel`, with **no `ReportsStore` and no request** — a deliberate departure from US-1302's first criterion, which asks for a store holding zero records: with no endpoint it would hold no state and load nothing, and FR-49 is met more strongly by a tab that instantiates none. It is the panel's first production consumer; only `/ui-kit` had rendered it since US-106. Two smaller things outlive the story: the tab carries an `<h1>` frame `5i` does not draw, because `UnavailablePanel`'s own heading is a `<p>` bound through `aria-labelledby` and this would otherwise be the app's only routed screen with no level-one heading (US-1405's axe gate would find it), and **`/admin/<unknown>` now redirects to `/admin/users`** through a `**` child rather than backtracking out of the area to `/chat` — which means **a new admin route has to be added above that entry**, or it is unreachable with nothing to report it.

**US-1207 is the second tab, and it copies almost none of the first.** The two-store seam is the same — a root-scoped `ModelActionsStore` for the requests, a route-scoped `AdminModelsStore` for the rows — but the endpoint decides everything else: `GET api/models/all` is unpaginated, so the screen is **regime C** with no URL contract, no `bindQuery` and a filter that runs in memory, making it `withClientQuery`'s first production consumer (`ProjectListStore` had deferred it to US-902). Its `isAuthoritative` is `isFulfilled() || entities().length > 0` rather than `isFulfilled` alone, because every mutation refetches and the rows on screen are still the whole catalog while the next copy is on the wire. US-1208's tab is the one that copies **this** screen, not `AdminUsers`.

**US-1208 is the third tab, and it copies the second almost exactly.** Same seam (a root-scoped `McpServerActionsStore`, a route-scoped `AdminMcpsStore`), same **regime C** with no URL contract, same two shaped `withClientQuery` values including `isAuthoritative: isFulfilled() || entities().length > 0` — the second consumer of that feature was a copy rather than a re-derivation, which is what §10.2 of the docs page was written down for. It departs in exactly one place, and deliberately: **every rejection kept on the dialog's own surface renders in the modal's `--fail` panel, a validation problem included**, because the criterion asks for a panel that names the server on a 502 as well as on a 400 — a non-validation failure therefore raises no toast, since reporting the same fact twice is the defect. Four things about the API decide the rest: the write DTOs carry **no permission field** (the server creates and renames that permission itself), `McpAuthTypes` has **two** members where frame `5h` draws three and they travel as **numbers**, `Scope` is conditional in **both** directions, and `DELETE` cascades to the linked permission and every grant of it. `adminEvents.mcpCatalogChanged` is `type<void>()` and both observers refetch, mirroring `modelCatalogChanged`. **The criterion's 502 is unreachable on save** — `POST`/`PUT api/mcps` attempt no MCP connection — and the panel is built to render any error anyway.

**No re-baseline.** The initial bundle measures **669.78 kB raw / 168.95 kB transfer** against 670 kB warn / 720 kB error, `styles` unchanged at 63.96 kB and the lazy `admin-routes` chunk grown 70.23 → **95.94 kB** — **0.22 kB of headroom left**. It got there in three paying steps and then stopped: **+0.27 kB** for US-1201–1204 (the shared kit's), **+0.46 kB** for US-1207 (all of it `ModelCatalogStore`'s `modelCatalogChanged` handler, since that store is root-scoped and genuinely initial), **+0.15 kB** for US-1208 (`McpCatalogStore`'s handler, a third the price because `withEventHandlers` and the `adminEvents` symbol were already on the graph) and **+0.00 kB** for US-1209, whose whole tab — 1.10 kB of it — landed in the lazy chunk, because it introduces no event, no root-scoped store and no dependency. Everything else rides that chunk too, including all three root-scoped action stores: `providedIn: 'root'` is a DI scope, not a chunk assignment, and nothing eagerly reachable imports any of them. `check-initial-chunk.mjs` still reports the admin area absent from the initial graph. **One note for US-1302**, which is the next story to touch this chunk: `admin.routes.ts` names every tab with a static `component:` import, so a charting library imported by the reports screen would be downloaded by everyone who opens `/admin/users` — switching that one route to `loadComponent` is the cheap fix, and it is cheap at that point rather than now.

**US-1402 opened the phase, and it was smaller in code than in reasoning.** Its first and third criteria look contradictory — a polite live region over streaming text reads every delta — and are reconciled by ARIA's batching rule rather than by a throttle: the streaming answer's `.assistant-turn__content` is `aria-live="polite"` **and carries its own `aria-busy`**, released as an explicit `false` when the folded `Finished` lands, so the region accumulates and is exposed once. The settled turn that replaces it carries no `aria-live` at all — the guard is at the call site in `transcript.html`, which is why `transcript.spec.ts` pins it and the component's own spec cannot. The transcript's `aria-busy` moved to `historyPending() || (inFlight() && !answerComplete())`, one step ahead of `!inFlight()`, because criterion 4 names the **frame** and reading the frame is what leaves the live turn mounted while its region is released. Two things that look like extras are the load-bearing parts: the activity cards and the reasoning region are `aria-live="off"`, or releasing the answer would flush every card's state, kind, source and sub-status list at the reader first — and a second time, since the status region already narrated them live; and that status region is rendered by `Chat` **outside** the `aria-busy` container, because anything inside it is deferred with the answer. It speaks the new pure `domain/stream/turn-announcement.ts`, which meets criterion 3 by construction — every branch changes only on a status transition, the one branch reading `snapshot.text` reads it as a boolean, and the recorded twelve-event turn reduces to seven distinct strings with none repeated. Two interim behaviours came out of it and are in the table below. Criterion 2 needed no work: US-106's two toast regions already covered it. **No re-baseline** — the initial bundle is unchanged at **669.78 kB raw / 168.97 kB transfer** against 670 / 720 kB, `styles` unchanged at 63.96 kB, everything on the lazy `chat` chunk.

**US-1401 was a conformance story, not a build one, and its two gaps were the only code it had to write.** `shared/a11y/`, the native `<dialog>` overlays with focus return, the roving-focus `Menu` and the absence of a single clickable `<i>` or `<div>` meant three of the four criteria were largely already met; what they lacked was anything that would notice them breaking. **Gap one** was a code block that could not be scrolled without a pointer — `overflow: auto` with no `tabindex` (SC 2.1.1) — closed by emitting `tabindex="0"` from `renderer.code`, admitting `tabindex` to the sanitizer profile, and leaving the block **deliberately unnamed**, because `<pre>` maps to `role="generic"` whose name ARIA prohibits, and naming it properly costs a role and a wider profile to announce a scroll box. **Gap two** was five focus indicators under 3:1, one of which was every button in the app: `--ring` is `ringpulse`'s 45%-alpha colour and composites to about 1.4:1, and it was drawing the indicator on three composer controls, the empty-state chips and the composer card, beside two form-field rules using an 18%-alpha wash. A global `:focus-visible` floor in the new `_focus.scss` fixes the elements with no rule at all — and **explicitly not the three Bootstrap components**, which declare `outline: 0` on a class and out-specify a bare `:focus-visible` whatever the source order; the first cut of the work missed that and reached none of them. They are overridden by name, the checkbox with two rules whose order is load-bearing, and the ring is an `outline` with an offset rather than a flush shadow, because drawn on `--btnP-bg` it measures **1.00:1** in dark, where the button fill *is* the focus token. Both claims are now gates inside `npm run lint`: `check:tokens` measures **38** contrast pairs (up from 26) and refuses to fall behind the stylesheets in either direction, following variable indirection because that is how every Bootstrap fill is set; `check:forbidden` refuses a suppressed indicator and `var(--ring)` outside its keyframe, with a per-line hatch **scoped to those two rules** after a review round found an earlier cut applying it to all seven. One shared helper changed with it — `dialog-polyfill.ts` now queues its `close` event as the platform does, which is what makes `Modal`'s destroy-time focus restore falsifiable. Three limits came out of it and are in the table below. **No re-baseline, and 0.07 kB of headroom left**: the initial bundle measures **669.93 kB raw / 168.91 kB transfer** against 670 / 720 kB and `styles` **64.17 kB** against 65 / 80 kB, the +0.15 kB entirely global CSS — dropping Bootstrap's unused `helpers/focus-ring` import paid back most of the override's cost. **US-1405 owns budgets and is where that line should be re-stated**; this story did not move it.

The `--warn` contrast question in §9 is **still open** and now blocks only US-1405's axe gate: light `#A96A10` measures 4.41:1 on white, 4.21:1 on `--bs-body-bg` and 3.99:1 on `--warn-bg`, all under 4.5:1. `check:tokens` blocks a local override by design, so it must be resolved upstream in `docs/design/project/theme.css` rather than worked around here.
