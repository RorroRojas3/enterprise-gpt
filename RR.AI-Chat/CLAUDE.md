## Code Design Rules

- Don't add interfaces/abstractions unless used for external dependencies or testing. **Note:** the existing service layer uniformly exposes `I<Service>` interfaces — keep that pattern.
- Don't wrap existing abstractions.
- Default to least exposure: `private` > `internal` > `protected` > `public`.
- Don't edit auto-generated code (`*.g.cs`, `// <auto-generated>`, EF migrations once applied).
- Comments explain **why**, not what. XML doc comments on public methods (existing services already do this — see `csharp-docs` skill).
- Reuse existing methods. Don't add unused params or methods.
- When fixing one method, check siblings for the same issue.

## Naming & Formatting

- **PascalCase:** types, methods, public members, properties.
- **camelCase:** locals, parameters.
- **`_camelCase`:** private readonly fields. **The codebase pattern** is to take primary-constructor parameters and assign them to `_underscore`-prefixed `private readonly` fields:
  ```csharp
  public class FooController(IFooService fooService) : ControllerBase
  {
      private readonly IFooService _fooService = fooService;
      // use _fooService throughout
  }
  ```
  Match this. Don't reference primary-constructor parameters bare in member bodies.
- **Interfaces** prefixed with `I` (`IUserService`).
- **Brace-style namespaces** are the consistent project pattern (every `.cs` file uses `namespace Foo { ... }`). The C# convention prefers file-scoped, but **stay brace-style for consistency** until a project-wide migration.
- Single-line `using` directives. Opening brace on a new line for blocks (per `.editorconfig`).
- Pattern matching and switch expressions where they read better than `if/else`.
- Use `nameof(...)` instead of string literals for member references.

## Nullable Reference Types

- Treat C# null annotations as authoritative — don't add null checks where the type system says a value can't be null.
- Use `is null` / `is not null`, never `== null` / `!= null`.
- At public API boundaries, use `ArgumentNullException.ThrowIfNull(x)` and `string.IsNullOrWhiteSpace(x)`. Avoid blanket `!`.

## Async Programming

- Every async method ends with `Async` (codebase is 100% on this).
- Return `Task<T>` / `Task` — never `void` (except event handlers); `ValueTask<T>` only when measured to help.
- **Always await.** No fire-and-forget. If you need to abandon work, **cancel** it.
- **`CancellationToken` end-to-end** — every async signature accepts `CancellationToken cancellationToken` and propagates it to:
  - EF Core: `ToListAsync(cancellationToken)`, `FirstOrDefaultAsync(cancellationToken)`, `SaveChangesAsync(cancellationToken)`
  - HTTP: `HttpClient.SendAsync(req, cancellationToken)`
  - Delays: `Task.Delay(ms, cancellationToken)`
  - Loops: `cancellationToken.ThrowIfCancellationRequested()` periodically
  - Service interface methods may default `cancellationToken = default` (existing pattern).
- **Timeouts:** linked `CancellationTokenSource` + `CancelAfter`, or `Task.WhenAny` plus cancelling the loser.
- **`ConfigureAwait(false)`** in helper/library code; omit at the API entry layer.
- **Stream JSON for large payloads:** `GetAsync(..., HttpCompletionOption.ResponseHeadersRead)` → `ReadAsStreamAsync` → `JsonDocument.ParseAsync`. Avoid `ReadAsStringAsync`.
- **Async dispose:** `await using` for async resources.
- **Never** call `.Wait()`, `.Result`, or `.GetAwaiter().GetResult()`.
- **No pointless wrappers:** if the body is `return SomeAsync(...);`, drop the `async/await`.

> For deeper async patterns, invoke the `csharp-async` skill.

## Error Handling

- Choose precise exception types: `ArgumentException`, `ArgumentNullException`, `InvalidOperationException`, `OperationCanceledException`, custom `NotFoundException`. **Don't** throw or catch base `Exception`.
- **No silent catches.** Log and rethrow, or let the exception bubble.
- **Wire shape is sacred.** The frontend reads [`ErrorDto`](RR.AI-Chat.Dto/ErrorDto.cs) — `{ statusCode, errors[], traceId, timestamp }` (camelCase via `[JsonPropertyName]`). Don't change the JSON contract.
- **Service layer should throw.** Don't catch-and-translate at the controller.
- `ValidationException` (FluentValidation) → 400 with rule messages in `errors[]`.
- `OperationCanceledException` → 499 (client cancelled).

### Target pattern: `IExceptionHandler` (ASP.NET Core 10)

New error-handling logic should be implemented as `class FooExceptionHandler : IExceptionHandler`, registered via `builder.Services.AddExceptionHandler<FooExceptionHandler>()`, and activated with `app.UseExceptionHandler()` in `Program.cs`. Multiple handlers chain in order; each returns `true` to claim the exception. Each handler still produces the same `ErrorDto` JSON shape.

> **.NET 10 behavior change** — when `TryHandleAsync` returns `true`, **exception diagnostics are suppressed by default** (previously always emitted). To preserve always-on diagnostics for handled exceptions, set `SuppressDiagnosticsCallback = ctx => false` in `app.UseExceptionHandler(new ExceptionHandlerOptions { … })`. Decide and document this choice in `Program.cs`.

## Validation

- **FluentValidation 12.x**, auto-registered via `AddValidatorsFromAssemblies(AppDomain.CurrentDomain.GetAssemblies())` in `Program.cs`.
- For each request DTO, write an `AbstractValidator<TDto>` colocated in the same `*Actions.cs` file (existing pattern in [`ConversationActions.cs`](RR.AI-Chat.Dto/Actions/Chat/ConversationActions.cs)).
- Inject `IValidator<TDto>` into services and call `await validator.ValidateAndThrowAsync(dto, cancellationToken)`. The thrown `ValidationException` is mapped to a 400 by error-handling middleware.
- Use `ChildRules` and `RuleForEach` for nested collections.
- FluentValidation works fine against records — convert DTOs to records as you touch them (see Migration Debt below).

## API Endpoints (Controllers)

- **Controller-based MVC, not Minimal APIs.** All controllers:
  ```csharp
  [Authorize]
  [ApiController]
  [Route("api/[controller]")]
  public class FooController(IFooService fooService) : ControllerBase
  {
      private readonly IFooService _fooService = fooService;

      [HttpGet("{id}")]
      public async Task<IActionResult> GetFooAsync(Guid id, CancellationToken cancellationToken)
      {
          var response = await _fooService.GetFooAsync(id, cancellationToken);
          return Ok(response);
      }
  }
  ```
- Each action is `async Task<IActionResult>` (or `async Task` for streaming SSE), takes `CancellationToken cancellationToken`, and returns `Ok(...)` / `NotFound()` / `BadRequest(...)` / `NoContent()`.
- For SSE streaming, set `Response.Headers.Append("Content-Type", "text/event-stream")` and write to `Response.Body` — see `ConversationsController.StreamConversationAsync`.

- **Async, cancellation-aware queries always** — `ToListAsync(cancellationToken)`, `SaveChangesAsync(cancellationToken)`, etc.

## Do / Don't Quick Reference

**Do**
- Use primary constructors with `_underscore` private readonly field assignment
- Register services with `I<Service>` interface, depend via primary-constructor params
- Pass `CancellationToken` through every async layer
- Throw precise exceptions; let the error-handling layer translate them
- Validate request DTOs with FluentValidation (`AbstractValidator<T>`, `ValidateAndThrowAsync`)
- Use keyed DI for multi-provider AI clients (`[FromKeyedServices("azureaifoundry")]`)
- Use `Async` suffix on every async method
- Use `is null` / `is not null` (never `== null`)
- Use `nameof(...)` over string literals for member references
- Write new DTOs as `record` types
- Write new error mappings as `IExceptionHandler` implementations

**Don't**
- Don't introduce a separate repository layer — services use `AIChatDbContext` directly
- Don't add Minimal APIs alongside controllers
- Don't catch base `Exception`; don't swallow exceptions silently
- Don't call `.Wait()` / `.Result` / `.GetAwaiter().GetResult()`
- Don't return `void` from async (except event handlers)
- Don't add new mutable class DTOs — new DTOs are records
- Don't extend the legacy `ExceptionHandlerMiddleware` — write `IExceptionHandler` for new error mappings
- Don't change the `ErrorDto` wire shape — frontend depends on `{ statusCode, errors[], traceId, timestamp }`
- Don't add data annotations to entities — fluent `IEntityTypeConfiguration<T>` only
- Don't edit EF migrations once they're in source control — add a new one
- Don't add Serilog / App Insights / Key Vault without explicit ask
- Don't change `<TargetFramework>`, `<Nullable>`, `<ImplicitUsings>`, or add `<LangVersion>`
- Don't reference primary-constructor parameters bare in member bodies — assign to `_underscore` fields

> **`appsettings.Development.json`** does not exist; **no test projects** exist; **no health-check endpoints** exist. Add these only when explicitly asked.
