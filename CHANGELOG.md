## [Unreleased]

### Added

- **A conversation can now be taken out of the platform as a Markdown, Word, or PDF file** (US-1501, US-1502). Export used to mean HTML or JSON only, and neither was offered anywhere in the client — the only way to get a transcript out was to view the HTML export and copy from it by hand. The export route now renders five formats behind one `?format=` parameter; `md` and the existing `html`/`json` read what the transcript already stores, while `.docx` and `.pdf` walk each message's markdown once into a shared, renderer-neutral block model, so Word and PDF can never disagree about what a message meant, and both inherit the same link-scheme allowlist that already guards the stored transcript — a `javascript:` link is exactly as dead in an exported Word document as it is on screen. **A Download control now appears in the composer and in the conversation header** — one shared menu behind both, offering Markdown, Word and PDF with their own file glyphs; choosing one shows that item preparing while the other two dim, and the menu stays open until the browser actually starts the download, so a failure leaves the menu open beside the error toast rather than closing on it. The control is **absent** on a conversation with nothing to export yet and **disabled with a reason** while a turn is streaming. Three decisions are worth knowing about if you build against this. **PDF export depends on a font this deployment may not have** — PDFsharp/MigraDoc (MIT, unlike QuestPDF's revenue-gated Community tier) embeds no glyphs of its own, so a container with no fonts installed serves PDF as a typed `503 export-renderer-not-configured` rather than a broken file, and any format can be withdrawn the same way through `Export:DisabledFormats`. **Images are dropped from Word and PDF exports, keeping only their alt text** — embedding one would mean the API fetching a URL that model output chose, from its own network position, which a transcript export has no reason to risk. **The export response is bytes, not a signed URL** — rendering to blob storage first would have made every export, markdown included, depend on storage being configured and left rendered transcripts behind to clean up; the client requests `blob` directly, opts out of the retry interceptor (an unclassifiable blob error body would otherwise see an application-typed 503 retried as if it were a gateway hiccup), and releases the object URL ten seconds after handing it to the browser rather than immediately, which would cancel the download it was just given. Backend: **1274 unit and 284 integration tests** pass (up from 1152/250); the generated `.docx` is checked with `OpenXmlValidator`, which caught four schema ordering bugs a round-trip read had missed. Frontend: **1830 tests** (up from 1788) and **38 browser accessibility audits** (up from 36, auditing the new menu open in both themes); the initial bundle grows **0.91 kB to 671.59 kB raw / 168.92 kB transfer**, inside the unchanged 675/720 kB budget. `html` and `json` remain on the route, unfiltered, for scripted callers — the client offers only the three formats the design draws. See [docs/conversations/conversation-export.md](docs/conversations/conversation-export.md) and [docs/ui/conversation-download.md](docs/ui/conversation-download.md).

- **Every file you have uploaded is now findable on one screen** (US-1001–US-1003). Finding a document used to mean remembering which conversation it went into: the platform could download a document by id but could not list what a conversation held, let alone everything a user holds. The API gained two listings — one for a conversation's documents, mirroring the project-documents route (an empty conversation answers an empty list, and a conversation that is deleted or someone else's answers 404, indistinguishable from one that never existed), and a paginated cross-conversation listing scoped to the caller, each row carrying the owning conversation's id **and name** so the new screen never issues one request per conversation. `/documents` — a new sidebar entry — lists them newest first with a file-type glyph, size, date, an `Uploaded` badge and a link to the conversation each file came from; downloads follow the existing click-only signed-link rules, so a link is minted only for a file you actually ask for. You can **filter by name** — the term lives in the URL, so a filtered view is shareable and the back button undoes it — and the list is **grouped by conversation by default**, under collapsible headers that link into the chat, with a flat view behind a toggle; only the deviation (`?view=flat`) is ever written to the URL, because grouped is the default the design draws. The counts stay honest at every edge: the screen loads at most the 500 most recent documents and says so when it stops there, the toolbar count reads the server's total rather than the rows loaded, and a filter that matches nothing names the term and offers Clear filter — distinct from "Nothing uploaded yet", which wins whenever there is genuinely nothing a cleared filter would reveal. Three limits are recorded rather than hidden: every row's badge reads `Uploaded` until the assistant-generated-document concept exists (US-1004 makes it data-driven; US-1005 then ships the filter), the filter covers file names only and says so on screen, and there is no way to detach a document from its conversation, because no such API exists. The initial download grows 0.75 kB to 670.68 kB raw / 169.07 kB transfer, inside the 675/720 kB budget — the screen rides its own lazy chunk. The UI has not been exercised against a live API; the two endpoints are covered by the integration suite against real SQL Server 2025. See [docs/ui/documents-library.md](docs/ui/documents-library.md).
- **The audit trail now records each model turn of a call, so what a tool adds to the *next* prompt is finally answerable.** A chat turn is not one model call: the model answers, asks for tools, the tools run, and the model is called again with their results appended to the prompt. Until now the whole loop landed as one row, which made a tool's real cost invisible — an MCP tool spends almost nothing itself, and what it actually costs is that its arguments and its result are billed inside the *next* turn's prompt, folded into an aggregate no provider itemizes. A new `Core.ConversationUsageTurn` table records every iteration as the provider reported it, and every tool-call row now names the iteration that issued it, so the growth between one turn and the next can be attributed to the calls that caused it — `input(N+1) − input(N) − output(N)`, written out as SQL in the reference. Two rules govern reading it, and both are the kind that silently corrupt a report if missed: **turn rows break the call's totals down, they never add to them** (summing them into the parent double-counts every call), and **a nested tool call carries the iteration of the outermost call it belongs to**, so any grouping has to be restricted to top-level calls or a sub-agent's whole tree is counted once per level it is deep. The figure is deliberately **not stored as a column**: it belongs to a *group* of calls rather than to one, and when a single turn issues three tools the number covers all three and cannot honestly be split — splitting it would need each tool's result, which this platform deliberately never records. It is also **null rather than zero** in three situations — a call's last turn has nothing after it to measure against, a call that did not stream has no breakdown at all, and rows written before this release cannot say which turn issued them. Usage rows and turn rows also gained cached-input and reasoning-token counts, both **already inside** the input and output totals rather than added to them; those two are wired end to end and **arrive empty today**, because the middleware's own arithmetic drops them in transit (recorded as a known limit rather than hidden). Schema arrives through migration `AddPerTurnUsageAndTokenDetails` — one new table and three nullable columns, no backfill, and reversible. See [docs/conversations/usage-and-favorites.md §3.9, §6.4 and §7](docs/conversations/usage-and-favorites.md#39-turn-rows-partition-the-assistant-columns-they-never-add-to-them).
- **A screen-reader user is no longer left in silence while an answer is being written** (US-1402). Sending a prompt used to produce nothing audible until the reply happened to be re-read: the transcript was marked as settling for the length of a turn, which stopped it chattering but also stopped it saying anything. A turn now narrates itself — "Starting the conversation", "Waiting for a response", "Get forecast is running", "Search Documents failed", "Writing the answer" — **one short line per step of the turn, never one per word**, and the finished answer is then read out once, whole. The two halves of that are in tension, and the tension is the design: the streaming answer *is* a live region, as the accessibility criteria require, but it is marked busy for as long as it is growing, which is the accessibility standard's own instruction to accumulate changes and speak them once when the work finishes. Nothing counts words, samples on a timer or throttles anything, so the behaviour does not change with how fast a model writes. **Nothing is announced twice, and that took more care than announcing it at all.** The settled copy of the answer that replaces the live one is silent, so a reply is spoken once rather than once as it arrives and again when it is saved; and the activity cards and the reasoning summary sitting inside the answer are excluded from it, because releasing the answer would otherwise recite every card's status, kind, source and sub-step list first — after the running commentary had already said each of those as it happened. Both stay **fully readable by browsing the transcript**; they are excluded from being spoken at you, not hidden. **A failure is never lost**: a failed step is added to whatever else is being said rather than ranked against it, since putting it first freezes the commentary on it for the rest of the turn and putting it last lets the next step bury it — so "Writing the answer. 1 step failed" is a sentence the reader will actually hear. Toasts already met their criterion, through the two announcement regions the shared UI kit has mounted since it was built. **Two limits are recorded rather than hidden.** Handing a held-back answer to the reader is a change of state with no new text behind it, so it depends on the screen reader replaying what it buffered — that is what the standard asks for and it is also the least reliably implemented corner of it, which is why a short "Answer ready" is spoken as a backstop alongside it; **this release has not been exercised against NVDA, JAWS or VoiceOver**, and that manual pass is tracked as outstanding. And a server that sent further answer text *after* the completion signal — which the streaming contract does not envisage, since that signal arrives only when the turn ran to completion — would have that text announced on its own; the alternative was to discard it, and losing answer text to protect an announcement is the worse failure. The initial download is **unchanged at 669.78 kB raw / 168.97 kB transfer**, inside the 670/720 kB budget, with all of it on the chat screen's lazy chunk. See [docs/ui/answer-rendering.md §10](docs/ui/answer-rendering.md#10-following-a-streaming-answer-with-a-screen-reader-us-1402).
- **Every administration tab now has its own address, including Reports** (US-1209). `/admin/users`, `/admin/models`, `/admin/mcps` and `/admin/reports` can each be opened, bookmarked and sent to a colleague; the tab that opens is marked in the rail as the current page — for a screen reader as well as visually — and the browser's back button moves between tabs, because the tabs are real routes rather than a remembered name. Most of that shipped with the earlier admin stories; what is new is the **fourth tab and two smaller behaviours around it**. **Reports exists as a page rather than as a dashboard.** There is no reporting API yet, so the tab says exactly that — "Usage reports aren't available yet", with a line explaining that the reporting API is not enabled for this deployment and that **token usage is still being recorded** in the meantime, which is true and is the part worth knowing: nothing is being lost while the screen waits. It shows no sample chart, no placeholder totals and no rows of any kind, and it asks the server for nothing, because a screen filled with invented figures is indistinguishable from a quiet month and a failed request would report "this is broken" where the truth is "this was not built yet". There is deliberately nothing to press: a missing capability does not come back because somebody pressed Retry. The usage dashboard itself arrives with the reporting API (US-1301/US-1302) and will replace the panel in place — the URL, the rail entry and the page title all stay. **A mistyped admin URL no longer throws you out of the admin area.** `/admin/anything-else` now lands on the user directory instead of bouncing to the chat screen, which is what a renamed or half-remembered tab URL used to do to every bookmark at once. The initial download is **unchanged at 669.78 kB raw / 168.95 kB transfer**, inside the 670/720 kB budget — the whole tab rides the admin-only lazy chunk, which a user without the Administrator permission never downloads. None of this has been exercised against a live API. See [docs/ui/administration.md §3.4](docs/ui/administration.md#34-the-reports-tab-the-url-exists-the-dashboard-does-not-us-1209).
- **Administrators can now register and maintain MCP tool servers from the app** (US-1208) — the third admin tab, and the first way to add or change a tool server without writing SQL. `/admin/mcps` lists every server the deployment knows about with its description, its URL in monospace, how the API authenticates to it, the delegated scope it asks for, the permission that gates it and whether it is active; one search field filters on the name, the description **and** the URL, because an administrator as often knows a server's host as its name. The whole registry arrives in one request, so that filter is exact rather than a filter over one page pretending to be the whole list — and for the same reason there is no pager and no sort control (the design draws none; the ordering work is wired but not offered). **Add server** and **Edit** open the same dialog; **Deactivate** confirms first. Six behaviours are deliberate and worth knowing. **There is no "Linked permission" field**, although the design draws one: the API creates that permission itself, names it after the server and renames it whenever the server is renamed, so there is nothing for such a control to set — a note under the Name field says so, which is also the only thing that makes "a server with this name already exists" comprehensible when you never created a permission by hand. **There are two authentication types, not three**: the product supports none and Entra ID on-behalf-of; the design's "Header key" and "OAuth2" do not exist in this system. **Scope appears only for an Entra ID server**, and is cleared when you switch away from it, because the API requires one there and refuses one otherwise — what the dialog shows is what the save will store, with no value retained behind a hidden field. **Deactivating a server does not remove its row** — it is a soft delete, so the server stays in this table greyed out and marked Inactive, and disappears from every user's tool picker immediately; there is no way to bring it back from here, and the confirmation says so. **That confirmation also says what nothing else in this product does**: deactivating a server deactivates the permission named after it *and revokes that permission from everyone who held it*, in one step — no other delete in the application changes somebody else's access, so it is stated as a warning rather than as an aside. And **a failed save is explained on the dialog itself**, in a panel naming the server that failed and, where the API says so, which field it rejected — with every value you typed still in its field, because the form has five of them and nothing here is retried automatically. Two limits are recorded rather than hidden: a server can carry **one** scope, because the API stores one, and there is no way to test-connect a server, list the tools it exposes or see whether it is healthy — all three need API surface that does not exist yet (see [docs/prd/mcp/mcp-server-integration.md](docs/prd/mcp/mcp-server-integration.md)). The initial download grows **0.15 kB to 669.78 kB raw / 168.94 kB transfer**, inside the unchanged 670/720 kB budget, with the whole screen on the admin-only lazy chunk. None of this has been exercised against a live API. See [docs/ui/administration.md §11](docs/ui/administration.md#11-the-mcp-server-registry-us-1208).
- **Administrators can now manage the model catalog from the app** (US-1207) — the second admin tab, and the first way to add, edit or retire a model without writing SQL. `/admin/models` lists every model the deployment knows about with its provider, its deployment name, how much context it holds, how many tokens it can produce and whether it can call tools, and one search field filters on the provider **and** the model name at once. The whole catalog arrives in a single request, so that filter is exact rather than a filter over one page pretending to be the whole list — and for the same reason there is no pager and no sort control (the design draws none; the ordering work is wired but not offered). **Add model** and **Edit** open the same dialog, **Set as default** promotes a model from its row menu, and **Delete** confirms first. Five behaviours are deliberate and worth knowing. **The form asks for eleven things where the design draws eight**: the three extras are "reasoning enabled" and the two prices per million tokens, and they are there because saving a model replaces it wholesale — an edit that left a price out would silently erase it, and this screen is the only place in the product that can set one. **A blank price means unpriced and a zero means free**, which are genuinely different: usage reports show the first as unknown rather than as nothing spent. **Deleting a model does not remove its row** — it is a soft delete, so the model stays in this table greyed out and marked Retired, disappears from every user's model picker immediately, and stays on the conversations that already used it; there is no way to bring it back from here, and the confirmation says so. If the model being deleted is the default, the confirmation also warns that the deployment is left with **no default at all** until you set another, because that is exactly what the server does. And **the chat model picker updates itself**: any change here refreshes the catalog every user's composer reads, so a retired model cannot go on being offered for the rest of somebody's session. Two smaller things: "Must be a whole number of tokens." is enforced by the app rather than by the API, so a model created outside this screen can still hold a fractional context size, and it will be shown as one; and the provider list gained **Azure AI Foundry**, which the client had been missing since that provider was added. The initial download grows **0.46 kB to 669.63 kB raw / 168.80 kB transfer**, inside the unchanged 670/720 kB budget, with the whole screen on the admin-only lazy chunk. None of this has been exercised against a live API. See [docs/ui/administration.md §10](docs/ui/administration.md#10-the-model-catalog-us-1207), and [docs/models/model-management.md](docs/models/model-management.md) for the API underneath it.
- **Pull requests are now tested by CI on both sides of the repository, and the checks can actually be required.** The .NET solution had no workflow at all; it now has one — `Detect API changes`, then **1152 unit tests** with no Docker and **250 integration tests** against real SQL Server 2025 and Cosmos DB emulator containers, as two independent jobs so a compile error is reported without waiting on a 1.5 GB image pull. The existing UI workflow was rewritten to the same shape (`Detect UI changes`, then the lint/test/build gate and the contract-drift check), and both now upload their test reports as artifacts. **The change that matters is what came out: both workflows dropped their `paths:` filters.** GitHub never reports a check for a workflow a path filter skipped — it stays Pending forever, so such a check can never be marked required without making every unrelated pull request unmergeable. That was an open question against turning branch protection on, and this closes it: the filter moved into a cheap `changes` job, because a job skipped by a *conditional* reports Success. Those conditions are written **fail-open** (`!= 'false'`, never `== 'true'`), since a job whose dependency failed is skipped — and a skipped job reporting Success would otherwise hand out a green required check over code nobody tested. **For whoever configures branch protection: list all three check names per workflow**, the `Detect …` job included. Requiring only the gates leaves a window where a filter job that dies after writing `false` lets its dependents skip straight to Success. Two limits are recorded rather than hidden: the integration test fixtures still name mutable `-latest` image tags, so an upstream push can turn `master` red with no change here, and Dependabot still tracks only the `github-actions` ecosystem — `nuget` and `npm` were deliberately left out. See [docs/ci/pull-request-checks.md](docs/ci/pull-request-checks.md).
- **The administration area is real: administrators can now find, add, edit and deactivate users** (US-1201–US-1204). `/admin` had shown a placeholder since sign-in landed; it now opens on a nav rail — Users for now, with the model and MCP tabs to follow — and a **user directory** that searches the server rather than the page: one field matches first name, last name **and** email, so an email fragment finds the person and no second control is needed. Results are paged with a numbered pager and a 25/50/100 selector, and the search term, the page and the page size all live in the address bar, so a filtered view is shareable as a link, the back button restores the page you came from, and opening such a link issues **one** request rather than a default one followed by the real one. Each row shows an initials avatar, the name, the email and one badge per permission the user holds — including grants that come from an MCP server, named after the server they belong to. **Add user** collects a work email and a permission checklist and nothing else: there is no name, role, status or password field anywhere, because the display name and the account id come from your directory and every credential is Entra's; nothing is pre-checked, and a note explains that the deployment's default permissions are granted on top of whatever you tick. **Edit** opens a drawer over the row, and states before you save it that **saving replaces the user's entire permission set** — unchecking a permission revokes it — because that is what the API does and a grant lost by omission is otherwise invisible. **Deactivate** confirms first, naming the person, then removes the row immediately and puts it back in the same position if the server refuses. Five behaviours are deliberate and worth knowing. **There is no "Last active" column**, and the edit drawer is one clause shorter than the design for the same reason: nothing in the API records when a user last signed in, and filling the column with the row's last-edited date would have been a plausible-looking wrong answer for exactly the accounts an administrator is looking for. **The two things you cannot do to your own account are explained where you tried them**, never as a toast in the corner — clearing your own Administrator permission puts "You can't remove your own Administrator permission — another administrator must make this change." beside that checkbox, and deactivating yourself puts "You can't deactivate your own account." under your own name; neither control is greyed out beforehand, so the refusal is the server's and your row is simply marked "(you)". **Permissions that come from an MCP server can be granted and revoked here**, marked with a lock that says the permission's _definition_ belongs to that server — disabling them would have left no way to give anyone MCP tool access at all. **The deactivate confirmation says what deactivation does not do:** an unexpired session keeps working until its token runs out, so cutting access off immediately still means disabling the account in Entra ID as well. And an address the directory does not know is reported **at the email field** rather than as a generic failure, because a create form asks for two things and a toast leaves you guessing which one was wrong. There is deliberately no sort control (no endpoint here accepts a sort parameter, so the order is stated instead), no row-selection column (nothing acts on more than one user), and no permission filter yet (US-1206, which needs a server-side enabler first). The whole area rides its own lazy chunk, which a user without the Administrator permission never downloads: the initial bundle moves **0.27 kB to 669.17 kB raw / 168.97 kB transfer**, inside the unchanged 670/720 kB budget. None of this has been exercised against a live API. See [docs/ui/administration.md](docs/ui/administration.md), and [docs/users/user-management.md](docs/users/user-management.md) for the API underneath it.
- **Move a conversation into or out of a project, from wherever you can see it.** Projects could group conversations from the moment they were created — a conversation started on a project's screen belonged to it — but there was no way to change that afterwards, so a chat begun in the wrong place stayed there. A searchable project picker is now on the conversation's row in the sidebar, on the conversation header's menu, on every row of the conversations library, and on the prompt box itself as a folder pill that names the project the open conversation is in. From it you can move a conversation into a project, straight from one project to another, or out of every project, and **create a new project and move the conversation into it in one step**. The conversations library gained a project chip and a per-row menu carrying the same five actions the sidebar has, so nothing has to be done in two places. Two behaviours are deliberate and worth knowing: **"Remove from project" is simply not shown** for a conversation that is not in one, rather than being shown greyed out; and the picker loads up to **500 projects** and says so when it stops there, so a list that is not the whole list never looks like one. Moving a conversation between projects changes which standing instructions and which shared documents its next turn sees — the project's instructions are read fresh on every turn, so the change takes effect immediately, and nothing already in the transcript is rewritten. See [docs/ui/projects.md](docs/ui/projects.md) and [docs/ui/conversation-actions.md](docs/ui/conversation-actions.md).
- **A project's conversations are now listed on the project.** The project screen had tabs for its instructions and its files and nothing that answered "what has been discussed here", so the only route to a project's own conversations was the sidebar, which shows every conversation regardless of project. A **Conversations** tab now lists them — name, when it was last updated, a star, and a menu offering rename, favourite, move to another project, remove from project and delete — with a count beside the tab that stays right whichever panel you are looking at. It reads one filtered request rather than downloading your whole history and sifting it locally, which is what the API change below is for; there is no "showing the most recent N" caveat on it as a result. The panel keeps itself honest in both directions while it is open: a conversation moved out of the project — including from this panel's own menu — leaves the list, and one moved **into** the project from the sidebar appears in it. See [docs/ui/projects.md](docs/ui/projects.md).
- **Conversation search can be filtered by project** — `GET api/conversations/search` takes an optional `projectId`, so a client can list one project's conversations directly instead of paging through every conversation a user owns and filtering locally. It narrows the existing query rather than replacing it: results are still the caller's own active conversations, newest first, in the same paginated envelope, and `name`, `isFavorite` and paging all still apply alongside it. **A project that is unknown, deactivated or owned by someone else answers 404, not an empty page**, matching how the single-project route behaves so the listing cannot be used to probe for other users' project ids — the deactivated case is the one that needs it, since deleting a project releases its conversations and an unchecked filter would report "nothing here" for a project that had rows an hour ago. Omitting the parameter leaves the endpoint's behaviour unchanged, by construction: the filter and the ownership check sit behind one guard. No schema change and no new index — the filtered listing is owner-scoped, so it seeks the index the sidebar listing already uses. See [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).
- **Document retrieval (RAG)** — the assistant can now read the documents attached to a conversation. Uploading a file previously changed nothing about the answers a user got; a new `document_search` tool, attached automatically to every turn where the conversation has documents, searches the conversation's own files and — when it is in one — its project's, and hands back the passages that answer the question, each with a citation like `handbook.pdf p.12` for the model to quote inline. Search is **hybrid**: a cosine vector pass finds text that means the same thing, a keyword pass finds the exact tokens embeddings are weak at (error codes, part numbers, surnames), and the two are fused by rank. Matches are widened into their neighbouring chunks and merged into whole passages with the repeated overlap written once, so the model reads complete thoughts rather than text that stops mid-sentence. A relevance gate is deliberate and load-bearing: a question the documents do not answer returns **no** passages and says which documents were searched, rather than the least-bad text in the corpus dressed up as evidence. One thing about the result shape surprises everyone — passages are ordered by the fused rank of both passes, **not** by the `score` field, so a passage matched on an exact term can sit first with the lowest score of the set. **Requirements and limits:** retrieval needs a tool-enabled model (on one that cannot call tools it is skipped with a warning and the answer is ungrounded), and it needs a SQL Server 2025 engine or Azure SQL Database for the `vector` type — a 2025 LocalDB counts, so check `SERVERPROPERTY('ProductVersion')` for major version `17` rather than assuming a local instance is too old; what does block local development is a database carried over from an earlier version of the application, which has no chunk tables for retrieval to read. There is **no schema change and no migration**: it reads the columns ingestion already writes, needs no vector index, and needs no `PREVIEW_FEATURES` (the `vector` type and `VECTOR_DISTANCE` are GA on Azure SQL Database). Documents ingested with a different embedding deployment than the one now configured must be re-uploaded. Tuning lives under `Documents:Retrieval` and is validated at startup — `MaxDistance` (0.62) trades groundedness against recall and `MaxResultTokens` (3000) caps how much evidence competes with the answer for the context window. Search queries and retrieved passages are never streamed to the client and never recorded in the usage audit; the activity feed shows only "Searching 3 documents…" and how many passages came back. See [docs/documents/retrieval.md](docs/documents/retrieval.md).
- **A new web client at `enterprise-gpt-ui/`, rebuilt from scratch** against [docs/prd/enterprise-ui-rebuild.md](docs/prd/enterprise-ui-rebuild.md) — Angular 21, zoneless, standalone, Vitest — replacing the deleted `enterprise-ui/`, which could not read the framed SSE stream. Nothing was migrated. This first batch is foundation only: there is no sign-in, no chat screen and no routes yet, so the app is not yet usable. Two things in it change how the client is deployed and operated. **Configuration is now read at runtime, not compiled in:** one build artifact is promoted across every environment and `config.json` — the API base URL, the Entra ID client, authority and scopes, and the renderer feature flags — is replaced per environment, so there are no `environments/` files and no build-time replacements, and a production bundle can no longer ship pointed at `localhost`. Serve `config.json` uncached beside `index.html`, and overwrite it as a deployment step. **A broken deployment now says so:** the page shows a startup shell from first paint, and a `config.json` that is missing, unreachable, or invalid switches it to a failure message naming the offending field, with a retry button — instead of the blank page that failure used to produce. Because the shell starts visible, it also covers the bundle itself never loading. Internally, every API failure is normalized into one typed error covering all ten of the API's problem types, so a `traceId` reaches the user for support, failed validation lands on the field that caused it, and idempotent GETs retry gateway errors with jittered backoff while a busy conversation (409) and a misconfigured provider or storage (503) deliberately do not. See [docs/ui/frontend-foundation.md](docs/ui/frontend-foundation.md).
- **The web client's state layer** — the five composable `@ngrx/signals` features every one of the client's sixteen planned stores builds on, written and specced before the first store exists so that two hand-rolled pagination implementations never have to be reconciled later. `withRequestStatus` holds the lifecycle of a request as **one** value (`idle | pending | fulfilled | { error }`), so "loading and errored at the same time" — where stale spinners come from — is unrepresentable, and its error arm carries the whole typed error rather than a message, because the toast shows the `traceId` support will ask for. `withOffsetPagination` reads the API's paginated envelope and derives from the offset it has actually reached rather than the envelope's page numbers, so a short final page, a page size the server clamped down, and a total that is an exact multiple of the page size all behave without a special case. `withPendingIds` tracks in-flight work per row, so renaming one conversation no longer disables the other forty. `withClientQuery` and `withResetOnSignOut` complete the set, alongside a first, deliberate use of the `@ngrx/signals/events` plugin for the one thing plain store methods cannot do: sign-out, where a single event has to reach route-scoped stores that a root service cannot reach and that do not know each other exist. **Two constraints are encoded as behaviour rather than left to each screen's good intentions.** No endpoint in this API accepts a sort parameter, so client-side sort is offered only over a set the client holds in full — where it does not, the sort keys are ignored, results stay in server order, and the feature hands the UI the sentence explaining why, because a silently disabled control reads as a bug. - **A long answer now stays smooth all the way to the end** (US-602). - **Diagrams and formulas now render when an answer contains them — and cost nothing when it does not** (US-605). A ` ```mermaid ` fence becomes a drawn diagram and LaTeX becomes typeset mathematics, each with the library that does it fetched at the moment such content first appears and never before. **Both sit behind feature flags** (`features.diagrams` and `features.math` in `config.json`), so no deployment gets either until it asks for it — the shipped dev configuration turns both on, and with a flag off the content renders as an ordinary code block or as its own source rather than as an error. The reason for all that care is size: Mermaid is roughly **1.5 MB** across a family of chunks — its own build loads each diagram type on demand — and KaTeX about **280 kB** plus a stylesheet and twenty font files. None of it is in the initial download, none of it is in the chat screen's chunk either, and the build now fails if a stray static import puts it in _either_ — and fails just as loudly if the on-demand import is ever deleted, since every check of this kind passes when a library is simply gone. **On safety**, a rendered diagram is not markdown and does not go through the markdown sanitizer: it gets a second, separate one that removes the links Mermaid's `click` syntax would otherwise mint to an outside origin, removes the one element that can open an HTML document inside an SVG, and rewrites any CSS that would reach off this origin — which is not hypothetical, because a model-authored `%%{init: {"themeCSS": …}}%%` inside the fence reaches that stylesheet and Mermaid's own guard explicitly permits remote `url()`. There is deliberately no single-`$` form, because "it costs $5 to $10" is far commoner in an answer than inline maths. **Deployers: run `npm run assets`.** KaTeX's stylesheet and its font files are copied into `public/vendor/katex`, which is generated rather than committed; a deployment that ships the build without it renders mathematics unstyled, and the browser console says so. **One limit stated plainly:** no automated test in this repository runs real Mermaid — the test DOM implements none of the SVG measurement APIs its layout needs — so the libraries sit behind injection seams and the tests verify this application's own behaviour around them (the flags, the parse-before-render order, the sanitizing, the fallbacks, the redraws) rather than that Mermaid draws a correct picture; the manual pass with both flags on has **not** been run, because it needs a live API to produce an assistant answer. - `Anthropic:Thinking` (`adaptive` or `disabled`, default `adaptive`) and `Anthropic:Effort` (`low`, `medium`, `high`, `xhigh`, or `max`, default `high`) control how much every Anthropic turn reasons before answering — including the conversation-naming turn that runs on a conversation's first message. Both are deployment-wide: a model row carries no per-model override, so every Anthropic-backed model in the catalog runs at the same setting, and changing either needs a restart. Disabled thinking above `high` effort is rejected at startup, because the models reject that combination on every request. Two things to know before sizing a deployment: `Anthropic:DefaultMaxOutputTokens` (default 32768) is the ceiling on **every** Anthropic turn rather than a fallback, and with thinking on it covers reasoning and answer text together — fitted to the expected answer alone, turns truncate; and sampling parameters (`temperature`, `top_p`, `top_k`) are cleared on every Anthropic turn, because the models this provider targets reject them.
- **Models can now show their reasoning, and it is opt-in per model.** When a model is asked for a reasoning summary, the account of its thinking streams into the chat while it works — filling the reasoning region the client has had all along and that Azure-served turns never once populated. The switch is a new `isReasoningEnabled` field on the model catalog, editable by an administrator through `POST`/`PUT api/models` and **off for every existing model**: a deployment that does not support reasoning **rejects the whole request** rather than ignoring the option, so the failure mode is total and the capability is asked for rather than assumed. It is not free either — reasoning tokens are billed as output tokens, and deeper reasoning also means a longer wait before the first word. How verbose the summary is and how hard the model thinks are deployment-wide rather than per-model: `AzureOpenAI:ReasoningSummary` (`auto`, `concise`, `detailed`, or `none` to ask for no summary while still reasoning; default `auto`) and `AzureOpenAI:ReasoningEffort` (`minimal`, `low`, `medium`, `high`; default `medium`), both validated at startup and read once, so changing either needs a restart. **Two limits are worth stating.** The flag is read by **one provider** — Azure OpenAI, on the Responses API; the Bedrock and Anthropic clients take their reasoning settings from their own configuration, and the Azure AI Foundry client has no reasoning surface to take them to, so setting it on a model any of the three serves changes nothing. And reasoning is still never stored: it is streamed and shown, never written to the transcript, so reopening a conversation shows the answers and not the thinking behind them. **Operators:** this ships as a real EF migration, `20260813233326_AddModelIsReasoningEnabled`, which `Database.Migrate()` applies at startup — the second migration in the repository after `InitialCreate` — adding `Core.Ref.Model.IsReasoningEnabled` as `bit NOT NULL DEFAULT 0`. **Clients** of the model API get one new additive field, but note that `PUT api/models/{id}` replaces the whole model, so an update that omits it silently turns reasoning off. See [docs/models/azure-openai.md](docs/models/azure-openai.md#5-reasoning) and [docs/models/model-management.md](docs/models/model-management.md#23-isreasoningenabled).
- **A fabricated weather tool, for exercising the assistant's activity timeline.** The timeline's running rings, sub-status bullets, durations and failed cards previously needed a live MCP server or an uploaded document to appear at all, which meant the surface was rarely looked at outside a test fixture. A fake `get_weather` function, attached to every turn when `Tools:Weather:Enabled` is set, gives the timeline something to draw from a real conversation: it reports two sub-statuses as it runs, takes a configurable `Tools:Weather:DelayMilliseconds` (default 600) so the running state is visible at all — an instant tool call completes inside a single stream flush and the card appears already finished — and **fails deliberately for any location whose name contains `fail`**, which is the only way to reach the failed card on demand. Everything it answers with is invented, so it is **off by default**; enabling it in Production is permitted but prints a warning to standard error at startup, and the model will report its invented readings to users as fact. Like every other tool it stands down on a model that cannot call tools, with a warning rather than a failed turn, and its progress messages deliberately carry no part of the model's arguments — the same privacy posture as every other activity event. Setup is in the [README](README.md#3-configure-api-environment-variables).
- **Request logging and Application Insights** — the API now writes an access-log record for every request, so a request that failed without raising an exception is no longer invisible. A 403 from the permission filter, a 401 challenge, an oversized upload and an unrouted 404 previously produced no log line at all; they now each produce one, at a level that carries the meaning (5xx and faults at Error, 4xx and slow requests at Warning, everything else at Information), with the method, path, status, duration, route, caller and outcome on it. Records go through `ILogger` under the category `Enterprise.Gpt.Api.Middleware.RequestLoggingMiddleware` — deliberately outside the `Microsoft.AspNetCore` prefix pinned to Warning — so setting `"Enterprise.Gpt.Api.Middleware": "Warning"` yields a complete error log and nothing else. Query string values, the request path and captured payloads are redacted and stripped of control characters, and logging can never fail a request. Optional request/response body capture is **off by default** and, when switched on, captures every request rather than only failures, so treat it as a debugging session rather than a setting: conversation and document routes are excluded, non-text media types are refused, and SSE streaming is unaffected. Configuration lives under `RequestLogging` and is validated at startup — note that setting any list in configuration **replaces** its default rather than extending it. Application Insights is wired through the Azure Monitor OpenTelemetry distro and registers only when `APPLICATIONINSIGHTS_CONNECTION_STRING` or `AzureMonitor:ConnectionString` is set, so local runs and tests stay exporter-free; once configured, access-log records land in `traces` correlated by `operation_Id` with the `traceId` the API already returns on problem responses, and the LLM spans and `gen_ai.client.token.usage` the chat clients were already emitting are finally exported. Check the distro's default sampling (5 traces/second) before relying on the log under load. See [docs/observability/request-logging.md](docs/observability/request-logging.md).
- **Projects** — a user-owned container that groups conversations and gives them a shared document set and standing instructions. Manage projects at `api/projects`, upload documents into one with `POST api/documents/projects/{projectId}` (same pipeline and upload-status route as conversation uploads), and place a conversation in a project with `projectId` on conversation create or update. A project's instructions are read fresh on every turn and applied as request-level instructions, so editing them affects conversations that already exist without altering their transcripts. Deleting a project removes its documents but keeps its conversations, which become standalone. Note two things before adopting it: `PUT api/conversations` replaces the whole conversation, so an omitted `projectId` removes it from its project; and a project's documents reach a conversation only through document retrieval, so they influence answers only on a tool-enabled model. The new `Core.Project`, `Core.ProjectDocument` and `Core.ProjectDocumentChunk` tables and the `Core.Conversation.ProjectId` column ship as EF model changes only — there is no migration and no DDL script, so they must be applied to each real database out of band before the feature can be used (SQL Server 2025 or later). See [docs/projects/project-management.md](docs/projects/project-management.md).
- **Document download** — users can now retrieve the original file behind a document they uploaded, from a conversation with `GET api/documents/conversations/{conversationId}/{documentId}` or from a project with `GET api/documents/projects/{projectId}/{documentId}`. The API never proxies the bytes: it authorizes the caller and returns `{ downloadUrl, fileName, expiresAt }`, and Azure Storage serves the file from a short-lived, read-only service SAS — which keeps 50 MB transfers off the API process, since a read path has none of the queue and concurrency limits that bound ingestion. **Treat `downloadUrl` as a credential, not a link:** anyone holding it can read the file until it expires, so the response is sent `Cache-Control: no-store`, the URL is never logged, and `downloadUrl` is now a default redacted property name in request logging. Lifetime is `Documents:DownloadUrlLifetimeMinutes` (default 5 minutes, range 1–60, absent from `appsettings.json` so it runs on the default); an issued link **cannot be revoked** before it expires, which is why the window is minutes. Access follows the parent conversation or project's owner rather than whoever uploaded the file, and a document the caller cannot see returns **404, never 403**, so the route cannot be used to probe for ids — no permission grant is involved, as `Upload File` gates uploading only. The link renames the file back to its uploaded name and serves it as an attachment with a content type derived from the validated extension (unrecognised extensions fall back to `application/octet-stream`). One deployment requirement: signing needs a **shared-key** `AzureStorage:ConnectionString` and a set `AzureStorage:DocumentsContainer`, or every download fails with the new 503 `/problems/storage-not-configured`; moving to `DefaultAzureCredential` later means switching to a user-delegation SAS. Clients should navigate to `downloadUrl` rather than fetching it, which needs no `Authorization` header and no storage CORS rule — the Angular app has no consumer for these routes yet. See [docs/documents/download-workflow.md](docs/documents/download-workflow.md).

- **Per-tool token tracking** — token usage is now attributed to the individual tool, MCP server or agent that consumed it, with nesting preserved, instead of disappearing into one undifferentiated total for the turn. A tool that calls an LLM of its own, an MCP call whose server spends tokens internally, and an agent-as-tool running a different model than the assistant are each recorded, and a tool invoked inside another tool is recorded underneath it. Every turn writes its invocations to the new append-only `Core.ConversationUsageToolCall` table: which tool ran, of what kind, under which parent, correlated to a catalog MCP server where that can be established, how long it took, whether it succeeded, and what it cost. The token columns split deliberately — each row carries its **own** consumption in `InputTokens`/`OutputTokens`/`TotalTokens` and the whole-subtree rollup in `SubtreeTotalTokens` — so `SUM` over any filter counts each token exactly once, while the end-to-end cost of one call stays a single-column read. `Core.ConversationUsage` gains `ToolInputTokens` and `ToolOutputTokens` alongside them, leaving `InputTokens`/`OutputTokens` to mean the assistant's own model turns; the assistant-only figure is now `AssistantTokens` and `TotalTokens` means the whole call. Two honest limits: nothing in a tool call names the model behind it — an MCP server is opaque by construction — so `ModelId` and `DeploymentName` are recorded only where this application knows the answer itself, which today is nowhere; and there is still no reporting endpoint, no UI and no price data, so this remains a SQL exercise. **Operators:** the new table and the two new columns ship as EF model changes only — no migration, no DDL script — so they must be applied to each real database out of band **before** this release is deployed; until they exist, every completed turn streams its answer and then fails. See [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).
- **Conversation usage tracking and favourites** — every model call charged to a conversation is now recorded in the new append-only `Core.ConversationUsage` table: which model, provider and deployment served it, the input/output token split, whether it completed, and (in `Core.ConversationUsageMcpServer`) which MCP servers were attached to it. The provider, deployment name and server names are snapshotted onto each row, so renaming a model or repointing it at another provider cannot rewrite the history of the calls it already served. That makes tokens by model, by provider, by user and by day — and the cost of turns users cancelled — a single `GROUP BY`, in SQL: there is no reporting endpoint and no UI yet, and no price data, so money is still a spreadsheet exercise. Conversations also remember the model and MCP selection of their most recent turn: `GET api/conversations/{id}` now answers with `modelId` and `mcpServerIds` so a client reopens a conversation on the model and tools it was last run with, with servers that have since been deactivated or revoked filtered out rather than replayed into a turn that would reject them. Favourites arrive as a dedicated `PUT api/conversations/{id}/favorite` (body `{ "isFavorite": true|false }` → 204) plus an optional `isFavorite=true|false` filter on `GET api/conversations/search`; it is its own route rather than a field on the full-representation `PUT api/conversations`, where a rename that forgot to echo the flag would silently un-favourite the conversation. **Operators:** the two new tables and the new `Core.Conversation.ModelId` and `IsFavorite` columns ship as EF model changes only — no migration, no DDL script — so they must be applied to each real database out of band **before** this release is deployed; until they exist, a conversation's first turn fails outright and every later turn streams its answer and then loses it. See [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).

- The Claude Design handoff bundle for the UI rebuild, under `docs/design/`, together with `node docs/design/serve.mjs` (or the `serve-design` VS Code task) to view it at <http://localhost:4300>. The boards have to be served over HTTP — opened from disk, the browser blocks the sibling-component fetches the prototype runtime depends on and every shared component renders empty — and they load React, Bootstrap and their fonts from CDNs, so viewing them needs an internet connection.

- **Every message now records what it costs to keep, and a turn is never sent with a prompt the model will reject.** Each stored message carries an estimated **context cost** — what that message contributes to the prompt on every future turn — counted locally from the message's own text, with a vocabulary chosen for the deployment that will read it, and rolled up onto the conversation and onto each usage row as `ContextTokens`. Built on that, replayed history is now **trimmed to the model's context window**: the oldest exchanges are dropped first, a dropped question takes its answer with it so the model never sees a reply to something it cannot see, and the system message and the current prompt are never dropped. A prompt that cannot fit even then **fails with a 400 naming the model and its window** instead of being sent and rejected after the user has waited for it — and a catalog row whose `ContextWindowSize` is still `0` is treated as unbounded rather than as a budget of zero, so an unfilled field cannot silently trim every conversation to nothing. Trimming decides what is _sent_, never what is _stored_; the transcript keeps everything either way. **Two things are worth knowing before reading these numbers.** `ContextTokens` and the billed token columns beside it are _supposed_ to disagree, by more the more tools a turn runs, because tool calls, tool results and reasoning are billed by the provider and never transcribed — the naming rule is that `Context*` means estimated and replayed while every other token field is provider-billed, and the two are never summed. And the estimate is measured rather than asserted: on turns that ran **no** tools, where the estimate and the provider's reported input tokens genuinely measure the same thing, the signed relative error is recorded to the solution's first `Meter` (on the existing `Enterprise.Gpt.Chat` source, so it exports with no new wiring), alongside counters for what trimming dropped — with no conversation id, user id or message content on any dimension. tiktoken is OpenAI's tokenizer and undercounts other vendors, so a per-provider calibration multiplier is read from configuration and validated at startup, letting a measured undercount be corrected without a code deployment. Tuning lives under `Tokenization:*` and every value has a default, so no configuration is required. See [docs/conversations/transcript-storage.md](docs/conversations/transcript-storage.md).
- **A conversation can now be taken out of the platform** — `GET api/conversations/{id}/export?format=html|json` returns the whole conversation as a self-contained HTML document or as structured JSON, chosen by query parameter rather than by `Accept` header so a plain browser link works. It is a **read, not a re-render**: every message is now rendered to HTML once, server-side, at the moment it is stored, so an export never depends on a client rendering markdown again. The JSON form is deliberately the _storage_ shape — the same property names the stored documents carry — rather than a third representation of the same data. Exporting another user's conversation, or a deleted one, answers **404** like every other conversation route, and an unsupported `?format=` answers 400 naming the two that work. A message stored before server-side rendering existed is HTML-escaped into the output rather than omitted. See [docs/conversations/transcript-storage.md §12](docs/conversations/transcript-storage.md#12-export).
- **Models carry a price, so the audit trail can answer "how much money" and not only "how many tokens"** — closing the gap this changelog's usage entries have recorded since the trail was built. Administrators set nullable input and output prices per **1,000,000 tokens** on a model (per million, not per thousand, because provider price sheets are quoted that way), through the existing admin-gated `POST api/models` and `PUT api/models/{id}` and returned on `ModelDto`; no new permission is introduced. Every usage row **snapshots the pair at write time**, exactly as it already snapshots the deployment name, so an administrator editing the catalog cannot rewrite what past calls cost — and naming calls are priced like any other, since they are real billed completions. Cost itself is a computed member with no column of its own, and it is deliberately **null rather than a partial figure** when either price is missing: adding only the priced half produces a number that looks like a cost, understates it, and cannot be told apart afterwards. Three limits are stated rather than hidden: tool tokens can only be priced at the _driving_ model's rate, because nothing in a tool call names the model behind it, so cost is an approximation by construction; a single currency is assumed and it is USD; and prices are snapshotted rather than versioned, so the trail answers "what did this call cost" and not "what would last quarter cost at today's rates". A reporting query producing per-conversation and per-model cost **from one table with no join to the catalog** — with billed model tokens, billed tool tokens and context tokens as three separate columns — is in [docs/conversations/usage-and-favorites.md §7](docs/conversations/usage-and-favorites.md#7-reporting).
- **The app works on a tablet and a phone** (US-1403). Below 1024px the sidebar stops being persistent: between 768px and 1023px it defaults to the 60px strip and expands as a panel floating over a backdrop, and **the content beside it does not move** — the panel leaves the layout and a spacer holds the track it vacated, so "never reflows" is structural rather than arithmetic, with the content behind the backdrop made unreachable by keyboard as well as by pointer. Below 768px the sidebar leaves the frame entirely: a 54px navbar carries a hamburger that opens it as a full-screen drawer with focus trapped and returned, and the conversation header gives up its bar — its star and kebab move into that navbar rather than disappearing, which is the last of the three things deferred out of the chat header back in EP-3. The composer, the transcript and the drawer all respect the device's safe areas, so nothing sits under a notch or a home indicator, and picker dropdowns span the viewport instead of hanging off its edge. The project-detail tabs become the same scrollable pill strip the admin area uses; the design boards ask for stacked accordions there, and the departure is deliberate and recorded — those tabs are real routes, one of which can refuse to navigate, so a control announcing itself as "expanded" would be announcing something it cannot guarantee. **One thing to know if you maintain a stylesheet:** the application's two breakpoints are now stated once, in `src/styles/_breakpoints.scss` and `shared/layout/breakpoints.ts`, and `npm run lint` refuses a hand-written one. Twelve stylesheets had carried six spellings of those two numbers, and the mismatched pair (`767px` beside `768px`) left a 0.98px band — reachable by browser zoom or Windows display scaling — that matched neither layout. Two gates now keep the two copies in step, including the fractional maxima.

Upgrading the streaming library (`Andes.Extensions.AI` 0.5.0 → 0.7.0) changed what the stream sends: an MCP activity now carries the real tool name, and the server stays in the subtitle where it belongs. The API side made the trimming reliable rather than lucky: a borrowed tool is now tagged with the server name **an administrator registered and the user picked**, not the name the server advertises about itself — those can differ, and when they did, the tool's usage could only be matched back to a catalogue entry by resemblance. - **Azure turns now go through the Responses API instead of Chat Completions.** The chat client is built on the plain OpenAI client pointed at the resource's OpenAI-compatible v1 endpoint, rather than on `AzureOpenAIClient`, because reasoning summaries exist only on that surface — over Chat Completions Azure returns none, whatever the deployment, which is why the assistant's reasoning region was always empty. **Answers, tools, streaming, telemetry and token accounting are unchanged**, and the other providers are untouched. Two things change for operators. **The Azure section is now validated at startup**, where it was previously read with unchecked configuration lookups: a missing key or a malformed URL refuses to boot with a message naming the setting, instead of throwing on the first conversation. And **`AzureOpenAI:Url` must be the resource root** — the v1 path is derived from it, so a URL that already carries `/openai` or `/openai/v1` is now a startup failure rather than an unexplained 404 on every turn; both the `services.ai.azure.com` and `openai.azure.com` hosts are accepted, and no new setting was added. **On privacy, the posture is preserved rather than inherited:** the Responses API retains prompts and answers service-side for 30 days by default, where Chat Completions stored nothing, so every turn is sent with storage explicitly disabled — the transcript this application keeps remains the only copy. That also happens to be what keeps tool calling working, since the whole exchange has to travel in each request once the service is no longer tracking it. This provider was called "Azure AI Foundry" when the swap landed and is now called **Azure OpenAI**; its settings moved with it, and both changes are described in the configuration-rename entry above. See [docs/models/azure-openai.md](docs/models/azure-openai.md).
- **The web client's shared table and bulk bar gained the three things a paged, selectable screen needs**, so the next list to be built does not re-solve them. A table can now be handed the count it should announce, for a caller that knows how many rows exist beyond the ones it holds — with the caller's own visible copy hidden from assistive technology, since two derivations of one number eventually disagree. Its header select-all can be turned off for a design that puts select-all in its own toolbar, because two controls bound to one state is a defect and there is no header row at all below 768px. And **row selection now works below that breakpoint**, where the table becomes a list of cards: previously a screen that enabled selection got checkboxes on a laptop and none on a phone, silently. The floating bulk-action bar also caps its width and wraps rather than running off a narrow viewport (WCAG SC 1.4.10), which it has to do itself because it is positioned outside the page flow and no call site can rescue it. One trap is documented rather than fixed, because it is Angular's projection semantics: a footer wrapped in an `@if` is dropped without an error, so the condition must go **inside** the projected element. See [docs/ui/design-system.md §7.4](docs/ui/design-system.md#74-data-surfaces--shareddata).
- **The web client's prompt box is now a shared component, and what runs a prompt is injected into it.** Putting the same composer on the project screen was the requirement; the obstacle was that it lived inside the chat feature and reached directly for the chat screen's own turn store, and two lazily-loaded features that import each other stop being lazy — everyone opening either screen downloads both. The composer, its model and tools menus and its dictation store therefore moved into the shared layer, the upload store moved down beside them, and what executes a prompt became an injection token: the chat screen supplies the store that streams a turn in place, the project screen supplies one that creates a conversation and navigates to it. **Nothing about either screen changed for users**, and the initial download did not grow — the composer now sits in a chunk the two lazy screens share. A lint rule was added so the layering that forced all this is checked rather than remembered: the shared, core and domain layers may no longer import from a feature, and the failure message names the escape hatch. Test files are exempt, since a spec that drives the real store is not part of the shipped graph. See [docs/ui/projects.md §3](docs/ui/projects.md#3-the-prep-step-the-composer-moved-down-a-layer).
- **Breaking for operators, and destructive — the conversation transcript moved to one document per message, and every existing transcript is destroyed at cutover.** A transcript used to be a single Cosmos document holding every message in an array, which meant a conversation that was used long enough eventually became unwritable against Cosmos's 2 MB item limit, and that the whole document was rewritten and re-indexed on every turn. Messages are now individual documents in a **new container**, under a synthetic partition key holding `{userId}:{conversationId}`, so the largest document a conversation produces is bounded by its longest single message rather than by its message count, and a turn's two messages and the conversation's counters are written in **one transaction** — a counter can no longer claim a message that was never stored. **There is no migration of existing transcripts: no backfill, no dual-read, no lazy conversion.** Everything in SQL survives untouched — names, favourites, projects, token counters, the whole usage audit trail and its tool-call trees — and every conversation still opens; it just opens **empty**, and the first turn taken in it rebuilds its header and re-seeds the assistant's standing instructions so the conversation is usable again from its next prompt. Three deployment gates come with it, all of which fail at boot rather than at the first request. The Cosmos section is now bound and validated at startup, so a missing database or container id refuses to start instead of throwing on the first conversation. **`CosmosDb:ContainerId` is rejected outright** — the new key is `CosmosDb:TranscriptContainerId`, and a configuration still naming the pre-cutover container fails startup by design, because starting would answer every transcript read with an empty result, which reads as data loss rather than as a setting nobody removed (remember App Service settings and `CosmosDb__ContainerId` container variables, not just the file you edited). And the container is provisioned by the application with the `/pk` key path and an indexing policy that excludes the two largest properties, refusing to start against a container partitioned any other way. Deleting the old container is a **separate, later** operator step — nothing reads it, so it costs storage only, and that gap is the one piece of reversibility this change has. One SQL migration ships with it and applies through `Database.Migrate()` at startup like the three before it; a database that predates the migration history must be baselined first, and the engine must be SQL Server 2025 or later, which was already true. **Read the runbook before deploying: [docs/conversations/transcript-cutover.md](docs/conversations/transcript-cutover.md).** Design and rationale: [docs/conversations/transcript-storage.md](docs/conversations/transcript-storage.md).
- **`GET api/conversations/{id}/messages` gained five per-message fields and opt-in paging, and its default is deliberately unchanged.** Each message now carries `id`, `dateCreated`, `htmlContent` (server-rendered, or null — a client that gets null renders the text itself), `tokens` and `tokenAccuracy`, and the envelope carries `totalCount` and `hasMore`. `text` and `role` are unchanged in name, type and meaning, so an existing client keeps working, and **calling the route with no query parameters still returns every message** — a stated deviation from the story, which specified "the newest 100 by default", so that the Angular client's transcript read is not broken by a server release. Paging is there when a client wants it: `?take=` (clamped 1–100) and `?before={dateCreated}` walk the transcript backwards from the newest message. Two shape notes for anyone building on this. `role` is still an **integer** on the wire while the stored document now serializes it as a camel-cased **string** — two different contracts, deliberately, because a global string-enum converter would have flipped `role` and broken every client reading it; `tokenAccuracy` is a string because it carries a property-level converter of its own. And `tokens` is the **context** cost, not what the turn was billed, so an assistant message's `tokens` will not equal the turn's reported output tokens. See [docs/conversations/turn-lifecycle.md §7.4](docs/conversations/turn-lifecycle.md#74-the-message-shape-has-two-sharp-edges).
- **Cosmos documents are now serialized with System.Text.Json, and stored timestamps are pinned to a fixed-width UTC format.** The SDK's Newtonsoft default was active while the document types carried `[JsonPropertyName]` attributes it never read — the two agreed only because the camel-case policy happened to produce the same names, and this repository already carried a bug from that mismatch, where a query's predicates matched no document and so silently selected nothing. The date format is not cosmetic: Cosmos has no date type, so ordering a transcript is a **lexicographic comparison of strings**, and that equals chronological order only while every value shares one offset and one width. The default round-trip format preserves the original offset and trims trailing zeros from the fractional part, both of which produce orderings that are wrong — an answer rendered before its question, and replayed to the model that way on every later turn. Every stored timestamp is now normalized to UTC and padded to seven fractional digits, which is also what keeps a turn's two messages distinguishable when it completes within a single tick.
- **Operators:** the Anthropic row in `Core.Ref.Provider` ships as an EF `HasData` seed only — this release contains no migration and no DDL script, so the row reaches test databases built by `EnsureCreated()` but not a real one, and the gap fails silently. Insert it by hand with the id `6F93EC17-E981-409F-A523-700584F1E7D6` and the name `Anthropic`, or every attempt to create an Anthropic-backed model returns 404 "Provider not found" regardless of configuration — and a row created with a freshly generated id creates models happily and then 503s on every turn. Steps in [docs/models/anthropic.md](docs/models/anthropic.md#101-the-anthropic-provider-row-does-not-reach-a-migrated-database).
- **Two colours changed, and both are visible.** The warning colour in the light theme is slightly deeper (`#A96A10` → `#9C6210`) and the "active row" tint in the dark theme slightly darker (`#173A58` → `#16354D`). Both were below the WCAG AA contrast minimum for the text drawn on them: the first affects every warning badge, chip and notice, and the second affects the admin rail's current tab, the sidebar's current navigation link and the paginator's current page. The second was found by the new axe run rather than by review, and only once the browser viewport was pinned to a desktop width — it had been shipping unnoticed for three releases of this work. Both corrections were made in the shared design bundle rather than overridden in the app, so anything else built from those boards inherits the fix, and both are now measured by `npm run lint` (46 contrast pairs, up from 38).
- **A reduced-motion preference now also defeats animation *delays*** (US-1404). The global suppression block already floored every duration; a delay survives a floored duration and reappears as a late jump, so `animation-delay` and `transition-delay` are zeroed alongside. The rest of the story was verification rather than change: every animation the app runs was checked end-state by end-state, and the global block is sufficient for all of them — so no redundant per-site overrides were added, and the four sites that carry one are the four whose settled state would otherwise be wrong. Two build gates now hold the contract: the app may define no fifth keyframe, and the four it does define are compared against the design bundle, so a drifted transcription cannot change how the app moves with every check still green.

### Removed

- **`IAzureCosmosService` and the single-document transcript are gone**, replaced by `ITranscriptStore` over the per-message shape. The old service could not express the two things the new transcript needs — a transactional batch and a continuation-token paged query scoped to a partition — and three of its members (`GetItemsAsync`, `UpdateItemAsync`, `DeleteItemAsync`) had no production caller at all; one of them drained every page of a query into a list with no partition key, which is a cross-partition fan-out waiting for a caller. The replacement has the opposite property: **every member requires a partition key and none accepts a cross-partition query**, so a transcript read that fanned out is unreachable through the surface rather than merely discouraged. Gone with it: the `CosmosConversation` document types, the `documents[]` array that had been dead since inception (nothing ever added to it — conversation documents live in SQL), the `messageCount` getter that counted an in-memory collection while the write path incremented the stored property beside it, and the integration suite's `FakeAzureCosmosService`, which is now `FakeTranscriptStore`. The storage layer is proved against the real **Cosmos DB Linux emulator** in Testcontainers, because transactional batches and ordered cross-document queries are exactly what a fake cannot prove — a fake that interpreted JSON-patch semantics would only be asserting its own arrangement.
- **`Azure.AI.OpenAI` is gone from the solution.** It was pinned at `2.9.0-beta.1` — a prerelease whose last stable release, 2.0.0, is long superseded — and after the chat client moved to the Responses API its only remaining consumer was the embedding generator, which now uses the plain OpenAI SDK against the same resource's v1 endpoint (see Changed). Microsoft's own `Azure.AI.OpenAI` migration guidance now carries the note _"This guidance is no longer recommended. To take advantage of the latest v1 API refer to the .NET programming language guide"_, so this follows current direction rather than anticipating it. `OpenAI` becomes a direct package reference in its place, at 2.12.0. Nothing observable changes: same resource, same deployments, same stored vectors, one fewer prerelease dependency and one fewer Azure-specific client shape in the codebase.

### Fixed

- **A document uploaded into a conversation that was deleted while the file was still processing no longer lingers.** Ingestion takes seconds to minutes, and deleting the conversation in that window ran its document clean-up before the new row existed — the clean-up never re-runs, so the document and its search chunks stayed active under a deleted conversation, invisible only because nothing listed documents until now, with a download that would then fail. Both ingestion paths (conversation and project — the project side had the same window) now re-check the parent after persisting, deactivate the just-stored document to match, and fail the upload job with the same not-found message an upload into an already-deleted conversation gets. See [docs/ui/documents-library.md §3.4](docs/ui/documents-library.md#34-the-ingestion-re-check).
- **Keyboard and low-vision users can now see where they are, and reach what they can see** (US-1401). The app was already largely operable without a mouse — every overlay returns focus to whatever opened it, menus move with the arrow keys, and there is not one clickable icon pretending to be a button — so this closed the two places that were genuinely broken and made the rest of the claim something the build checks rather than something a comment asserts. **A code block wider than the column could only be scrolled with a pointer.** It scrolls sideways, and there was no way to put the keyboard inside it, so the end of a long line was simply unreadable without a mouse; code blocks are now focusable. They are deliberately left **unnamed** when you land on one — the obvious label is invalid rather than merely unnecessary, because the accessibility mapping for a code block forbids naming it, and giving it a name properly would mean announcing every code block as a titled region. The Copy button beside it already says "Copy ts code block", which is the name a reader actually needs. **And five focus indicators were too faint to meet the 3:1 contrast the standard asks for — one of them being every button in the app.** The ring three composer controls, the empty-state chips and the prompt box drew was a colour meant to *fade out* from under a control, not to outline one; the form fields drew a tinted glow at roughly a fifth opacity; and Bootstrap's own buttons, tabs and checkboxes each remove the browser's outline and replace it with a wash measuring between 1.3:1 and 2.4:1 — that is every dialog footer button, every administration row action, the sign-in screens' calls to action, the project tabs and every checkbox. All of them now draw the one measured focus colour. **Two smaller decisions in that are worth knowing, because both look like details and neither is.** The ring sits **outside** the control with a gap, never flush against it: drawn on a filled primary button it measures 1.00:1 in the dark theme, where the button's own fill *is* the focus colour — a ring that is literally invisible. And a checkbox needs two rules rather than one, because Chrome does not treat a checkbox clicked with a mouse as keyboard-focused, so one rule clears the old wash on a click and a second draws the ring for the keyboard. **What stops this coming back is two build checks rather than a review habit.** The first measures the focus colour against every surface a ring can land on and refuses to fall behind the stylesheets in either direction — a new surface nothing measures fails the build, and so does an exemption for a surface that no longer exists. The second refuses any rule that removes a focus outline without drawing one, and refuses the fade-out colour outside the animation it belongs to; a per-line exemption covers the four places that are right anyway, and it applies **only** to those two rules, after a review round caught an earlier version that would have let a comment wave through the ban on trusting model output as HTML. **Three limits are recorded rather than hidden.** The outline check reads the application's own stylesheets, not the compiled one — which is exactly how Bootstrap's five suppressions passed the check written to catch them, and closing it needs a build step the check does not have today. A focused button held down briefly regains Bootstrap's wash, which is transient and has no persistent case. And every code block now costs two stops on the way through a page, whether or not it overflows, so a long answer takes longer to tab past. **The initial download grows 0.15 kB to 669.93 kB raw / 168.91 kB transfer**, inside the unchanged 670/720 kB budget, with the stylesheet at 64.17 kB against 65/80 kB — all of it global CSS, and most of the override's cost paid back by dropping a Bootstrap helper that emitted an unused 1.4:1 ring. That leaves **0.07 kB of headroom** against the warning line, which US-1405 owns and is the right place to re-state. Verified by 1697 passing tests and the lint gates; the browser-only behaviours (the top layer, native inerting, light dismiss) are checked by hand through the development gallery, and no screen-reader pass against real assistive technology has been run. See [docs/ui/design-system.md §8.1](docs/ui/design-system.md#81-focus) and [docs/ui/answer-rendering.md §3.5](docs/ui/answer-rendering.md#35-the-code-block-chrome-and-its-copy-control-us-603).
- **A misconfigured Azure provider URL built a nonsense endpoint on Linux instead of failing.** `V1Endpoint` derived the client's base address by handing `Url` straight to `Uri`, trusting it to reject anything that is not a URL. It does on Windows — but on Unix a string starting with `/` is an implicit file path, so an unset or path-shaped `Url` quietly produced `file:///openai/v1/` on exactly the hosts the API is deployed to, and every request went nowhere with no hint as to why. The property now checks the same absolute-http rule the startup validator uses and throws `UriFormatException` otherwise, identically on both platforms. The startup validator still rejects such a URL first; this is the guard for a caller that never went through it. The unit test that covered this had been asserting a Windows-only accident and broke the Linux CI run.
- **The integration test suite could not start at all.** Every integration test failed before a single one ran, and the message pointed at Azure configuration rather than at the tests. `appsettings.json` ships the optional Azure AI Foundry provider with `Enabled: true` but an empty `Url` and no key — harmless for a developer who never resolves that client, and fatal under `WebApplicationFactory`, which loads the same `appsettings.json` from the test output and validates the section at host startup. The test factory now switches the section off explicitly, which is what its own comment always said it intended: no keyed client is exactly the shape the provider resolver's 503 path expects.
- **A seeded-model integration test asserted the wrong field.** `GetModel_SeededModel_ReturnsModel` compared the seed's _deployment_ name against `ModelDto.Name`, so it would have failed against the data it was written for. It was invisible for as long as the suite above could not run; it now checks the display name and the deployment name separately.
- **The assistant's reasoning never appeared.** The chat screen has a region for the model's thinking, and on every Azure-served turn it stayed empty — the only reasoning text a turn ever carried was the opening sentence the server writes itself, which the client deliberately does not show. Nothing in the pipeline was missing: the stream already carries reasoning frames and the client already renders them. What was missing was a provider that emits any, because Azure returns reasoning summaries only on the Responses API (see Changed) and only for a deployment that was asked for one (see Added). Turns on a model with `isReasoningEnabled` set now fill the region as the model works.
- **The API project did not compile.** `Microsoft.OpenApi` was pinned to 3.9.0, where `IOpenApiMediaType.Example` became read-only, while the XML-comment source generator shipped with `Microsoft.AspNetCore.OpenApi` 10.0.10 still assigns it — so the build failed inside generated code and no amount of source changes could clear it. The pin moves to 2.11.0, which stays in-major for the generator and is above 2.7.5, the patched release for GHSA-v5pm-xwqc-g5wc that motivated pinning in the first place. Both packages move together when a matching `Microsoft.AspNetCore.OpenApi` ships.
- A turn abandoned or faulted mid-stream now records what its **tools** spent as well as what the assistant spent. Usage is collected out of band from the tracking middleware rather than read off the response, so an outcome that never reaches the end of the stream still accounts for itself. The provider-side limit is unchanged and unavoidable: usage is reported at the end of a model turn, so tokens from a turn cut off mid-generation were billed and cannot be known — a cancelled turn's recorded cost is a lower bound.
- Token accounting no longer loses the calls it could not see. A turn the user stopped, or one that faulted mid-stream, consumed tokens the provider billed for and moved nothing: its cost simply vanished. Such turns are now added to the conversation's running totals and recorded with a `Cancelled` or `Failed` outcome — while still, deliberately, being kept out of the transcript, since replaying a truncated answer to the model on every later turn is worse than not having it. The completion that names a conversation from its first prompt was likewise a real, billed model call recorded nowhere; it now writes its own usage row and counts towards the conversation's totals, which means totals and reports built on them no longer understate what was spent.
- **The projects screen never actually had a grid.** Its cards were asking for a three-column layout using Bootstrap grid classes that this application deliberately does not ship, so they had been stacking one per row at every width — on a wide monitor as much as on a phone — since the screen was built. They now lay out in as many columns as the width allows, down to a single full-width column on the narrowest phone.
- **Four screens were being cut off below the fold with no way to scroll.** The conversation library, the projects grid, a project's detail screen and the whole administration area sat inside a fixed-height frame without a scroll region of their own, so any content past the bottom of the window was simply unreachable — at every window size, not only on a small one. All four now scroll.
- **A dropdown opened near the right edge of the window could run off screen.** Menus and the project picker were positioned from their trigger with nothing keeping them inside the viewport; they are now clamped, and on a phone they span the width instead of hanging off the edge.

### Security

- **Server-side markdown rendering treats model output as untrusted, and the transcript's partition key now enforces tenancy in storage.** Storing a rendered form of every message means the API produces HTML for the first time, from input that is attacker-influenceable — model output is shaped by uploaded documents and MCP tool results, and user prompts go through the same renderer. Two independent layers stand behind it. Raw HTML is **dropped at the parser**, so a `<script>` block or an `<img onerror=…>` in an answer is emitted as escaped text and never becomes an element. Link targets are then filtered against an **allowlist** of `http`, `https` and `mailto` — an allowlist rather than a blocklist of the known-dangerous schemes, because `javascript:` is only the best-known of them and a blocklist is wrong the moment a browser accepts something not on it — with control characters stripped before the scheme is read, since browsers ignore them inside a scheme while a naive comparison sees something on no list. Rendering never throws: a failure degrades to escaped plain text and is logged by **length only**, because the content is a prompt or an answer and neither belongs in a log. Separately, composing both the user id and the conversation id into the transcript's partition key means **a foreign conversation id addresses a partition that holds nothing**, so another user's transcript is unreadable even if a code-level ownership check is ever missed — the read answers 404, as every other conversation route does, without relying on a filter. Export applies the same rule and additionally re-checks in SQL, because a soft-deleted conversation still has a transcript. And the new metrics carry **no conversation id, user id or message content on any dimension**: metric dimensions are high-cardinality storage retained and queried far more widely than logs, and neither identifier answers a question the deployment name does not. See [docs/conversations/transcript-storage.md §11](docs/conversations/transcript-storage.md#11-server-rendered-html).
- **A high-severity SSH.NET advisory reaching the build through Testcontainers is cleared.** `SSH.NET` 2025.1.0 arrived transitively via Testcontainers 4.13.0 and carries **GHSA-q939-rpr3-3284 / CVE-2026-48798** — arbitrary file write from a hostile SCP server during a recursive download. The integration test project now pins **2026.0.0**, the first patched release, as a direct reference. This is a test-only dependency and the exposure was theoretical: Testcontainers uses SSH.NET solely for its port-forwarding container, a path these tests never take, and no test connects to an SCP server at all. The override is safe because Testcontainers declares a version floor rather than an exact pin, so nothing is being forced past a supported range. It also removes the finding from the build's advisory report, which is what keeps a real one visible.
