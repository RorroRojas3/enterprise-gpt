## [Unreleased]

### Added

- **Document retrieval (RAG)** — the assistant can now read the documents attached to a conversation. Uploading a file previously changed nothing about the answers a user got; a new `document_search` tool, attached automatically to every turn where the conversation has documents, searches the conversation's own files and — when it is in one — its project's, and hands back the passages that answer the question, each with a citation like `handbook.pdf p.12` for the model to quote inline. Search is **hybrid**: a cosine vector pass finds text that means the same thing, a keyword pass finds the exact tokens embeddings are weak at (error codes, part numbers, surnames), and the two are fused by rank. Matches are widened into their neighbouring chunks and merged into whole passages with the repeated overlap written once, so the model reads complete thoughts rather than text that stops mid-sentence. A relevance gate is deliberate and load-bearing: a question the documents do not answer returns **no** passages and says which documents were searched, rather than the least-bad text in the corpus dressed up as evidence. One thing about the result shape surprises everyone — passages are ordered by the fused rank of both passes, **not** by the `score` field, so a passage matched on an exact term can sit first with the lowest score of the set. **Requirements and limits:** retrieval needs a tool-enabled model (on one that cannot call tools it is skipped with a warning and the answer is ungrounded), and it needs a SQL Server 2025 engine or Azure SQL Database for the `vector` type — a 2025 LocalDB counts, so check `SERVERPROPERTY('ProductVersion')` for major version `17` rather than assuming a local instance is too old; what does block local development is a database carried over from an earlier version of the application, which has no chunk tables for retrieval to read. There is **no schema change and no migration**: it reads the columns ingestion already writes, needs no vector index, and needs no `PREVIEW_FEATURES` (the `vector` type and `VECTOR_DISTANCE` are GA on Azure SQL Database). Documents ingested with a different embedding deployment than the one now configured must be re-uploaded. Tuning lives under `Documents:Retrieval` and is validated at startup — `MaxDistance` (0.62) trades groundedness against recall and `MaxResultTokens` (3000) caps how much evidence competes with the answer for the context window. Search queries and retrieved passages are never streamed to the client and never recorded in the usage audit; the activity feed shows only "Searching 3 documents…" and how many passages came back. See [docs/documents/retrieval.md](docs/documents/retrieval.md).
- **A new web client at `enterprise-gpt-ui/`, rebuilt from scratch** against [docs/prd/enterprise-ui-rebuild.md](docs/prd/enterprise-ui-rebuild.md) — Angular 21, zoneless, standalone, Vitest — replacing the deleted `enterprise-ui/`, which could not read the framed SSE stream. Nothing was migrated. This first batch is foundation only: there is no sign-in, no chat screen and no routes yet, so the app is not yet usable. Two things in it change how the client is deployed and operated. **Configuration is now read at runtime, not compiled in:** one build artifact is promoted across every environment and `config.json` — the API base URL, the Entra ID client, authority and scopes, and the renderer feature flags — is replaced per environment, so there are no `environments/` files and no build-time replacements, and a production bundle can no longer ship pointed at `localhost`. Serve `config.json` uncached beside `index.html`, and overwrite it as a deployment step. **A broken deployment now says so:** the page shows a startup shell from first paint, and a `config.json` that is missing, unreachable, or invalid switches it to a failure message naming the offending field, with a retry button — instead of the blank page that failure used to produce. Because the shell starts visible, it also covers the bundle itself never loading. Internally, every API failure is normalized into one typed error covering all ten of the API's problem types, so a `traceId` reaches the user for support, failed validation lands on the field that caused it, and idempotent GETs retry gateway errors with jittered backoff while a busy conversation (409) and a misconfigured provider or storage (503) deliberately do not. See [docs/ui/frontend-foundation.md](docs/ui/frontend-foundation.md).
- Anthropic as a first-party LLM provider, so Claude models can be served directly by Anthropic rather than through Amazon Bedrock and sit in the catalog beside Azure OpenAI and Bedrock models. A model's provider still selects the chat client that serves its turns: the Anthropic provider id is `6f93ec17-e981-409f-a523-700584f1e7d6`, and its models carry a **bare** model id in `deploymentName` — `claude-opus-5`, not the `anthropic.`-prefixed, date-suffixed form Bedrock uses, a mistake startup validation catches. Anthropic stays off unless `Anthropic:Enabled` is `true`; when it is on, `ApiKey`, `DefaultModelId`, `DefaultMaxOutputTokens`, `Timeout`, `MaxRetries`, `Thinking`, and `Effort` are all validated at startup and the application refuses to boot if any is missing or invalid. Authentication is a single Anthropic API key — no region, and the key is supplied explicitly so an `ANTHROPIC_API_KEY` on the host cannot authenticate a deployment whose configured key is wrong. MCP tool calling, SSE streaming, and token accounting work on Anthropic unchanged, and a model whose provider has no client in this deployment still fails with the existing 503 `/problems/provider-not-configured` rather than falling through to the other provider that happens to serve Claude. See [docs/models/anthropic.md](docs/models/anthropic.md).
- `Anthropic:Thinking` (`adaptive` or `disabled`, default `adaptive`) and `Anthropic:Effort` (`low`, `medium`, `high`, `xhigh`, or `max`, default `high`) control how much every Anthropic turn reasons before answering — including the conversation-naming turn that runs on a conversation's first message. Both are deployment-wide: a model row carries no per-model override, so every Anthropic-backed model in the catalog runs at the same setting, and changing either needs a restart. Disabled thinking above `high` effort is rejected at startup, because the models reject that combination on every request. Two things to know before sizing a deployment: `Anthropic:DefaultMaxOutputTokens` (default 32768) is the ceiling on **every** Anthropic turn rather than a fallback, and with thinking on it covers reasoning and answer text together — fitted to the expected answer alone, turns truncate; and sampling parameters (`temperature`, `top_p`, `top_k`) are cleared on every Anthropic turn, because the models this provider targets reject them.
- **Request logging and Application Insights** — the API now writes an access-log record for every request, so a request that failed without raising an exception is no longer invisible. A 403 from the permission filter, a 401 challenge, an oversized upload and an unrouted 404 previously produced no log line at all; they now each produce one, at a level that carries the meaning (5xx and faults at Error, 4xx and slow requests at Warning, everything else at Information), with the method, path, status, duration, route, caller and outcome on it. Records go through `ILogger` under the category `Enterprise.Gpt.Api.Middleware.RequestLoggingMiddleware` — deliberately outside the `Microsoft.AspNetCore` prefix pinned to Warning — so setting `"Enterprise.Gpt.Api.Middleware": "Warning"` yields a complete error log and nothing else. Query string values, the request path and captured payloads are redacted and stripped of control characters, and logging can never fail a request. Optional request/response body capture is **off by default** and, when switched on, captures every request rather than only failures, so treat it as a debugging session rather than a setting: conversation and document routes are excluded, non-text media types are refused, and SSE streaming is unaffected. Configuration lives under `RequestLogging` and is validated at startup — note that setting any list in configuration **replaces** its default rather than extending it. Application Insights is wired through the Azure Monitor OpenTelemetry distro and registers only when `APPLICATIONINSIGHTS_CONNECTION_STRING` or `AzureMonitor:ConnectionString` is set, so local runs and tests stay exporter-free; once configured, access-log records land in `traces` correlated by `operation_Id` with the `traceId` the API already returns on problem responses, and the LLM spans and `gen_ai.client.token.usage` the chat clients were already emitting are finally exported. Check the distro's default sampling (5 traces/second) before relying on the log under load. See [docs/observability/request-logging.md](docs/observability/request-logging.md).
- **Projects** — a user-owned container that groups conversations and gives them a shared document set and standing instructions. Manage projects at `api/projects`, upload documents into one with `POST api/documents/projects/{projectId}` (same pipeline and upload-status route as conversation uploads), and place a conversation in a project with `projectId` on conversation create or update. A project's instructions are read fresh on every turn and applied as request-level instructions, so editing them affects conversations that already exist without altering their transcripts. Deleting a project removes its documents but keeps its conversations, which become standalone. Note two things before adopting it: `PUT api/conversations` replaces the whole conversation, so an omitted `projectId` removes it from its project; and a project's documents reach a conversation only through document retrieval, so they influence answers only on a tool-enabled model. The new `Core.Project`, `Core.ProjectDocument` and `Core.ProjectDocumentChunk` tables and the `Core.Conversation.ProjectId` column ship as EF model changes only — there is no migration and no DDL script, so they must be applied to each real database out of band before the feature can be used (SQL Server 2025 or later). See [docs/projects/project-management.md](docs/projects/project-management.md).
- **Document download** — users can now retrieve the original file behind a document they uploaded, from a conversation with `GET api/documents/conversations/{conversationId}/{documentId}` or from a project with `GET api/documents/projects/{projectId}/{documentId}`. The API never proxies the bytes: it authorizes the caller and returns `{ downloadUrl, fileName, expiresAt }`, and Azure Storage serves the file from a short-lived, read-only service SAS — which keeps 50 MB transfers off the API process, since a read path has none of the queue and concurrency limits that bound ingestion. **Treat `downloadUrl` as a credential, not a link:** anyone holding it can read the file until it expires, so the response is sent `Cache-Control: no-store`, the URL is never logged, and `downloadUrl` is now a default redacted property name in request logging. Lifetime is `Documents:DownloadUrlLifetimeMinutes` (default 5 minutes, range 1–60, absent from `appsettings.json` so it runs on the default); an issued link **cannot be revoked** before it expires, which is why the window is minutes. Access follows the parent conversation or project's owner rather than whoever uploaded the file, and a document the caller cannot see returns **404, never 403**, so the route cannot be used to probe for ids — no permission grant is involved, as `Upload File` gates uploading only. The link renames the file back to its uploaded name and serves it as an attachment with a content type derived from the validated extension (unrecognised extensions fall back to `application/octet-stream`). One deployment requirement: signing needs a **shared-key** `AzureStorage:ConnectionString` and a set `AzureStorage:DocumentsContainer`, or every download fails with the new 503 `/problems/storage-not-configured`; moving to `DefaultAzureCredential` later means switching to a user-delegation SAS. Clients should navigate to `downloadUrl` rather than fetching it, which needs no `Authorization` header and no storage CORS rule — the Angular app has no consumer for these routes yet. See [docs/documents/download-workflow.md](docs/documents/download-workflow.md).

- **Per-tool token tracking** — token usage is now attributed to the individual tool, MCP server or agent that consumed it, with nesting preserved, instead of disappearing into one undifferentiated total for the turn. A tool that calls an LLM of its own, an MCP call whose server spends tokens internally, and an agent-as-tool running a different model than the assistant are each recorded, and a tool invoked inside another tool is recorded underneath it. Every turn writes its invocations to the new append-only `Core.ConversationUsageToolCall` table: which tool ran, of what kind, under which parent, correlated to a catalog MCP server where that can be established, how long it took, whether it succeeded, and what it cost. The token columns split deliberately — each row carries its **own** consumption in `InputTokens`/`OutputTokens`/`TotalTokens` and the whole-subtree rollup in `SubtreeTotalTokens` — so `SUM` over any filter counts each token exactly once, while the end-to-end cost of one call stays a single-column read. `Core.ConversationUsage` gains `ToolInputTokens` and `ToolOutputTokens` alongside them, leaving `InputTokens`/`OutputTokens` to mean the assistant's own model turns; the assistant-only figure is now `AssistantTokens` and `TotalTokens` means the whole call. Two honest limits: nothing in a tool call names the model behind it — an MCP server is opaque by construction — so `ModelId` and `DeploymentName` are recorded only where this application knows the answer itself, which today is nowhere; and there is still no reporting endpoint, no UI and no price data, so this remains a SQL exercise. **Operators:** the new table and the two new columns ship as EF model changes only — no migration, no DDL script — so they must be applied to each real database out of band **before** this release is deployed; until they exist, every completed turn streams its answer and then fails. See [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).
- **Conversation usage tracking and favourites** — every model call charged to a conversation is now recorded in the new append-only `Core.ConversationUsage` table: which model, provider and deployment served it, the input/output token split, whether it completed, and (in `Core.ConversationUsageMcpServer`) which MCP servers were attached to it. The provider, deployment name and server names are snapshotted onto each row, so renaming a model or repointing it at another provider cannot rewrite the history of the calls it already served. That makes tokens by model, by provider, by user and by day — and the cost of turns users cancelled — a single `GROUP BY`, in SQL: there is no reporting endpoint and no UI yet, and no price data, so money is still a spreadsheet exercise. Conversations also remember the model and MCP selection of their most recent turn: `GET api/conversations/{id}` now answers with `modelId` and `mcpServerIds` so a client reopens a conversation on the model and tools it was last run with, with servers that have since been deactivated or revoked filtered out rather than replayed into a turn that would reject them. Favourites arrive as a dedicated `PUT api/conversations/{id}/favorite` (body `{ "isFavorite": true|false }` → 204) plus an optional `isFavorite=true|false` filter on `GET api/conversations/search`; it is its own route rather than a field on the full-representation `PUT api/conversations`, where a rename that forgot to echo the flag would silently un-favourite the conversation. **Operators:** the two new tables and the new `Core.Conversation.ModelId` and `IsFavorite` columns ship as EF model changes only — no migration, no DDL script — so they must be applied to each real database out of band **before** this release is deployed; until they exist, a conversation's first turn fails outright and every later turn streams its answer and then loses it. See [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).

### Changed

- **Breaking — `POST api/conversations/{id}/stream` now emits structured events instead of raw answer text.** The response is framed server-sent events, one `data:` line per event, carrying answer text, reasoning, and a start/progress/completion record for every tool, MCP call and agent the turn invokes — so a client can show what the assistant is doing while it does it, and rebuild the tool tree from the `scopeId`/`parentScopeId`/`depth` each event carries. A final event reports the turn's token usage. Every existing client of this route breaks: it previously read the body as plain text and appended it verbatim, and would now render the framing. `enterprise-ui` is knowingly left on the old contract and is being rewritten against the new one separately; the package supplying the contract ships a matching TypeScript definition and fold function to build that on. See [docs/conversations/streaming-contract.md](docs/conversations/streaming-contract.md).
- **A conversation's token counters now include what its tools spent.** `Core.Conversation.InputTokens`/`OutputTokens` and the Cosmos transcript's `totalTokens` move by everything a turn consumed rather than by the assistant's own model turns alone, so a conversation's displayed total will be higher than before for any turn that used tools. Existing reports that add `ConversationUsage.InputTokens + OutputTokens` now compute the assistant-only figure and understate such turns; the updated queries are in [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).
- `GET api/conversations/{id}` now returns `ConversationDetailDto`, which adds `modelId` and `mcpServerIds` to the existing shape, and `ConversationDto` — returned by conversation create, update and search — gains `modelId` and `isFavorite`. Both are additive: existing clients keep working, and a conversation that has not had a turn yet reports `"modelId": null` and an empty `mcpServerIds`, which is indistinguishable from a turn that selected no MCP servers.
- **Operators:** the Anthropic row in `Core.Ref.Provider` ships as an EF `HasData` seed only — this release contains no migration and no DDL script, so the row reaches test databases built by `EnsureCreated()` but not a real one, and the gap fails silently. Insert it by hand with the id `6F93EC17-E981-409F-A523-700584F1E7D6` and the name `Anthropic`, or every attempt to create an Anthropic-backed model returns 404 "Provider not found" regardless of configuration — and a row created with a freshly generated id creates models happily and then 503s on every turn. Steps in [docs/models/anthropic.md](docs/models/anthropic.md#101-the-anthropic-provider-row-does-not-reach-a-migrated-database).

### Fixed

- **The API project did not compile.** `Microsoft.OpenApi` was pinned to 3.9.0, where `IOpenApiMediaType.Example` became read-only, while the XML-comment source generator shipped with `Microsoft.AspNetCore.OpenApi` 10.0.10 still assigns it — so the build failed inside generated code and no amount of source changes could clear it. The pin moves to 2.11.0, which stays in-major for the generator and is above 2.7.5, the patched release for GHSA-v5pm-xwqc-g5wc that motivated pinning in the first place. Both packages move together when a matching `Microsoft.AspNetCore.OpenApi` ships.
- A turn abandoned or faulted mid-stream now records what its **tools** spent as well as what the assistant spent. Usage is collected out of band from the tracking middleware rather than read off the response, so an outcome that never reaches the end of the stream still accounts for itself. The provider-side limit is unchanged and unavoidable: usage is reported at the end of a model turn, so tokens from a turn cut off mid-generation were billed and cannot be known — a cancelled turn's recorded cost is a lower bound.
- Token accounting no longer loses the calls it could not see. A turn the user stopped, or one that faulted mid-stream, consumed tokens the provider billed for and moved nothing: its cost simply vanished. Such turns are now added to the conversation's running totals and recorded with a `Cancelled` or `Failed` outcome — while still, deliberately, being kept out of the transcript, since replaying a truncated answer to the model on every later turn is worse than not having it. The completion that names a conversation from its first prompt was likewise a real, billed model call recorded nowhere; it now writes its own usage row and counts towards the conversation's totals, which means totals and reports built on them no longer understate what was spent.
