## [Unreleased]

### Added

- **Document retrieval (RAG)** — the assistant can now read the documents attached to a conversation. Uploading a file previously changed nothing about the answers a user got; a new `document_search` tool, attached automatically to every turn where the conversation has documents, searches the conversation's own files and — when it is in one — its project's, and hands back the passages that answer the question, each with a citation like `handbook.pdf p.12` for the model to quote inline. Search is **hybrid**: a cosine vector pass finds text that means the same thing, a keyword pass finds the exact tokens embeddings are weak at (error codes, part numbers, surnames), and the two are fused by rank. Matches are widened into their neighbouring chunks and merged into whole passages with the repeated overlap written once, so the model reads complete thoughts rather than text that stops mid-sentence. A relevance gate is deliberate and load-bearing: a question the documents do not answer returns **no** passages and says which documents were searched, rather than the least-bad text in the corpus dressed up as evidence. One thing about the result shape surprises everyone — passages are ordered by the fused rank of both passes, **not** by the `score` field, so a passage matched on an exact term can sit first with the lowest score of the set. **Requirements and limits:** retrieval needs a tool-enabled model (on one that cannot call tools it is skipped with a warning and the answer is ungrounded), and it needs a SQL Server 2025 engine or Azure SQL Database for the `vector` type — a 2025 LocalDB counts, so check `SERVERPROPERTY('ProductVersion')` for major version `17` rather than assuming a local instance is too old; what does block local development is a database carried over from an earlier version of the application, which has no chunk tables for retrieval to read. There is **no schema change and no migration**: it reads the columns ingestion already writes, needs no vector index, and needs no `PREVIEW_FEATURES` (the `vector` type and `VECTOR_DISTANCE` are GA on Azure SQL Database). Documents ingested with a different embedding deployment than the one now configured must be re-uploaded. Tuning lives under `Documents:Retrieval` and is validated at startup — `MaxDistance` (0.62) trades groundedness against recall and `MaxResultTokens` (3000) caps how much evidence competes with the answer for the context window. Search queries and retrieved passages are never streamed to the client and never recorded in the usage audit; the activity feed shows only "Searching 3 documents…" and how many passages came back. See [docs/documents/retrieval.md](docs/documents/retrieval.md).
- **A new web client at `enterprise-gpt-ui/`, rebuilt from scratch** against [docs/prd/enterprise-ui-rebuild.md](docs/prd/enterprise-ui-rebuild.md) — Angular 21, zoneless, standalone, Vitest — replacing the deleted `enterprise-ui/`, which could not read the framed SSE stream. Nothing was migrated. This first batch is foundation only: there is no sign-in, no chat screen and no routes yet, so the app is not yet usable. Two things in it change how the client is deployed and operated. **Configuration is now read at runtime, not compiled in:** one build artifact is promoted across every environment and `config.json` — the API base URL, the Entra ID client, authority and scopes, and the renderer feature flags — is replaced per environment, so there are no `environments/` files and no build-time replacements, and a production bundle can no longer ship pointed at `localhost`. Serve `config.json` uncached beside `index.html`, and overwrite it as a deployment step. **A broken deployment now says so:** the page shows a startup shell from first paint, and a `config.json` that is missing, unreachable, or invalid switches it to a failure message naming the offending field, with a retry button — instead of the blank page that failure used to produce. Because the shell starts visible, it also covers the bundle itself never loading. Internally, every API failure is normalized into one typed error covering all ten of the API's problem types, so a `traceId` reaches the user for support, failed validation lands on the field that caused it, and idempotent GETs retry gateway errors with jittered backoff while a busy conversation (409) and a misconfigured provider or storage (503) deliberately do not. See [docs/ui/frontend-foundation.md](docs/ui/frontend-foundation.md).
- **The web client's state layer** — the five composable `@ngrx/signals` features every one of the client's sixteen planned stores builds on, written and specced before the first store exists so that two hand-rolled pagination implementations never have to be reconciled later. `withRequestStatus` holds the lifecycle of a request as **one** value (`idle | pending | fulfilled | { error }`), so "loading and errored at the same time" — where stale spinners come from — is unrepresentable, and its error arm carries the whole typed error rather than a message, because the toast shows the `traceId` support will ask for. `withOffsetPagination` reads the API's paginated envelope and derives from the offset it has actually reached rather than the envelope's page numbers, so a short final page, a page size the server clamped down, and a total that is an exact multiple of the page size all behave without a special case. `withPendingIds` tracks in-flight work per row, so renaming one conversation no longer disables the other forty. `withClientQuery` and `withResetOnSignOut` complete the set, alongside a first, deliberate use of the `@ngrx/signals/events` plugin for the one thing plain store methods cannot do: sign-out, where a single event has to reach route-scoped stores that a root service cannot reach and that do not know each other exist. **Two constraints are encoded as behaviour rather than left to each screen's good intentions.** No endpoint in this API accepts a sort parameter, so client-side sort is offered only over a set the client holds in full — where it does not, the sort keys are ignored, results stay in server order, and the feature hands the UI the sentence explaining why, because a silently disabled control reads as a bug. Filtering is still allowed over an incomplete set but is qualified: a count computed over part of the data reports itself as partial, so "No projects match" can be rendered as "No matches among the projects loaded so far" instead of as a false statement about the user's data. **Four traps are worth knowing before writing a store**, all of which fail quietly rather than loudly: `withResetOnSignOut` must be composed **last** — it snapshots the store's initial state during construction, so a state-contributing feature after it survives sign-out and leaves the previous user's data in a half-cleared store, which the type system cannot catch and a development-only startup check therefore throws on, naming the offending keys; clearing state is not cancelling work, so any store that loads asynchronously must also drop in-flight responses on sign-out or they will write the previous user's rows back over the cleared state; the pending-id updaters replace the set rather than mutating it, because a mutated set is the same reference and produces no signal write at all — nothing re-renders, nothing fails, the list just stops updating; and "fully loaded" reads true before anything has been fetched, so it must be paired with request status wherever that distinction decides what the user sees. Separately, the markdown stack moved from markdown-it to **`ngx-markdown` 21.3.0 over marked and Prism** to match the rendering design (a stable head plus a volatile tail per streamed answer, with DOMPurify behind its sanitizer provider), and `bootstrap-icons` was added so no icon font is fetched from a third-party origin. Both are installed and imported nowhere yet, so the initial bundle is unchanged at **220.34 kB** raw against a 240 kB warning and a 300 kB failure — the cost lands, and the baseline is restated, when EP-6 wires them. See [docs/ui/frontend-foundation.md](docs/ui/frontend-foundation.md).
- **Light and dark theming in the web client, with no flash of the wrong one.** The theme follows the operating system by default, can be pinned either way from a control in the app, and is remembered across sessions. The part worth knowing is what it took to make the *first* frame correct: a small script in `index.html` resolves the stored preference and paints the document before any stylesheet loads, and the production build's critical-CSS inliner had to be turned off for that to work at all — it inlines only the rules matching the static HTML, so a theme chosen at runtime was never in the inlined set and the real stylesheet then loaded non-blocking, which meant a dark-theme user painted a light frame no matter how early the script ran. Every colour comes from one token vocabulary transcribed from the design bundle's `theme.css`, and a build check (`npm run check:tokens`) diffs the two, so a colour changed in the design and not the app — or a token added to one theme and forgotten in the other — is a red build rather than a screen someone notices in dark mode three weeks later. Two colours are deliberately *not* the designers': the focus indicator, because the brand accent measures 2.5–2.7:1 on every light surface in the kit and WCAG asks for 3:1, and the tooltip flyout, whose hard-coded background is the dark theme's page background and would have been invisible in it. See [docs/ui/design-system.md](docs/ui/design-system.md).
- **The web client now serves its own fonts, icons and brand imagery — it makes zero third-party requests at runtime.** The design prototypes pull React, Bootstrap, Bootstrap Icons and Google Fonts from CDNs; none of that reaches the application. Three type faces ship as twelve WOFF2 files from our own origin, with the two on the critical path preloaded and the rest fetched only when a rule needs them; icons ship as a single SVG sprite built from a checked-in manifest of the 74 glyphs the design actually uses, rather than an icon font whose stylesheet alone is 72 kB and which would carry 2,078 glyphs to draw them; and the brand images are WebP derived from the design bundle's PNGs, 732 kB down to 81 kB. The sprite is *injected* into the page rather than referenced as a file, which is the difference between icons that follow the theme and icons that render black in both — an externally referenced sprite resolves `currentColor` against its own document. Adding an icon is a two-step change (edit the manifest, rebuild the sprite) and three separate checks catch a name that exists in only one of those places. Generated fonts and icons are rebuilt automatically before every start, build and test; brand images are rebuilt on demand and committed, which keeps a native image binary off the build's critical path.
- **A shared UI kit for the web client** — about twenty presentational components covering overlays, feedback, data tables, badges, chips, cards, search and navigation, so screens are assembled rather than hand-rolled. The accessibility contracts live in the components instead of in each screen's good intentions: focus moves into an overlay and returns to whatever opened it, including when the overlay is closed by a route change; errors and warnings are announced assertively while success and progress are announced politely, through two live regions that exist from app start because one created alongside its first message is never read out; and the table's ARIA roles are written out explicitly, because the CSS grid layout the design uses strips the implicit ones in Chrome and Firefox. Several places deliberately depart from the design boards, which the PRD authorises where accessibility is at stake: real checkboxes instead of icon glyphs for row selection, real buttons for every clickable icon, genuinely disabled pager ends instead of dimmed text, 44px touch targets at the mobile breakpoint, and a tooltip that supplies the accessible *name* of the icon-only control it labels rather than a description that would leave the control nameless. **There is no Bootstrap JavaScript anywhere:** modals and drawers are the browser's own `<dialog>` in the top layer, where the page behind them is genuinely inert, and the menu and tooltip are about 3.9 kB of our own code — together replacing 86 kB. Bootstrap's CSS is imported module by module, 230 kB trimmed to a 60 kB stylesheet. The initial bundle is re-baselined at **349.83 kB** raw against a raised 360 kB warning and 400 kB failure, with the stylesheet held to its own 65/80 kB budget; MSAL will need another raise when sign-in lands. A development-only `/ui-kit` route renders every component in both themes side by side and is never shipped to production. See [docs/ui/design-system.md](docs/ui/design-system.md).
- **The web client's copy of the streaming contract is now vendored and drift-checked.** The TypeScript types and the fold function that turn the chat stream into an activity tree are copied byte for byte out of the `Andes.Extensions.AI.UI` NuGet package — the same package the API serialises that stream with — instead of being re-typed by hand. `npm run check:contract` compares the file against the installed package and, just as importantly, against the package version the API actually references, because a byte comparison alone keeps passing after the API upgrades and would leave the client quietly folding a stale contract. It also fails if anyone hand-declares one of the four public symbols somewhere else. The file is excluded from the formatter and the linter for the same reason it is checked: reformatting it *is* the drift.
- **Lint and build gates for the web client.** ESLint is now wired (flat config over typescript-eslint, angular-eslint's template and accessibility rules, and the NgRx Signals rules that police the store patterns the state layer was written against), joined by four Node checks that cover what a lint rule cannot see: an icon name that is not in the sprite, a Google Fonts or CDN origin, a design token that has drifted from the design bundle, and a diagram or math library that has leaked into the initial bundle. That last one is not a size budget — a chunk created by a dynamic import has no entry point for a size budget to attribute bytes to, so it would sum zero and never fail; this check walks the build's own module graph and names the library and the import path that pulled it in. `bypassSecurityTrustHtml` is banned outright, structurally and again as a text scan that also catches an inline lint suppression, because model output is attacker-influenceable through uploaded documents and MCP tool results and the markdown renderer already performs that trust after sanitising. Unused-symbol detection stays with the TypeScript compiler rather than ESLint, so it runs on every build and every test instead of only under `npm run lint`.
- **Sign-in and the session in the web client — the app is now something a person can be *in*.** Users authenticate with their work account through Microsoft Entra ID over the MSAL redirect flow, and no screen renders before the client knows who they are and what they may do: a guard resolves `POST api/users/me` first, then requests the model and MCP catalogs, and a user with **zero** permission grants is a valid session rather than a load failure. Four full-page states cover the paths that are not the happy one — signing in, sign-in didn't complete, couldn't start (with the `traceId` support will ask for, and a Retry), and access denied — each of which used to be a blank page. There is no password field anywhere; every credential is Entra's. **The administration area is withheld rather than hidden:** its code chunk is never requested by a user without the `Administrator` permission, because the guard runs during URL recognition rather than after the download, the Admin entry is absent from the navigation instead of shown-and-disabled, and a build check fails the whole build if a stray static import ever pulls the admin code into the initial bundle where everyone would get it. **Three things a contributor will trip over.** Angular runs every guard in a single `canActivate` array *concurrently*, so ordering two of them is possible only by nesting them on separate route levels — putting sign-in and session checks in one array would call the API before a token existed. `@azure/msal-angular` is installed and deliberately **used nowhere**: its guard cannot run in the phase that keeps a lazy chunk off the wire, its service replays a consumed redirect and bounces the user to the failure page right after a *successful* sign-in, and its event service routes through `NgZone`, which is a no-op in this zoneless app — roughly 120 lines over `@azure/msal-browser` replace it, and the package stays in `package.json` only because an earlier story's criteria require it installed. And the startup card in `index.html` is now removed on the first settled navigation rather than when bootstrap finishes, so no empty app shell paints while the guards are still deciding; its watchdog moved 30s → 60s to match, since a cold API can legitimately hold that screen for tens of seconds. **Security posture:** tokens live in `sessionStorage`, not `localStorage`, so nothing outlives the tab on a shared machine — the visible cost is that a second tab re-establishes through Entra; the post-sign-in return URL is validated against open redirects; the consumed authorization code is kept out of browser history; and MSAL's PII log channel is off. **Operators:** `config.json` carries the Entra client id, authority and scopes, and MSAL's security settings are deliberately *not* in it, so a deployment cannot weaken them by editing one file; note that the `/`-prefixed redirect URIs in the committed copy resolve against the origin, which is wrong under a sub-path deployment. The initial bundle is re-baselined at **629.33 kB raw / 151.96 kB transfer** against a raised 650 kB warning and 720 kB failure — MSAL is **248.9 kB** of it, not the ~150 kB previously estimated, because the estimate missed `msal-common`, and none of it can be deferred. Upload gating and sign-out complete this epic and are listed separately below. Note that the browser sign-in has **not** been exercised against a live Entra tenant. See [docs/ui/authentication-and-session.md](docs/ui/authentication-and-session.md).
- **Sign-out in the web client — signing out now leaves nothing behind.** A user footer in the app chrome shows who is signed in and offers Sign out; pressing it empties every store, wipes the MSAL token cache and the crypto keystore, ends the Entra ID session, and lands on a new `/signed-out` page. **It also signs out every other tab.** The token cache is `sessionStorage`, which is per tab, so a second window would otherwise sit there fully signed in — a broadcast tells the others to tear down and leave. What deliberately *survives* is the theme and sidebar preference and nothing else, and that is enforced by a build gate rather than a cleanup pass: `localStorage` now has exactly one permitted call site with an enumerated key list, and the build fails on a write anywhere else, so the guarantee holds for stories not yet written. **The landing page is not the home page, on purpose.** If the round trip to Entra never happens — an unreachable tenant, a blocked redirect — the Entra session cookie is still live, so returning to `/` would take the user through the chat route and silently re-authenticate the person who just walked away from the machine; the client wipes local state and lands on an explicit signed-out page with a deliberate "Sign in again" instead. **Two things to know when it misbehaves.** A blocked redirect leaves the "Signing you out…" screen up for up to 30 seconds before the fallback runs, and shortening MSAL's timeout is not the fix — the same setting governs sign-in. And a sign-out attempt clears the counter that terminates an inconclusive sign-in loop, so a badly broken tenant restarts that count afterwards. **Operators:** `postLogoutRedirectUri` in `config.json` now points at `/signed-out`, which must be registered as a post-logout redirect URI in the Entra app registration; without it Entra shows its own signed-out page, which degrades gracefully. This and the upload work close EP-2 of the client rebuild, and together they cost 7.77 kB — the initial bundle finishes the epic at **637.10 kB raw / 153.38 kB transfer**, inside the 650/720 kB budget set when sign-in landed, so no re-baseline was needed. Note that neither the end-session round trip nor the `/signed-out` landing has been exercised against a live Entra tenant. See [docs/ui/authentication-and-session.md](docs/ui/authentication-and-session.md).
- **Upload rights are now enforced in the web client, ahead of the screen that will use them.** A user without the `Upload File` permission gets no attach control at all — absent, not disabled — and the prompt box, which still has to render and still has to accept typing, will not react to a dropped file. Those are two different requirements and they needed two different mechanisms; the second is a reusable drop-zone directive that takes the permission as a **required** input, so an unbound one is a compile error rather than a silently open drop zone, and an administrator is never assumed to hold the grant. Separately and for **every** user, including one with no upload rights at all: a file dropped anywhere outside a live drop zone is now swallowed instead of navigating the browser to it, which previously meant losing the page and, mid-answer, the reply streaming into it. The composer that consumes all of this is still to come (EP-8); until then the pieces are exercised by a test host and by a toggleable drop zone in the development-only `/ui-kit` gallery. See [docs/ui/authentication-and-session.md](docs/ui/authentication-and-session.md).
- **The web client now has a shell, and a user can reach their conversations.** Signing in lands on a persistent sidebar listing every conversation, newest first, with a search field and a one-click route back into any of them; the conversation that is open is marked as the current page for a screen reader as well as visually, from the same fact rather than two that can disagree. **The sidebar collapses to a 60px icon strip and is still collapsed next time** — that preference is deliberately one of exactly two things (with the theme) that survive signing out, because it describes the machine rather than the person, and a build gate enforces that nothing else joins them. **"New conversation" creates nothing.** It opens an empty screen with the wordmark and "How can I help you today?", and no conversation exists until the first prompt is actually sent, so abandoning an idea no longer litters the sidebar with empty rows — the suggested prompt chips the design shows are held back until the composer that gives them something to do arrives. Three things about the list are stated rather than hidden: it is **paged**, so when there are more than fifty a "Load more" row says so instead of presenting the first fifty as all of them; a failed *further* page raises a toast and keeps the rows already on screen, where a failed *first* page gets a panel with the `traceId`; and a Retry button is offered only where pressing it could plausibly work — a 403 or a "no such conversation" gets an explanation and no button, because a Retry that cannot succeed reads as broken. Rows are ordered by when a conversation was **created**, not last touched, which is the server's ordering and the client does not re-sort it: renaming a conversation or adding a turn will not move it to the top, and no sort control is offered until the API can sort (there is no honest way to sort one page of many). Searching sends the `name` parameter, which is worth recording because the deleted client sent `filter` — the server bound nothing and every search silently returned everything, looking exactly like a search that matched. **For contributors, two decisions shape everything built on top of this.** The conversation list store is the reference the app's remaining fifteen stores are written against: it loads declaratively from one wired query rather than from call sites scattered through the app, and it carries two separate rules that stop a "Load more" page landing inside a result set it does not belong to — without both, a page arrives against a list that has been replaced underneath it and leaves rows the user can never scroll to, with no error anywhere. And the chat screen is served for both `/chat` and `/chat/{id}` from a **single** route configuration, so moving between them changes a parameter instead of destroying and rebuilding the page — which is what lets the next story create a conversation around the first prompt while the answer is already streaming into it. Both the shell and the chat screen are loaded on demand, which keeps roughly 24 kB of signed-in chrome off the sign-in, sign-in-failed, couldn't-start and signed-out pages and leaves room for the markdown renderer still to come; the initial bundle moves only 6.52 kB, to **643.62 kB raw / 158.05 kB transfer**, and only the warning threshold moved (650 → 660 kB) with the failure threshold unchanged at 720 kB. Renaming, favouriting, deleting and moving a conversation between projects are the next stories and are not here yet, and none of this has been exercised against a live API. See [docs/ui/shell-and-navigation.md](docs/ui/shell-and-navigation.md).
- **Conversations can now be renamed and deleted in the web client**, from each sidebar row's kebab menu and from a new actions menu on the conversation header, which routes through the same two flows rather than reimplementing them — US-304, US-306 and US-308, closing phase P2 of the rebuild. Rename opens a modal with a live 256-character counter; the sidebar shows the new name immediately, and a server refusal puts the old name back and renders the server's message inline under the field — where it clears itself the moment the user edits the rejected value, and blocks resubmitting the identical doomed one until they do. Delete confirms in a modal that names the conversation (messages go, uploaded files stay; initial focus lands on Cancel, so Enter on a freshly opened destructive confirm destroys nothing), then removes the row at once while the request settles in the background: success raises a toast, failure restores the row to the position it was removed from — unless the user searched mid-flight, in which case the restore is deliberately refused rather than splicing a row into a result set it may not belong to, and a page fetch that would otherwise leave a permanent one-row hole is cancelled. Deleting the conversation that is open navigates to the empty chat screen only when the delete actually completes, never optimistically, and only for a user still looking at it. While a conversation's own action is in flight, its menu items disable — that conversation's, not the other forty's. Two decisions land underneath for every story that follows: the rename dialog is the application's **first Signal Form** (`@angular/forms/signals`), now the recorded standard for all future forms — a product-owner decision of 2026-08-11; the API is experimental in Angular 21.2, so it is re-checked on every upgrade — and every conversation update builds its body through one builder that always echoes `projectId`, because the API's `PUT` replaces the whole conversation and an omitted field would silently pull it out of its project. The favourite star, the project-move items and the sub-768px mobile header are deliberately deferred to their own stories. See [docs/ui/conversation-actions.md](docs/ui/conversation-actions.md).
- **The web client can now read the chat stream, and the composer can say what a turn should use** — the four stories beneath sending a message (US-402–US-405). Nothing sends yet: the send button renders with its real disable conditions and no click handler, which is the next story's, so this ships as the tested pipeline under it. A framework-free codec decodes the framed SSE stream correctly across arbitrary chunk boundaries — a frame split mid-JSON or mid-character reassembles, a malformed frame is skipped rather than allowed to kill a live turn, and an unknown event kind drops through an exhaustive table so a contract upgrade that adds a ninth kind fails compilation instead of silently discarding events in production — with a `features.rawStreamCodec` config flag selecting a raw-text fallback for a deployment still on the pre-framing server. The transport reads errors first: a pre-stream failure arrives as ordinary problem JSON parsed before a single body byte, every error the stream emits is the client's one typed error, and a bare 401 is replayed exactly once with a force-refreshed token — while the 403 consent problem structurally cannot enter that path. Stop, sign-out, and unsubscribing all abort the underlying fetch while keeping every batch already delivered, a failure after the body began completes gracefully because the wire cannot distinguish it from a network drop, and events arrive in ~16ms batches so the eventual chat store folds once per animation frame at any token rate. In the composer, the model picker preselects the catalog's default declaratively — "no explicit choice" is a state of its own, so the selection self-heals catalog reloads and resets on sign-out — and the app never sends blind: until a model resolves, including when the catalog fails to load, send is disabled and the model menu offers Retry. The tools picker is a stay-open multi-select whose gating invariant is enforced twice: choosing a model that cannot call tools visibly clears the selection and names the model, and the wire-facing set is re-derived to empty so even stale settings seeded later can never trigger the server's 400. Two deviations agreed with the design: the tools rows omit the mono key column, because the API's MCP shape carries no key field to fill it, and the tool-server-unavailable panel is deferred to the turn-edge-state cards it belongs beside. The initial bundle moves 3.97 kB to **647.59 kB raw**, inside the 660/720 kB budget. See [docs/conversations/streaming-client.md](docs/conversations/streaming-client.md).
- **The web client can now hold a conversation: send a prompt, watch the answer stream in, and stop it mid-turn** — US-401, US-406, US-407 and US-501, the first end-to-end chat slice, which also closes two recorded deferrals (the landing screen's four suggested prompt chips, and the tool-server-unavailable card). Sending the first prompt creates the conversation *around* it: nothing exists until Send is pressed, then the conversation is created, appears at the top of the sidebar, and the URL is replaced in place while the answer is already streaming into the same screen — so the browser's Back never returns to a half-created state. The answer renders as it arrives with a blinking caret, as plain text until the markdown story lands, and everything the assistant does on the way — tool calls, MCP calls, agents, reasoning — appears as activity cards interleaved with the text **in the order it happened**, each carrying the tool's name, a kind badge, its source verbatim, and a running/completed/failed state with the duration once done. Turns that end abnormally are told apart honestly: a stream that dies without its completion signal keeps the partial answer in the transcript under a "cut off" warning with a Retry that re-sends that turn's own prompt and settings, while **Stop** keeps the partial output on a detached "Stopped — not saved to this conversation" card offering Copy and a Retry that restores the prompt, model and tool selection into the composer without re-sending — and a Stop that races a clean finish resolves in the server's favour, because the answer *was* saved and a card claiming otherwise would lie. Send and Stop are one morphing button, so keyboard focus survives the swap, and abnormal endings are announced to assistive tech through a persistent status region. The transcript — including the activity timeline, which the server deliberately does not transcribe — lives for the session only: reopening a conversation replays nothing until the history story (US-410). All new code rides the lazy chat chunk; the initial bundle moves ~1 kB to **648.75 kB raw**, inside the 660/720 kB budget. See [docs/conversations/turn-lifecycle.md](docs/conversations/turn-lifecycle.md).
- **Assistant answers now render as markdown — and it cannot execute** (US-601). Headings, lists, tables, links, task lists, quotes and fenced code with syntax highlighting replace the plain pre-wrapped text the transcript showed before; single newlines still break the line, so answers users had already read do not silently reflow. Model output is untrusted input — it can quote an uploaded document or an MCP tool result — so **two independent layers** stand between it and the page: raw HTML is dropped at the parser (`<script>alert(1)</script>` never becomes markup at all, an inline `<em>x</em>` degrades to its text), and DOMPurify then filters what is left against a closed profile of exactly the tags and attributes markdown can produce, with data attributes off and `javascript:` links reduced to inert text. Neither layer is load-bearing alone. Two deliberate policies come with it: **images are dropped and their alt text rendered in their place**, because the client makes no third-party request at run time and a remote image in an answer is both such a request and a read receipt for whoever hosts it; and **headings inside an answer shift down a level**, because the conversation title is the page's heading and a model's `#` would otherwise open a second one. Task-list checkboxes are announced as "Completed" or "Not completed" rather than as unlabelled controls — the box is the only thing carrying that state, since the text beside it reads the same either way. The whole renderer — `ngx-markdown`, marked, Prism and DOMPurify, **124.8 kB** — loads only with the chat screen, so no other page pays for it, and the build now fails if any of it ever reaches the initial download. That resolves the rebuild's last open budget question: the initial bundle grows 11.5 kB to **660.24 kB raw / 161.01 kB transfer** — Angular's own sanitizer implementation and some stylesheet, not the markdown libraries — and its warning threshold is re-stated 660 → 665 kB with the 720 kB failure ceiling unchanged. See [docs/ui/answer-rendering.md](docs/ui/answer-rendering.md).
- **A long answer now stays smooth all the way to the end** (US-602). The renderer re-parses everything it is given on every update, so an answer bound to it whole would re-parse itself from the top for each of the ~60 updates a second a fast model produces, getting slower the longer it got. A streaming answer is therefore rendered in two pieces — the part that has stopped changing and the part still arriving — split at the last point where one block ends and the next begins, so the settled part re-parses once per **block** instead of once per token, and a half-written code block is kept whole with the text it belongs to rather than cut down the middle. Code that is still arriving is deliberately left unhighlighted, because highlighting half a line against a grammar it does not satisfy yet produces flicker; when the turn finishes, the whole answer renders once, canonically, highlighting and all — and a test asserts that final render is character-for-character identical to rendering the same answer in one go, so the optimisation cannot change what the reader ends up with.
- **An agent's own tool calls now appear inside that agent's card** (US-502). The activity timeline used to flatten everything into one column, so a search an agent ran on your behalf looked exactly like a search the assistant ran directly. Nested work is now drawn inside the card that caused it, behind an indent rail, with each level of nesting on its own surface tint and slightly tighter type so depth reads without a label — three levels as the design draws them, and anything deeper reuses the third, because an agent tree can nest as far as it likes. On a phone only the outermost level indents: the deeper cards keep the rail that says "inside" but stop stealing width, which below 390px is the difference between a third-level card showing its name and showing nothing. Nothing about the stream or the way it is folded changed — this is entirely how it is drawn. One subtlety worth recording, because it looks like a bug and is not: a nested activity whose parent the client never saw (its parent arrived late, or not at all) is still shown, at the top level, rather than being dropped. An unattached card is a cosmetic imperfection; a dropped one is a tool call that silently never happened.
- **A failed tool call now says how long it took before it failed** (US-505). Most of this was already true — a failure marks only the activity that failed, so a failed tool call inside an agent no longer looks like the agent failing, and it never marks the turn itself as failed — but US-502's nesting is what makes that visible instead of merely correct. What is new is for screen-reader users: the card's state now reads "Failed after 0.6s" rather than a bare "Failed", since the warning colour and glyph were the only thing carrying that before, and the difference between a call that timed out and one that refused immediately is worth a second of listening. **The card still carries no failure *reason*** — the stream sends none, and inventing one would be worse than the silence.
- **A completed turn now shows what it cost** (US-504). The token counts land in a footer under the answer — `1,842 in · 512 out · 2,354 total` — so usage is visible without leaving the chat. A count the provider did not report is left out rather than shown as a zero, because a turn that reported no output tokens did not produce none; and a turn that never completed cleanly claims nothing at all, which covers stopped turns, cut-off turns and anything replayed from a reopened conversation, none of which the counts survive. Each activity card also gains a chevron opening onto what that step cost. **Two limits are deliberate and will close later.** The per-activity strip shows the duration only, because nothing on the wire attributes tokens to an individual tool, MCP call or agent yet — the columns appear the moment something does. And the footer is always visible rather than appearing on hover as the design draws it: a hover-only footer is unreachable by keyboard and touch, and it stays visible until US-607 puts a Copy control in it worth focusing.
- **You can now watch the model think** (US-503). When a model streams a reasoning summary, it appears in its own collapsible region above the answer — a "Reasoning" pill with the elapsed time, opening onto the summary itself — and it fills the pause that used to show only an animated placeholder, so the wait before the first word is now readable rather than merely occupied. It stays open for the rest of the turn once you open it. Two things about it are worth knowing. **The opening sentence every turn starts with is not shown**, because the server writes it, not the model; this client's standing rule is that it never presents a status line as though the model said it, so a turn whose only "reasoning" is that sentence shows no region at all. And **the duration is measured in your browser**, from the model's first real reasoning to its first word of the answer, because no such figure exists on the wire — it deliberately excludes the queue and network time before the model started, which is why it can read lower than the gap you sat through. Reasoning is not stored anywhere: reopening a conversation shows the answers, never the thinking behind them.
- **Every code block in an answer now has a Copy button** (US-603). Each fenced block is drawn with a header bar naming its language and a Copy control that puts the block on your clipboard — the exact source, entities and all, not what highlighting made of it — confirming with "Copied" for two seconds. For screen-reader users each button is named for its block ("Copy ts code block"), so six code blocks in one answer are six distinguishable controls rather than six identical ones, and the confirmation is announced through its own live region — including when you copy a second block while the first is still confirming. The control is part of the rendered answer rather than something bolted onto the page afterwards, which is what keeps it stable while an answer is still streaming into it, and one listener on the transcript serves every block on screen. **A security note, because this is the first time the renderer's two independent safety layers lean on each other:** drawing that chrome means the sanitizer must now permit `<div>` and `<button>`, which markdown itself cannot produce. Model text still cannot create either — raw HTML is discarded before the sanitizer ever sees it — but the two allowances are safe *because* of that earlier layer rather than regardless of it, so a test drives forged copy-button markup through the real pipeline to make sure a regression there fails a build instead of shipping. The language label is restricted to real language characters rather than escaped, so nothing in a code fence's info string can become an attribute. The button carries no icon: the design draws one, but the icon set is an SVG sprite and admitting SVG to the sanitizer is a far bigger opening than a Copy button is worth. The initial download grows about 1 kB, to **661.36 kB raw / 161.19 kB transfer**, inside the unchanged 665/720 kB budget.
- **The transcript follows the newest message, or stays where you are reading** (US-606). While an answer streams and you are at the bottom, the view keeps pace with it; scroll up to re-read something and it stops moving, with a round jump-to-latest button appearing above the composer — pulsing while the turn is still running, and staying put once it ends, because a finished turn deliberately does not yank the page down and hiding the button then would strand you. Pressing it returns to the newest content, resumes following, and puts keyboard focus on the transcript rather than dropping it to the top of the page. "At the bottom" is judged with about a line of tolerance, so being a few pixels short still counts as following.
- **Conversations can be marked as favourites** (US-305), from a new item in the sidebar row's menu or from the star on the conversation header — the control that header shipped without. The star and the sidebar row flip together the moment you click, before the server answers; if the request fails, both go back and an error toast names the trace id to quote in a support request. Favouriting deliberately does **not** touch the conversation's "last modified" time, so the sidebar's ordering does not shuffle when you star something old, and a double-click sends one request rather than two racing to decide the outcome. Filtering the list down to favourites is still to come (US-703).
- **Reopening a conversation now shows what was said in it, and the chat screen's remaining edge cases have their designed treatments** — US-408, US-409, US-410, US-412 and US-413, closing EP-4 of the client rebuild. **Conversations have a past again.** Opening one from the sidebar used to show its title over an empty screen, because nothing in the client had ever fetched the stored messages; it now replays them, and restores the model and tool servers the conversation last ran with, so the next turn behaves like the last one. A model that has since been deactivated is *stated* rather than silently swapped — the composer falls back to the default and says so, once the catalog has actually loaded, so a deep link does not flash a warning it then withdraws. A transcript read back **shorter** than the one on screen, which is what an aborted turn leaves behind, **replaces** the local copy rather than merging into it: an abandoned exchange must not linger on screen looking like something the model saw. What replay deliberately does **not** restore is the activity timeline — the stream that produces tool, MCP, agent and reasoning cards is never transcribed, so history is answer text only, and that is permanent rather than pending; closing it would need a new server-side record of a turn. **A new conversation acquires its server-generated name on its own**, the moment its first turn completes, instead of sitting in the sidebar under a placeholder until something else refreshes it — and only a turn that actually finished triggers it, so a stopped or cut-off attempt does not send the client to read back a name that was never generated. **Two failures that used to render as a generic warning now say what they are:** a second tab already answering in the same conversation produces a one-line "Another response is still running in this conversation." with a Retry and, deliberately, no automatic retry at any interval, since the only thing that resolves it is the other turn ending; and a tool server that needs interactive consent produces a card naming the server and stating that no authorization flow is available yet and to contact an administrator — with **no** button, because the scope a consent request needs is not on the wire until US-411 puts it there. The sentence a screen-reader user hears for that second case was also wrong and is corrected: it said the server needed "your authorization", which nobody in this deployment can supply. **And a prompt can now be spoken.** A microphone in the composer transcribes through the browser's own speech recognition: **Enterprise GPT never receives the audio** — none of it reaches the application's code or the API, and there is no server-side transcription service in the product — though the browser itself may recognise remotely (Chrome does), which is the thing to evaluate before encouraging it in a regulated tenant. The control is **absent rather than disabled** where the browser has none (Firefox, and any non-secure origin); finalized phrases *append* to what is already typed instead of replacing it, and a blocked microphone is explained in place while the prompt box stays usable. Keyboard users get a fix that only shows up in the loop this work is about: retrying a failed turn destroyed the button that was pressed and dropped focus to the page body, so every attempt meant re-traversing the page; focus now returns to the replacement Retry. Everything here rides the lazy chat chunk, so the initial bundle is **unchanged at 660.25 kB raw / 160.99 kB transfer** against the 665/720 kB budget. See [docs/conversations/turn-lifecycle.md](docs/conversations/turn-lifecycle.md).

Anthropic stays off unless `Anthropic:Enabled` is `true`; when it is on, `ApiKey`, `DefaultModelId`, `DefaultMaxOutputTokens`, `Timeout`, `MaxRetries`, `Thinking`, and `Effort` are all validated at startup and the application refuses to boot if any is missing or invalid. - `Anthropic:Thinking` (`adaptive` or `disabled`, default `adaptive`) and `Anthropic:Effort` (`low`, `medium`, `high`, `xhigh`, or `max`, default `high`) control how much every Anthropic turn reasons before answering — including the conversation-naming turn that runs on a conversation's first message. Both are deployment-wide: a model row carries no per-model override, so every Anthropic-backed model in the catalog runs at the same setting, and changing either needs a restart. Disabled thinking above `high` effort is rejected at startup, because the models reject that combination on every request. Two things to know before sizing a deployment: `Anthropic:DefaultMaxOutputTokens` (default 32768) is the ceiling on **every** Anthropic turn rather than a fallback, and with thinking on it covers reasoning and answer text together — fitted to the expected answer alone, turns truncate; and sampling parameters (`temperature`, `top_p`, `top_k`) are cleared on every Anthropic turn, because the models this provider targets reject them.
- **Models can now show their reasoning, and it is opt-in per model.** When a model is asked for a reasoning summary, the account of its thinking streams into the chat while it works — filling the reasoning region the client has had all along and that Azure-served turns never once populated. The switch is a new `isReasoningEnabled` field on the model catalog, editable by an administrator through `POST`/`PUT api/models` and **off for every existing model**: a deployment that does not support reasoning **rejects the whole request** rather than ignoring the option, so the failure mode is total and the capability is asked for rather than assumed. It is not free either — reasoning tokens are billed as output tokens, and deeper reasoning also means a longer wait before the first word. How verbose the summary is and how hard the model thinks are deployment-wide rather than per-model: `AzureAIFoundry:ReasoningSummary` (`auto`, `concise`, `detailed`, or `none` to ask for no summary while still reasoning; default `auto`) and `AzureAIFoundry:ReasoningEffort` (`minimal`, `low`, `medium`, `high`; default `medium`), both validated at startup and read once, so changing either needs a restart. **Two limits are worth stating.** The flag is **Azure-only** today — the Bedrock and Anthropic clients take their reasoning settings from their own configuration, so setting it on a model either of them serves changes nothing. And reasoning is still never stored: it is streamed and shown, never written to the transcript, so reopening a conversation shows the answers and not the thinking behind them. **Operators:** this ships as a real EF migration, `20260813233326_AddModelIsReasoningEnabled`, which `Database.Migrate()` applies at startup — the second migration in the repository after `InitialCreate` — adding `Core.Ref.Model.IsReasoningEnabled` as `bit NOT NULL DEFAULT 0`. **Clients** of the model API get one new additive field, but note that `PUT api/models/{id}` replaces the whole model, so an update that omits it silently turns reasoning off. See [docs/models/azure-ai-foundry.md](docs/models/azure-ai-foundry.md#5-reasoning) and [docs/models/model-management.md](docs/models/model-management.md#23-isreasoningenabled).
- **A fabricated weather tool, for exercising the assistant's activity timeline.** The timeline's running rings, sub-status bullets, durations and failed cards previously needed a live MCP server or an uploaded document to appear at all, which meant the surface was rarely looked at outside a test fixture. A fake `get_weather` function, attached to every turn when `Tools:Weather:Enabled` is set, gives the timeline something to draw from a real conversation: it reports two sub-statuses as it runs, takes a configurable `Tools:Weather:DelayMilliseconds` (default 600) so the running state is visible at all — an instant tool call completes inside a single stream flush and the card appears already finished — and **fails deliberately for any location whose name contains `fail`**, which is the only way to reach the failed card on demand. Everything it answers with is invented, so it is **off by default**; enabling it in Production is permitted but prints a warning to standard error at startup, and the model will report its invented readings to users as fact. Like every other tool it stands down on a model that cannot call tools, with a warning rather than a failed turn, and its progress messages deliberately carry no part of the model's arguments — the same privacy posture as every other activity event. Setup is in the [README](README.md#3-configure-api-environment-variables).
- **Request logging and Application Insights** — the API now writes an access-log record for every request, so a request that failed without raising an exception is no longer invisible. A 403 from the permission filter, a 401 challenge, an oversized upload and an unrouted 404 previously produced no log line at all; they now each produce one, at a level that carries the meaning (5xx and faults at Error, 4xx and slow requests at Warning, everything else at Information), with the method, path, status, duration, route, caller and outcome on it. Records go through `ILogger` under the category `Enterprise.Gpt.Api.Middleware.RequestLoggingMiddleware` — deliberately outside the `Microsoft.AspNetCore` prefix pinned to Warning — so setting `"Enterprise.Gpt.Api.Middleware": "Warning"` yields a complete error log and nothing else. Query string values, the request path and captured payloads are redacted and stripped of control characters, and logging can never fail a request. Optional request/response body capture is **off by default** and, when switched on, captures every request rather than only failures, so treat it as a debugging session rather than a setting: conversation and document routes are excluded, non-text media types are refused, and SSE streaming is unaffected. Configuration lives under `RequestLogging` and is validated at startup — note that setting any list in configuration **replaces** its default rather than extending it. Application Insights is wired through the Azure Monitor OpenTelemetry distro and registers only when `APPLICATIONINSIGHTS_CONNECTION_STRING` or `AzureMonitor:ConnectionString` is set, so local runs and tests stay exporter-free; once configured, access-log records land in `traces` correlated by `operation_Id` with the `traceId` the API already returns on problem responses, and the LLM spans and `gen_ai.client.token.usage` the chat clients were already emitting are finally exported. Check the distro's default sampling (5 traces/second) before relying on the log under load. See [docs/observability/request-logging.md](docs/observability/request-logging.md).
- **Projects** — a user-owned container that groups conversations and gives them a shared document set and standing instructions. Manage projects at `api/projects`, upload documents into one with `POST api/documents/projects/{projectId}` (same pipeline and upload-status route as conversation uploads), and place a conversation in a project with `projectId` on conversation create or update. A project's instructions are read fresh on every turn and applied as request-level instructions, so editing them affects conversations that already exist without altering their transcripts. Deleting a project removes its documents but keeps its conversations, which become standalone. Note two things before adopting it: `PUT api/conversations` replaces the whole conversation, so an omitted `projectId` removes it from its project; and a project's documents reach a conversation only through document retrieval, so they influence answers only on a tool-enabled model. The new `Core.Project`, `Core.ProjectDocument` and `Core.ProjectDocumentChunk` tables and the `Core.Conversation.ProjectId` column ship as EF model changes only — there is no migration and no DDL script, so they must be applied to each real database out of band before the feature can be used (SQL Server 2025 or later). See [docs/projects/project-management.md](docs/projects/project-management.md).
- **Document download** — users can now retrieve the original file behind a document they uploaded, from a conversation with `GET api/documents/conversations/{conversationId}/{documentId}` or from a project with `GET api/documents/projects/{projectId}/{documentId}`. The API never proxies the bytes: it authorizes the caller and returns `{ downloadUrl, fileName, expiresAt }`, and Azure Storage serves the file from a short-lived, read-only service SAS — which keeps 50 MB transfers off the API process, since a read path has none of the queue and concurrency limits that bound ingestion. **Treat `downloadUrl` as a credential, not a link:** anyone holding it can read the file until it expires, so the response is sent `Cache-Control: no-store`, the URL is never logged, and `downloadUrl` is now a default redacted property name in request logging. Lifetime is `Documents:DownloadUrlLifetimeMinutes` (default 5 minutes, range 1–60, absent from `appsettings.json` so it runs on the default); an issued link **cannot be revoked** before it expires, which is why the window is minutes. Access follows the parent conversation or project's owner rather than whoever uploaded the file, and a document the caller cannot see returns **404, never 403**, so the route cannot be used to probe for ids — no permission grant is involved, as `Upload File` gates uploading only. The link renames the file back to its uploaded name and serves it as an attachment with a content type derived from the validated extension (unrecognised extensions fall back to `application/octet-stream`). One deployment requirement: signing needs a **shared-key** `AzureStorage:ConnectionString` and a set `AzureStorage:DocumentsContainer`, or every download fails with the new 503 `/problems/storage-not-configured`; moving to `DefaultAzureCredential` later means switching to a user-delegation SAS. Clients should navigate to `downloadUrl` rather than fetching it, which needs no `Authorization` header and no storage CORS rule — the Angular app has no consumer for these routes yet. See [docs/documents/download-workflow.md](docs/documents/download-workflow.md).

- **Per-tool token tracking** — token usage is now attributed to the individual tool, MCP server or agent that consumed it, with nesting preserved, instead of disappearing into one undifferentiated total for the turn. A tool that calls an LLM of its own, an MCP call whose server spends tokens internally, and an agent-as-tool running a different model than the assistant are each recorded, and a tool invoked inside another tool is recorded underneath it. Every turn writes its invocations to the new append-only `Core.ConversationUsageToolCall` table: which tool ran, of what kind, under which parent, correlated to a catalog MCP server where that can be established, how long it took, whether it succeeded, and what it cost. The token columns split deliberately — each row carries its **own** consumption in `InputTokens`/`OutputTokens`/`TotalTokens` and the whole-subtree rollup in `SubtreeTotalTokens` — so `SUM` over any filter counts each token exactly once, while the end-to-end cost of one call stays a single-column read. `Core.ConversationUsage` gains `ToolInputTokens` and `ToolOutputTokens` alongside them, leaving `InputTokens`/`OutputTokens` to mean the assistant's own model turns; the assistant-only figure is now `AssistantTokens` and `TotalTokens` means the whole call. Two honest limits: nothing in a tool call names the model behind it — an MCP server is opaque by construction — so `ModelId` and `DeploymentName` are recorded only where this application knows the answer itself, which today is nowhere; and there is still no reporting endpoint, no UI and no price data, so this remains a SQL exercise. **Operators:** the new table and the two new columns ship as EF model changes only — no migration, no DDL script — so they must be applied to each real database out of band **before** this release is deployed; until they exist, every completed turn streams its answer and then fails. See [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).
- **Conversation usage tracking and favourites** — every model call charged to a conversation is now recorded in the new append-only `Core.ConversationUsage` table: which model, provider and deployment served it, the input/output token split, whether it completed, and (in `Core.ConversationUsageMcpServer`) which MCP servers were attached to it. The provider, deployment name and server names are snapshotted onto each row, so renaming a model or repointing it at another provider cannot rewrite the history of the calls it already served. That makes tokens by model, by provider, by user and by day — and the cost of turns users cancelled — a single `GROUP BY`, in SQL: there is no reporting endpoint and no UI yet, and no price data, so money is still a spreadsheet exercise. Conversations also remember the model and MCP selection of their most recent turn: `GET api/conversations/{id}` now answers with `modelId` and `mcpServerIds` so a client reopens a conversation on the model and tools it was last run with, with servers that have since been deactivated or revoked filtered out rather than replayed into a turn that would reject them. Favourites arrive as a dedicated `PUT api/conversations/{id}/favorite` (body `{ "isFavorite": true|false }` → 204) plus an optional `isFavorite=true|false` filter on `GET api/conversations/search`; it is its own route rather than a field on the full-representation `PUT api/conversations`, where a rename that forgot to echo the flag would silently un-favourite the conversation. **Operators:** the two new tables and the new `Core.Conversation.ModelId` and `IsFavorite` columns ship as EF model changes only — no migration, no DDL script — so they must be applied to each real database out of band **before** this release is deployed; until they exist, a conversation's first turn fails outright and every later turn streams its answer and then loses it. ### Changed

- **Every chat turn's stream now opens with two server-synthesized frames** — a `Status` event (`"Starting"`, with a real timestamp) and a `ReasoningDelta` (`"Reviewing the request and preparing a response."` plus a separating blank line), emitted ahead of the first model event so a client hears something during model latency instead of silence. Three consequences for stream consumers: every turn carries two new leading frames; reasoning text is now non-null on every turn whatever the model — a deliberate, product-requested deviation from the package's model-sourced `ReasoningDelta`, so the field's presence no longer implies a reasoning-capable model; and the response commits to `text/event-stream` before the model's first token, so a provider that faults on its very first token (a bad deployment, an expired key, quota) now surfaces as a truncated stream rather than pre-stream problem JSON — every failure before that point (busy 409, not-found 404, first-turn naming, model resolution 503, MCP validation, consent and tool acquisition) still arrives as `application/problem+json`. The web client deliberately keeps its thinking indicator up through these frames and does not render them yet. See [docs/conversations/streaming-contract.md](docs/conversations/streaming-contract.md).
- **Breaking — `POST api/conversations/{id}/stream` now emits structured events instead of raw answer text.** The response is framed server-sent events, one `data:` line per event, carrying answer text, reasoning, and a start/progress/completion record for every tool, MCP call and agent the turn invokes — so a client can show what the assistant is doing while it does it, and rebuild the tool tree from the `scopeId`/`parentScopeId`/`depth` each event carries. A final event reports the turn's token usage. Every existing client of this route breaks: it previously read the body as plain text and appended it verbatim, and would now render the framing. `enterprise-ui` is knowingly left on the old contract and is being rewritten against the new one separately; the package supplying the contract ships a matching TypeScript definition and fold function to build that on. See [docs/conversations/streaming-contract.md](docs/conversations/streaming-contract.md).
- **A conversation's token counters now include what its tools spent.** `Core.Conversation.InputTokens`/`OutputTokens` and the Cosmos transcript's `totalTokens` move by everything a turn consumed rather than by the assistant's own model turns alone, so a conversation's displayed total will be higher than before for any turn that used tools. Existing reports that add `ConversationUsage.InputTokens + OutputTokens` now compute the assistant-only figure and understate such turns; the updated queries are in [docs/conversations/usage-and-favorites.md](docs/conversations/usage-and-favorites.md).
- `GET api/conversations/{id}` now returns `ConversationDetailDto`, which adds `modelId` and `mcpServerIds` to the existing shape, and `ConversationDto` — returned by conversation create, update and search — gains `modelId` and `isFavorite`. Both are additive: existing clients keep working, and a conversation that has not had a turn yet reports `"modelId": null` and an empty `mcpServerIds`, which is indistinguishable from a turn that selected no MCP servers.
- **Azure AI Foundry turns now go through the Responses API instead of Chat Completions.** The chat client is built on the plain OpenAI client pointed at Foundry's OpenAI-compatible v1 endpoint, rather than on `AzureOpenAIClient`, because reasoning summaries exist only on that surface — over Chat Completions Azure returns none, whatever the deployment, which is why the assistant's reasoning region was always empty. **Answers, tools, streaming, telemetry and token accounting are unchanged**, and the other two providers are untouched. Three things do change for operators. **The `AzureAIFoundry` section is now validated at startup**, where it was previously read with unchecked configuration lookups: a missing key or a malformed URL refuses to boot with a message naming the setting, instead of throwing on the first conversation. **`AzureAIFoundry:Url` must be the resource root** — the v1 path is derived from it, so a URL that already carries `/openai` or `/openai/v1` is now a startup failure rather than an unexplained 404 on every turn; both the `services.ai.azure.com` and `openai.azure.com` hosts are accepted, and no new setting was added. And **document embeddings deliberately did not move**: they stay on `AzureOpenAIClient` against the same resource root, because embeddings have no Responses equivalent and every vector already in the database depends on that client behaving identically. **On privacy, the posture is preserved rather than inherited:** the Responses API retains prompts and answers service-side for 30 days by default, where Chat Completions stored nothing, so every turn is sent with storage explicitly disabled — the transcript this application keeps remains the only copy. That also happens to be what keeps tool calling working, since the whole exchange has to travel in each request once the service is no longer tracking it. See [docs/models/azure-ai-foundry.md](docs/models/azure-ai-foundry.md).
- **Operators:** the Anthropic row in `Core.Ref.Provider` ships as an EF `HasData` seed only — this release contains no migration and no DDL script, so the row reaches test databases built by `EnsureCreated()` but not a real one, and the gap fails silently. Insert it by hand with the id `6F93EC17-E981-409F-A523-700584F1E7D6` and the name `Anthropic`, or every attempt to create an Anthropic-backed model returns 404 "Provider not found" regardless of configuration — and a row created with a freshly generated id creates models happily and then 503s on every turn. Steps in [docs/models/anthropic.md](docs/models/anthropic.md#101-the-anthropic-provider-row-does-not-reach-a-migrated-database).

### Fixed

- **The assistant's reasoning never appeared.** The chat screen has a region for the model's thinking, and on every Azure-served turn it stayed empty — the only reasoning text a turn ever carried was the opening sentence the server writes itself, which the client deliberately does not show. Nothing in the pipeline was missing: the stream already carries reasoning frames and the client already renders them. What was missing was a provider that emits any, because Azure returns reasoning summaries only on the Responses API (see Changed) and only for a deployment that was asked for one (see Added). Turns on a model with `isReasoningEnabled` set now fill the region as the model works.
- **The API project did not compile.** `Microsoft.OpenApi` was pinned to 3.9.0, where `IOpenApiMediaType.Example` became read-only, while the XML-comment source generator shipped with `Microsoft.AspNetCore.OpenApi` 10.0.10 still assigns it — so the build failed inside generated code and no amount of source changes could clear it. The pin moves to 2.11.0, which stays in-major for the generator and is above 2.7.5, the patched release for GHSA-v5pm-xwqc-g5wc that motivated pinning in the first place. Both packages move together when a matching `Microsoft.AspNetCore.OpenApi` ships.
- A turn abandoned or faulted mid-stream now records what its **tools** spent as well as what the assistant spent. Usage is collected out of band from the tracking middleware rather than read off the response, so an outcome that never reaches the end of the stream still accounts for itself. The provider-side limit is unchanged and unavoidable: usage is reported at the end of a model turn, so tokens from a turn cut off mid-generation were billed and cannot be known — a cancelled turn's recorded cost is a lower bound.
- Token accounting no longer loses the calls it could not see. A turn the user stopped, or one that faulted mid-stream, consumed tokens the provider billed for and moved nothing: its cost simply vanished. Such turns are now added to the conversation's running totals and recorded with a `Cancelled` or `Failed` outcome — while still, deliberately, being kept out of the transcript, since replaying a truncated answer to the model on every later turn is worse than not having it. The completion that names a conversation from its first prompt was likewise a real, billed model call recorded nowhere; it now writes its own usage row and counts towards the conversation's totals, which means totals and reports built on them no longer understate what was spent.
